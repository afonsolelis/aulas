2. The case: the market of Pokémon cards on TCGplayer

TCGplayer is the largest marketplace of collectible cards in the United States. For each product it lists, a single card in a given printing or a sealed product such as a booster box, it publishes a market price computed from recent sales, together with the lowest, the middle and the highest listing. The public site tcgcsv.com mirrors the catalogue and the prices of TCGplayer once a day and keeps a daily archive of the prices, which makes it possible to know the price of a card on past dates without an account or a key of the official API, whose access is restricted to approved partners.

The case of the lesson takes the seven Pokémon TCG sets released in 2026, from ME: Ascended Heroes in January to ME06: Delta Reign in November, with their 1,490 products and the prices of those products on five dates. Collectors, stores and investors ask different questions of the same prices: a collector wants the current value of a card, a store wants to know which rarities and printings are worth keeping in stock, and an investor wants to know which cards gained value during the year. The last question is the question of the session.

The question needs care, because a set is not priced all at once. TCGplayer lists the sealed products of a set in pre-sale weeks before the release, and the single cards enter the price list after the release, many of them weeks later. A comparison between the total value of a set on two dates therefore mixes appreciation with coverage, and the only valid comparison of appreciation is the same card, in the same printing, on two dates.

4. The lab in the browser

The lab page loads DuckDB compiled to WebAssembly, which runs the same SQL engine as the command line, inside the tab and without a server. On the first visit the page downloads the compressed landing table, keeps it in the localStorage of the browser and creates db_ingestion from it; on later visits the copy in the localStorage is used, and the page works without network once DuckDB itself is in the cache. Every statement that creates, changes or removes an object is also kept, and it runs again when the page reloads, so the model built during the session survives a reload or the closing of the tab.

The localStorage holds about 5 MB per site, counted in characters of two bytes, and is shared by every page of the same address. The compressed landing table occupies about 343 KB of it and the statements of the complete model less than 20 KB, which leaves room for the other pages of the portal. The data itself lives in the memory of the tab while it is open: what persists is the source and the recipe, and the model is rebuilt from them in less than a second. The panel at the side of the editor shows the objects of the model, the space used, and two buttons, one that drops the model and keeps the data, and one that forgets everything.

The choice of the browser has a teaching purpose and a limit. It removes every installation from the session, so that the time is spent on the model and not on the environment, and it makes the lab reproducible by any student at home. It does not replace a warehouse: the data of a real partner, with millions of rows, belongs to a server, which is why the second hour runs in ClickHouse.

Part IIDimensional modelling

5. Grain and dimensions

Kimball and Ross design a dimensional model in four decisions taken in order, because each one depends on the previous. The first selects the business process to be measured, which here is the pricing of a product by TCGplayer. The second declares the grain, the exact meaning of one row of the fact table: one product, in one printing, on one capture date. The third chooses the dimensions that describe the context of each row, and the fourth the numerical facts that are measured. The grain comes before the dimensions because it determines which questions the model can answer: a grain of one set per date would answer how much a set is worth on that date, but never which card appreciated, while the finer grain answers both, since the value of a set is the sum of its cards.

The dimensions of the case and their hierarchies

Each dimension has a hierarchy, an order of its attributes from the general to the specific, which is the path along which a question climbs or descends. The four dimensions of the case are written as views over the landing table, because they are small, read in every query and rarely changed; as views they keep no copy and always reflect the current landing table, at the cost of reading the JSON again at each use.

The attributes of a product arrive as a list of pairs in extendedData, and a card is told apart from a sealed product by the presence of a collector number in that list. A macro gold.attr(json, name) filters the list and returns the value of one attribute, so each attribute is one line of the view and the rule that reads the list is written once.

A natural key that repeats

The code of a set looks like a key, but TCGplayer gave the code 30C to two sets released on the same day, ME: 30th Celebration and its Classic Collection. A model that identifies or groups sets by the code merges the two without any error message, and the merged set shows a value that belongs to neither. The fact therefore refers to a set by set_id, the identifier that TCGplayer guarantees as unique, the cube groups by set_name, and the code remains in the dimension as an attribute for display. This is the role that a natural key has in a star schema: it describes the member, while the identity comes from a key that the model can trust.

6. The fact and its kind

Kimball distinguishes three kinds of fact table by what one row records. A transaction fact has one row per event, inserted once and never updated, as the item of an order in the star of Lesson 5. A periodic snapshot has one row per entity per period, even when nothing happened in the period, and records the state of the entity at that moment, as the price of a card on each capture date. An accumulating snapshot has one row per process and is updated as the process advances through its milestones, as an order with the dates of approval, shipping and delivery. The fact of this lesson is a periodic snapshot, because TCGplayer does not publish each sale but the price of the day, and the state on each capture date is the finest measurement available.

gold.fact_price is a table, not a view, because it is the only object of the star that grows with every capture and the one read by every question; as a table, its JSON is read and typed once, when the fact is built. It carries the four prices of the record and the number of days since the release of the set, computed when the fact is built, together with the keys of the product, the set, the variant and the date.

The test of the grain

The grain declared in the specification is verified with a query: the number of rows of the fact must be equal to the number of distinct combinations of its key. A larger number of rows means that the same product, variant and date appear twice, and that every sum over the fact counts some prices twice. In the case the test returns 5,951 rows and 5,951 combinations, and 49 rows without market price, which are kept because the other prices of the record are valid.

7. Additive, semi-additive and non-additive measures

A measure is classified by the dimensions across which its sum still has meaning, and the classification decides how every aggregate of the model may treat it. An additive measure can be summed across every dimension, as the number of price records. A semi-additive measure can be summed across some dimensions but not across time: the market prices of all the cards of a set on one date add up to the cost of buying one copy of each, but the price of one card summed over five dates is a number without meaning. A non-additive measure cannot be summed across any dimension, as an average or a percentage, and must be recomputed from the fact at each level.

KindAdds up acrossIn this lessonIn Lesson 5
additiveevery dimensionnumber of price recordsprice and freight of the items
semi-additiveevery dimension except timemarket priceopen orders on a day
non-additiveno dimensionaverage price of a rarity; percentage of appreciationdistinct count of orders

The classification has two practical consequences. Every aggregation of a semi-additive measure keeps the time dimension, or takes one point of it, such as the first or the last date, and never sums over it; this is why the cube of the lesson groups by the date in every one of its levels. A non-additive measure is recomputed from the fact for each cell, and an average of averages or a sum of distinct counts gives a wrong number that looks plausible, which makes the error hard to notice.

Part IIICubes and marts

8. Data cubes and OLAP

A data cube organises a measure by several dimensions at once. Each cell holds the measure for one combination of members, one set, one rarity and one variant in the case, and the totals along each dimension are cells too: the cell of a set with every rarity and every variant is the total of the set. With three dimensions there are 2³ = 8 combinations of grouped and aggregated dimensions, from the finest level, where the three are present, to the grand total, where none is.

Online analytical processing, OLAP, is the kind of workload that a cube serves: few users, wide questions over large volumes, read much more often than written. A cube can be kept in a dedicated multidimensional engine (MOLAP), as summary tables of a relational warehouse (ROLAP), or in a mix of both (HOLAP). This lesson builds the relational kind, in which the cube is a summarised fact table: a fact table with a coarser grain, computed from the base fact, that answers the frequent questions without reading every price and joining four dimensions each time.

9. CUBE, ROLLUP and GROUPING SETS

The three extensions of GROUP BY compute several groupings in one statement and return them in one result. CUBE (a, b, c) generates every combination of the listed columns; ROLLUP (a, b, c) generates only the hierarchy from left to right, that is (a, b, c), (a, b), (a) and the total; GROUPING SETS generates only the combinations listed. In a row of a level where a column was aggregated the column is NULL, and the function grouping() tells this NULL apart from a real one: with several arguments it returns a number in which each bit says whether the corresponding column was aggregated, so 0 is the finest level and 7 the total of three columns.

ClauseGeneratesFor three columns
CUBE (a, b, c)every combination8 groupings
ROLLUP (a, b, c)the hierarchy from left to right4 groupings
GROUPING SETS (...)only the listed onesas many as listed
grouping(a, b, c)a bit per aggregated column0 = finest, 7 = total

ROLLUP fits a hierarchy, such as year, quarter and month, because it generates only the meaningful levels; CUBE over the same columns would also produce the month without the year, which merges the same month of different years. The cube of the case uses CUBE, because set, rarity and variant are independent dimensions, and keeps the date outside it, in the plain GROUP BY, because the price is semi-additive. The result has 524 cells in eight levels, against 5,951 rows of the fact.

10. Views, tables and materialisation

An optimised view is a stored result that spares the repeated cost of a query, and the engines differ in how they keep that result up to date. A view keeps only its query and computes it at every read, so it is always current and pays the full cost each time. A stored result is cheap to read and remains as it was until it is computed again. DuckDB has no materialized view: a stored result is a table created with CREATE TABLE ... AS SELECT, and refreshing it means running the same statement again, which the lab does when the page replays the model. ClickHouse has two kinds of materialized view, which the second hour uses.

ObjectKeeps dataWhen it is computedIn this lesson
view (DuckDB and ClickHouse)no, only the queryat every readdimensions and mart
CREATE TABLE AS (DuckDB)yeswhen the statement runsfact and cube
incremental materialized view (ClickHouse)yes, in a target tableat every INSERT, over the inserted block onlysecond hour, for loads in batches
refreshable materialized view (ClickHouse)yes, replaced at onceon a schedule, over the whole sourcesecond hour: fact and cube

The choice follows from how often the object is read and how current it must be. A dimension that is small and changes little fits a view; a fact and a cube read by a dashboard fit a stored result, refreshed after each load. An incremental materialized view of ClickHouse sees only the rows inserted after it was created, so the rows already in the source must be loaded once, separately, with the same query.

11. Data marts and conformed dimensions

A data mart is the part of the warehouse that serves one area of the business, with the names, the granularity and the questions of that area. In the approach of Kimball the warehouse is the union of its marts, built one at a time, and what keeps them consistent is that they share their dimensions: a dimension is conformed when it has the same keys, the same attributes and the same meaning in every fact that uses it. A question that crosses two marts, such as the price of a card against the sales of a store, then compares the same sets, the same cards and the same dates.

The mart of the case, mart_collectors, has two views over gold. card_price joins the fact to its four dimensions and exposes the price of each card on each date with readable names; set_value exposes the level "set" of the cube. A dashboard reads the mart and never the landing table, so a change in the JSON of the source is absorbed by the dimensions and does not reach the users. The bus matrix records which dimension each mart uses and is the plan of the warehouse.

12. The five operations of OLAP

Every multidimensional question can be described as a movement over the cube. Roll-up climbs a hierarchy, from the card to its rarity or from the day to the month, and returns fewer cells at a higher level; drill-down descends it, from the rarity to its cards. Slice fixes one member of one dimension, such as one set, and leaves a cube with one dimension less; dice fixes several members of several dimensions, such as four rarities, three variants and one date, and leaves a smaller cube. Pivot turns the axes and shows the same cells in another layout, with the dates as columns and the sets as rows.

pivotPIVOT in DuckDB; conditional aggregation in ClickHouseQ3: value of each set on each date

Reference SQL of step 01
lab/lesson-6/sql/01_dimensions.sql
-- Lesson 6 · Step 01 · Dimensions over the landing table
--
-- Reference of the professor for prompt 01. In class the coding agent writes
-- its own version and the professor runs it in the lab page.
-- Everything reads db_ingestion, where each record is a JSON object with
-- the field names of TCGplayer.
--
-- Dimensions are views: they store no copy and always show the current
-- state of db_ingestion.

CREATE SCHEMA IF NOT EXISTS gold;

-- The extended attributes of a product arrive as a list of {name, value}.
CREATE OR REPLACE MACRO gold.attr(j, attr_name) AS
    list_filter(from_json(json_extract(j, '$.extendedData'), '[{"name":"VARCHAR","value":"VARCHAR"}]'),
                lambda e: e.name = attr_name)[1].value;

-- Set (collection): one row per set released in 2026.
CREATE OR REPLACE VIEW gold.dim_set AS
SELECT
    CAST(data_json->>'groupId' AS INTEGER)              AS set_id,
    data_json->>'name'                                  AS set_name,
    data_json->>'abbreviation'                          AS set_code,
    CAST(CAST(data_json->>'publishedOn' AS TIMESTAMP) AS DATE) AS released_on,
    strftime(CAST(data_json->>'publishedOn' AS TIMESTAMP), '%Y-%m') AS release_month
FROM db_ingestion
WHERE data_tag = 'tcgplayer.set.v1';

-- Product: a single card (it has a collector number) or a sealed product.
-- Hierarchy of the card: set > rarity > card.
CREATE OR REPLACE VIEW gold.dim_product AS
SELECT
    CAST(data_json->>'productId' AS INTEGER)            AS product_id,
    CAST(data_json->>'groupId' AS INTEGER)              AS set_id,
    data_json->>'name'                                  AS product_name,
    CASE WHEN gold.attr(data_json, 'Number') IS NULL THEN 'sealed' ELSE 'card' END AS kind,
    gold.attr(data_json, 'Number')                      AS number,
    coalesce(gold.attr(data_json, 'Rarity'), 'n/a')     AS rarity,
    gold.attr(data_json, 'Card Type')                   AS card_type,
    TRY_CAST(gold.attr(data_json, 'HP') AS INTEGER)     AS hp,
    gold.attr(data_json, 'Stage')                       AS stage
FROM db_ingestion
WHERE data_tag = 'tcgplayer.product.v1';

-- Variant: the printing of a card, which TCGplayer prices separately.
CREATE OR REPLACE VIEW gold.dim_variant AS
SELECT DISTINCT data_json->>'subTypeName' AS variant
FROM db_ingestion
WHERE data_tag = 'tcgplayer.price.v1';

-- Date of capture, with the hierarchy year > quarter > month > day.
CREATE OR REPLACE VIEW gold.dim_date AS
SELECT DISTINCT
    CAST(strftime(timestamp, '%Y%m%d') AS INTEGER) AS date_key,
    CAST(timestamp AS DATE)                        AS date,
    strftime(timestamp, '%Y-%m')                   AS month,
    year(timestamp) || '-Q' || quarter(timestamp)  AS quarter,
    year(timestamp)                                AS year
FROM db_ingestion

-- Lesson 6 · Step 02 · The fact and the test of the grain
--
-- Reference of the professor for prompt 02.
--
-- gold.fact_price is a periodic snapshot: one product, in one variant, on
-- one date of capture. It is a table, so the JSON is read and typed once.
-- Its prices are semi-additive: the market price of all the cards of a set
-- on one date adds up to the cost of the set, but adding the same card over
-- several dates means nothing.

CREATE OR REPLACE TABLE gold.fact_price AS
SELECT
    CAST(strftime(i.timestamp, '%Y%m%d') AS INTEGER)   AS date_key,
    CAST(i.data_json->>'productId' AS INTEGER)          AS product_id,
    p.set_id,
    i.data_json->>'subTypeName'                         AS variant,
    CAST(i.data_json->>'marketPrice' AS DECIMAL(10, 2)) AS market_price,
    CAST(i.data_json->>'lowPrice' AS DECIMAL(10, 2))    AS low_price,
    CAST(i.data_json->>'midPrice' AS DECIMAL(10, 2))    AS mid_price,
    CAST(i.data_json->>'highPrice' AS DECIMAL(10, 2))   AS high_price,
    date_diff('day', s.released_on, CAST(i.timestamp AS DATE)) AS days_since_release
FROM db_ingestion AS i
JOIN gold.dim_product AS p ON p.product_id = CAST(i.data_json->>'productId' AS INTEGER)
JOIN gold.dim_set     AS s ON s.set_id = p.set_id
WHERE i.data_tag = 'tcgplayer.price.v1';

-- The test of the grain: rows = distinct (date, product, variant).
SELECT count(*) AS rows,
       count(DISTINCT (date_key, product_id, variant)) AS grain_keys,
       count(*) FILTER (WHERE market_price IS NULL)    AS without_market_price
FROM gold.fact_price;

-- Prices per date and set: the sets released later appear later.
SELECT d.date, s.set_code, count(*) AS prices
FROM gold.fact_price AS f
JOIN gold.dim_date AS d USING (date_key)
JOIN gold.dim_set  AS s USING (set_id)
GROUP BY ALL ORDER BY d.date, s.set_code;

lab/lesson-6/sql/03_cube_and_mart.sql
-- Lesson 6 · Step 03 · The cube and a data mart for collectors
--
-- Reference of the professor for prompt 03.
--
-- The cube crosses set, rarity and variant on every date. It groups by
-- set_name and not by set_code, because the code 30C belongs to two sets
-- (ME: 30th Celebration and its Classic Collection): a natural key that
-- repeats would merge them.
--
-- The cube crosses set, rarity and variant on every date. Because the price
-- is semi-additive, the date stays in every grouping: GROUP BY date_key and
-- CUBE of the other three. A cell answers "on this date, how much did the
-- cards of this set, of this rarity, in this variant cost?".

CREATE OR REPLACE TABLE gold.agg_price_cube AS
SELECT
    f.date_key,
    grouping(s.set_name, p.rarity, f.variant) AS grouping_id,
    coalesce(s.set_name, 'all')               AS set_name,
    coalesce(p.rarity, 'all')                 AS rarity,
    coalesce(f.variant, 'all')                AS variant,
    count(*)                                  AS prices,
    sum(f.market_price)                       AS market_value,
    round(avg(f.market_price), 2)             AS avg_market_price,
    max(f.market_price)                       AS max_market_price
FROM gold.fact_price AS f
JOIN gold.dim_product AS p USING (product_id)
JOIN gold.dim_set     AS s ON s.set_id = f.set_id
WHERE p.kind = 'card' AND f.market_price IS NOT NULL
GROUP BY f.date_key, CUBE (s.set_name, p.rarity, f.variant);

-- A data mart for the collectors area: friendly names, one view per question.
CREATE SCHEMA IF NOT EXISTS mart_collectors;

CREATE OR REPLACE VIEW mart_collectors.card_price AS
SELECT d.date, s.set_code, s.set_name, s.released_on, p.product_name AS card, p.number,
       p.rarity, f.variant, f.market_price, f.days_since_release
FROM gold.fact_price AS f
JOIN gold.dim_date    AS d USING (date_key)
JOIN gold.dim_product AS p USING (product_id)
JOIN gold.dim_set     AS s ON s.set_id = f.set_id
WHERE p.kind = 'card';

CREATE OR REPLACE VIEW mart_collectors.set_value AS
SELECT d.date, c.set_name, c.prices, c.market_value
FROM gold.agg_price_cube AS c
JOIN gold.dim_date AS d USING (date_key)
WHERE c.grouping_id = 3;

-- Size of the cube by level.
SELECT grouping_id,
       CASE grouping_id
           WHEN 0 THEN 'set x rarity x variant' WHEN 1 THEN 'set x rarity'
           WHEN 2 THEN 'set x variant'          WHEN 3 THEN 'set'
           WHEN 4 THEN 'rarity x variant'       WHEN 5 THEN 'rarity'
           WHEN 6 THEN 'variant'                WHEN 7 THEN 'all cards' END AS level,
       count(*) AS cells
FROM gold.agg_price_cube
GROUP BY ALL ORDER BY grouping_id;

-- Why the date stays in the grouping: the value of all cards on the last
-- date is meaningful; the sum of that value over the five dates is not.
SELECT
    (SELECT market_value FROM gold.agg_price_cube WHERE grouping_id = 7 AND date_key = 20261107) AS value_on_2026_11_07,
    (SELECT sum(market_value) FROM gold.agg_price_cube WHERE grouping_id = 7)                    AS sum_over_dates_meaningless;

-- Lesson 6 · Step 04 · Five questions, one OLAP operation each
--
-- Reference of the professor for prompt 04. Every question reads the cube or
-- the mart, never db_ingestion.

-- Q1 · Roll-up: from the card to the rarity. On 07/11/2026, how much is
--      the average card of each rarity worth?
SELECT rarity, prices, avg_market_price, max_market_price
FROM gold.agg_price_cube
WHERE date_key = 20261107 AND grouping_id = 5
ORDER BY avg_market_price DESC;

-- Q2 · Slice: one set. Which are the five most expensive cards of
--      Ascended Heroes on 07/11/2026?
SELECT card, rarity, variant, market_price
FROM mart_collectors.card_price
WHERE set_code = 'ASC' AND date = DATE '2026-11-07'
ORDER BY market_price DESC LIMIT 5;

-- Q3 · Pivot: sets as rows, dates as columns. How did the market value of
--      one copy of every card of each set change? (semi-additive: it adds
--      cards inside a date, never dates)
PIVOT (SELECT set_name, strftime(date, '%m-%d') AS day, market_value FROM mart_collectors.set_value)
ON day USING sum(market_value)
GROUP BY set_name
ORDER BY set_name;

-- Q4 · Dice and pivot: the four lowest rarities, the three variants, the
--      last date. How much does each printing of the same rarity cost?
PIVOT (SELECT rarity, variant, avg_market_price
       FROM gold.agg_price_cube
       WHERE date_key = 20261107 AND grouping_id = 4
         AND rarity IN ('Common', 'Uncommon', 'Rare', 'Double Rare'))
ON variant IN ('Normal', 'Reverse Holofoil', 'Holofoil') USING max(avg_market_price)
GROUP BY rarity
ORDER BY rarity;

-- Q5 · The question of the session. Which cards appreciated most between
--      their first capture and 07/11/2026? Cards that cost at least US$ 5 at
--      the first capture, so that a few cents do not become 100 %.
WITH first_and_last AS (
    SELECT set_code, card, rarity, variant,
           arg_min(market_price, date) AS first_price,
           min(date)                   AS first_date,
           arg_max(market_price, date) AS last_price
    FROM mart_collectors.card_price
    WHERE market_price IS NOT NULL
    GROUP BY ALL
    HAVING count(*) >= 2
)
SELECT set_code, card, rarity, variant, first_date, first_price, last_price,
       last_price - first_price                         AS gain_usd,
       round(100 * (last_price / first_price - 1), 1)  AS gain_pct
FROM first_and_last
WHERE first_price >= 5
ORDER BY gain_pct DESC
LIMIT 10;

16. Recurring mistakes of agents

The traps below were found while the lab was rehearsed on 07/11/2026, and the prompts already carry the corresponding adjustments. Most of them do not raise an error and are caught only by a count or by one specific number, which is why each prompt states the facts measured in the rehearsal.

Reading the JSON

Inside a macro or a lambda of DuckDB the operator -> is read as the arrow of a lambda, and a macro written as j->'extendedData' fails with an error about a column that does not exist. The attribute must be read with json_extract(j, '$.extendedData') and the lambda written with the syntax lambda e: .... An agent that treats extendedData as an object, and not as a list of pairs, returns NULL for every rarity without any error.

Keys and joins

The fact and dim_product both carry set_id, and a chain of joins with USING (set_id) after USING (product_id) is ambiguous; the set must be joined with ON s.set_id = f.set_id. An agent that groups the cube by set_code merges the two sets with the code 30C silently, which is visible only in the value of the set.

Measures

The most frequent error of the cube is to leave the date out of the grouping, or to sum the level "all cards" over the dates, which returns US$ 51,967.84 instead of a value on one date. In Q5, comparing the value of a set between two dates confuses appreciation with coverage; the comparison must be the same card and variant, with arg_min and arg_max of the price by date. An average of rarity computed by averaging the averages of the sets gives a different and wrong number, because the sets have different numbers of cards.

The lab

The lab runs DuckDB 1.4, not the 2.0 of the command line of Lesson 5, and an agent that writes for 2.0, or that uses read_json, COPY or files, writes SQL that does not run in the browser. A statement that fails stops the script, and the statements before it are already kept in the localStorage, so the script can be corrected and run again from the failed statement.

periodic snapshota fact with one row per entity per period, recording a state
semi-additivea measure that adds up across every dimension except time
data cubea measure organised by several dimensions, with the totals of each one
summarised fact tablea fact table with a coarser grain, computed from the base fact

grouping()function that says which columns of a row were aggregated
data martthe part of the warehouse that serves one area of the business
conformed dimensiona dimension with the same keys and meaning in every fact that uses it
natural keyan identifier that comes from the source, such as the code of a set
localStoragethe key-value storage of the browser, about 5 MB per site

20. Checklist

  • The grain is declared in one sentence before any SQL.
  • The dimensions are views over the landing table, and their hierarchies are written in the specification.
  • No natural key that repeats is used as an identity.
  • The grain test returns the same number of rows and of distinct keys.
  • Every measure is classified as additive, semi-additive or non-additive.
  • The cube keeps the time dimension in every grouping when a measure is semi-additive.
  • Distinct counts and averages are computed by the cube, never by summing finer cells.
  • The mart reads the gold layer and never the landing table.
  • Each of the five questions names its OLAP operation and its query.
