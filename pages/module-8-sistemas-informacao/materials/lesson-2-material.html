3. Exploratory analysis and the information viewpoint

In Lesson 1 the group described the partner problem from two viewpoints of the RM-ODP. The enterprise viewpoint named the community, the decision at stake and the policies that constrain the use of data. The information viewpoint described the information objects that the decision needs, their relationships and the constraints over them, organised into invariant, static and dynamic schemas. That description was written before the data was read in depth, and it therefore contains assumptions that only the data can confirm.

The exploratory analysis is the procedure that tests those assumptions. Each invariant of the canvas becomes a query that counts violations, the declared grain becomes a test of uniqueness, and each relationship becomes a join whose losses are measured. The static schema is checked by looking at the state of the objects on a given date, for instance whether every store has a stock position every day. The dynamic schema is checked by following the life cycle of an object across time, for instance whether purchase orders move through the expected statuses. When a check fails, the group learns either that the data has an error or that its own description of the partner was wrong, and both outcomes are useful.

This lesson therefore closes the information viewpoint of Sprint 1. It also opens a new concern. Deciding where the sample of data is stored, under which naming convention and in which format is a decision about the mechanisms that hold the data, which belongs to the engineering viewpoint. The module develops that viewpoint in Sprints 4 and 5, but the first decisions are taken today, because every later layer of the pipeline will read from the structure created now.

Correspondence with the canvas

The findings of the analysis return to the canvas through the data quality log of section 12. Indicators that the data supports are confirmed in block 4, questions that need the partner go to block 6, checks that the pipeline must repeat go to block 14 and block j of the cube receives the correction rules.

4. The data lifecycle and the place of this lesson

Reis and Housley describe the data engineering lifecycle in five stages: generation, storage, ingestion, transformation and serving. Generation happens in the source systems, which in the illustrative case are the point-of-sale terminals and the stock control of the stores. Ingestion moves the data from those systems into the platform. Storage underlies every stage, because data is stored on arrival, after each transformation and before it is served. Transformation cleans, integrates and models the data, and serving delivers it to the people and systems that use it.

The two self-studies on lifecycles approach the same sequence from different angles. The reading on data lifecycle management emphasises the governance of each stage, from collection to deletion or archival. The reading on the analytics lifecycle emphasises the phases through which a question becomes an answer. Read together, they show that exploratory analysis sits between ingestion and transformation. It is the first moment in which the data received is examined, and its findings determine what the transformations must correct.

The consequence for the module is a clear division of work. This lesson receives a sample, explores it and stores it in a raw zone of the Data Lake. Lesson 3 organises the zones into the Bronze, Silver and Gold layers of the medallion architecture, and the lessons that follow implement the transformations, the data warehouse and the cubes. A finding recorded today, such as duplicated stock counts, becomes a rule of the Silver layer two weeks later.

5. Preparing the environment with Poetry and Jupyter

An exploratory analysis is only useful if another person can run it and obtain the same results. Reproducibility depends on the exact versions of the libraries, because functions change behaviour between versions and a notebook that runs on one machine may fail or produce different numbers on another. Poetry addresses this problem by recording the dependencies of the project in pyproject.toml and the exact versions resolved for them in poetry.lock. When the lock file is committed, every member of the group installs the same versions with a single command.

The environment is prepared before the session, as a pre-class checklist, as part of the pre-class tasks of section 2, so that the time in class is spent on the partner data and not on installing software. One member adopts the group repository with poetry init and commits the two files. The option package-mode = false, added under [tool.poetry] in pyproject.toml, tells Poetry that the repository is a set of notebooks and scripts and not a library to be packaged, so it does not look for a package with the name of the project. The other members pull the repository and run poetry install. For a project that does not exist yet, poetry new <name> && cd <name> creates the standard layout instead.

Shell · pre-class checklist, adopting the group repository
poetry init --no-interaction --python ">=3.12,<3.13"
# then add, under [tool.poetry] in pyproject.toml:  package-mode = false
poetry env use python3.12
poetry add "pandas<3" pyarrow matplotlib pyspark jupyter
java -version                # PySpark 4 requires Java 17 or later
poetry run jupyter notebook

# teammates, after pulling pyproject.toml and poetry.lock
poetry install

Two constraints in these commands deserve an explanation. The Python version is pinned in requires-python because, without an upper bound, Poetry tries to resolve the dependencies for every future Python version and may refuse libraries that do not yet declare support for them. The pandas version is kept below 3 because PySpark 4 does not yet fully support pandas 3, and the Sprint 1 notebook uses both libraries in the same environment. Java is checked because PySpark starts a Java virtual machine, and PySpark 4 requires Java 17 or later. Since Poetry 2, the shell command is no longer part of the default installation, so commands are executed inside the environment through poetry run.

The notebooks are organised so that their structure mirrors the procedure. Each notebook covers one table or one analytical question, and its headings follow the eight steps of section 6. This organisation makes the notebook readable by the reviewer, who can find the evidence for each entry of the data quality log in the step with the same number.

Data outside the repository

Partner extracts must not be committed to a public repository. Keep them in a folder listed in .gitignore, such as data/, and commit only the notebooks, the lock file and the documentation.

6. The procedure in eight steps

Tukey introduced exploratory data analysis as a stage that precedes confirmatory analysis, in which the analyst looks at the data to discover what it can say before testing any hypothesis. In a data platform project the same idea takes a more procedural form. The group explores each table in a fixed order, because the conclusions of one step are premises of the next. Distributions computed before the grain is checked may count duplicated rows, and relationships computed before missing values are measured may reflect gaps in the extract rather than real behaviour.

The procedure below has eight steps. Each one answers a question about the table, computes a small number of measures and produces, when something relevant is found, an entry in the data quality log. The procedure is repeated for each table that supports an analytical question of the canvas.

StepQuestion it answersWhat is computed
1 · Start from the canvasWhich question and which grain does this table serve?A markdown cell with question, grain and invariants
2 · Load and inventoryHow large is the table, with which types, over which period?Shape, types, memory, minimum and maximum dates
3 · Structure and grainDoes the declared key identify each row?Duplicated keys and their inspection
4 · CompletenessWhere are values missing, and following which pattern?Null rates by column and by dimension
5 · Univariate profileHow is each column distributed?Summary statistics, cardinality, IQR outliers
6 · RelationshipsHow do variables move together and over time?Time series, cross-tabs, rank correlation
7 · Consistency across tablesDo joins and invariants hold?Orphan rows and invariant violations
8 · Record and decideWhat enters the log, and which canvas block changes?One log row per finding

The self-study on functional exploratory analysis organises a similar sequence into reusable Python functions. That organisation is worth adopting once the group has applied the steps to the first table, because the same checks will be repeated for every table and every new extract. Its cleaning functions belong to the Silver layer and are not applied during exploration.

7. Steps 1 and 2: from the canvas to the inventory

The first step writes down why the table is being explored. A markdown cell at the top of the notebook records the analytical question from block 2 of the canvas, the grain declared for the table and the invariants that the group expects to hold. This cell has a practical function. It turns the notebook into a test of the canvas, and it allows the reviewer to judge each later cell by asking whether it contributes to the question stated at the top.

Markdown · first cell of the notebook
# Table: stock_position
# Question (block 2): which stores run out most often, and of which products?
# Declared grain: one row per product, store and day
# Invariants: on_hand >= 0; every (store_id, product_id) exists in store and product

The second step loads the table and takes its inventory. Dates are parsed at load time, so that the period covered can be computed from real date values and not from text. The shape gives the number of rows and columns, the types show whether numbers and dates were recognised, and the memory used indicates whether pandas on a single machine is sufficient or whether the analysis must move to Spark. The period covered is decisive, because an indicator computed over two weeks cannot support a decision that depends on seasonality.

pandas · load and inventory
import pandas as pd

sales = pd.read_csv("data/sale_line.csv", parse_dates=["sold_at"])
stock = pd.read_csv("data/stock_position.csv", parse_dates=["date"])

display(sales.shape)
display(sales.dtypes)
display(sales.memory_usage(deep=True).sum() / 1e6)   # megabytes
display(sales["sold_at"].agg(["min", "max"]))               # period covered

Jupyter shows only the value of the last expression of a cell. When a cell computes several results, as the inventory does, each one is wrapped in display, or the cell is split into one expression per cell, otherwise only the period covered would appear. The same convention is used in steps 5 and 7.

A column that should be numeric but appears with type object is the first finding of many analyses. It usually means that some values contain text, such as a decimal comma or a placeholder like "N/A", and the offending values are listed before any conversion is attempted.

8. Steps 3 and 4: grain and completeness

The grain is tested before any distribution is computed, because a duplicated row inflates every count and every sum that follows. The test is simple. The columns that the canvas declares as the key of the table are used to look for repeated combinations, and the repeated rows are displayed side by side. Two situations are common. In the first, the rows are identical, which indicates a duplicated extract or a record sent twice by the source system. In the second, the rows differ in some column, which indicates that the real grain is finer than the declared one, for instance because the stock is counted twice a day.

pandas · test of the declared grain
key = ["store_id", "product_id", "date"]

stock.duplicated(subset=key).sum()                     # rows beyond the first
dups = stock[stock.duplicated(subset=key, keep=False)]
dups.sort_values(key).head(20)                          # inspect side by side

Completeness is measured next. The null rate of each column is the starting point, but a single rate hides the pattern of the missing values, which is what explains them. Missing values concentrated in one store, one supplier or one period usually indicate a failure in the process that produced the data. Missing values spread uniformly are more often a property of the field, such as an optional attribute. The distinction matters, because the first case is reported to the partner and the second may be handled in the transformation layer.

pandas · null rates and their pattern
stock.isna().mean().sort_values(ascending=False)

(stock.groupby("store_id")["on_hand"]
      .apply(lambda s: s.isna().mean())
      .sort_values(ascending=False))

(stock.groupby(stock["date"].dt.to_period("W"))["on_hand"]
      .apply(lambda s: s.isna().mean()))

Missing values are not imputed during the exploration. Filling them with a mean or a zero at this stage would hide the finding from the partner and would introduce, without record, a decision that belongs to the transformation rules.

9. Step 5: the univariate profile

The univariate profile describes each column on its own. For numeric columns it consists of summary statistics, a histogram and a rule for outliers. For categorical columns it consists of the cardinality, that is, the number of distinct values, and the frequency of the most common values. The profile answers practical questions. It shows whether quantities are plausible, whether a category has too many values to be a useful dimension and whether a supposed code is in fact an identifier.

The rule most used for outliers is the one proposed by Tukey, based on the interquartile range. The first and third quartiles delimit the central half of the data, and the interquartile range is their difference. Values below the first quartile minus 1.5 times that range, or above the third quartile plus 1.5 times it, are marked as outliers. The rule is robust, because quartiles are not distorted by the extreme values that the rule seeks to find, which is what happens with the mean and the standard deviation.

pandas · summary, cardinality and IQR outliers
display(sales["quantity"].describe())
display(sales.nunique().sort_values())
display(sales["store_id"].value_counts().head(10))

q1, q3 = sales["quantity"].quantile([0.25, 0.75])
iqr = q3 - q1
low, high = q1 - 1.5 * iqr, q3 + 1.5 * iqr
outliers = sales[(sales.quantity < low) | (sales.quantity > high)]
display(len(outliers) / len(sales))

sales["quantity"].plot.hist(bins=50)

An outlier is a finding, and it is not deleted. A sale of four hundred units in a pharmacy may be a typing error or a legitimate order from a clinic, and only the partner can tell which. The group records the volume of outliers, examples of them and the question to be put to the partner. Sales data is also typically skewed, with many small values and few large ones, so the histogram is often more informative on a logarithmic scale.

10. Step 6: relationships between variables

Relationships are examined in three forms, each of which answers a different part of the analytical question. Relationships over time reveal seasonality, changes of level and gaps in the extract. Relationships between categories show how a measure varies across stores, products or regions. Relationships between numeric measures show which quantities move together. A chart produced in this step is kept in the notebook only if it supports a sentence in the data quality log or in the canvas, which prevents the notebook from becoming a gallery without conclusions.

pandas · time, categories and measures
# Over time: daily totals, which expose gaps and seasonality
daily = sales.groupby(sales.sold_at.dt.date)["quantity"].sum()
daily.plot()

# Between categories: share of stock-out days per store (first draft of the KPI)
obs = (stock.dropna(subset=["on_hand"])
            .drop_duplicates(["store_id", "product_id", "date"], keep="last"))
obs["on_hand"].le(0).groupby(obs["store_id"]).mean()

# Between measures: rank correlation on the measures only, never on identifiers
daily_sp = (sales.assign(date=sales["sold_at"].dt.normalize())
                 .groupby(["store_id", "product_id", "date"], as_index=False)["quantity"].sum()
                 .merge(obs, on=["store_id", "product_id", "date"]))
daily_sp[["quantity", "on_hand"]].corr(method="spearman")

The share of stock-out days by store deserves attention, because it is the first computation of the indicator defined in block 4 of the canvas. Rows without a stock count are removed and repeated counts keep the last record, so that days without a record leave the denominator and duplicates do not count twice, while a negative stock counts as a stock-out. The full KPI of Lesson 1 also keeps only continuous-use products and groups by week and product, as in its SQL query. If the share of stock-out days is close to zero in every store, the indicator may be poorly defined or the extract may not record stock-outs at all. Either conclusion changes the canvas before the pipeline is built around an indicator that the data cannot support.

Spearman correlation is preferred to Pearson correlation in this step because it uses the ranks of the values and not the values themselves. It therefore tolerates skewed distributions and outliers, which are common in sales and stock data. The measures are selected by name, because a matrix computed over every numeric column would correlate identifiers such as store_id, whose numbers carry no quantity. A correlation is a description and does not establish a cause, so it is recorded as a hypothesis to be discussed with the partner.

11. Step 7: consistency across tables

The relationships and invariants of the information viewpoint involve more than one table, and they are tested in this step. A relationship is tested with a join that marks the rows without a match. The share of unmatched rows decides whether the join can be used as it is, or whether the Silver layer must treat those rows before any indicator is built on the joined data. Measuring this share before using the join is essential, because an inner join silently discards unmatched rows and every indicator computed afterwards inherits the loss.

pandas · orphan rows and invariant violations
products = pd.read_csv("data/product.csv")

m = sales.merge(products, on="product_id", how="left", indicator=True)
display((m["_merge"] == "left_only").mean())          # share of orphan sale lines

display((stock["on_hand"] < 0).sum())                       # invariant on_hand >= 0
display((sales["quantity"] <= 0).sum())                    # returns or errors?
display((sales["sold_at"] > pd.Timestamp.now()).sum())       # dates in the future

Each invariant of the canvas becomes one line of code that counts violations. The log records the number of violations, because the decision depends on their volume. Three negative stock positions in two million rows may be handled by a rule in the Silver layer, whereas thousands of them indicate that the field has a meaning different from the one the group assumed.

The dynamic schema is checked in the same step when the dataset contains objects with a life cycle. For purchase orders, the group checks whether the statuses follow the expected order and whether the dates of each transition are consistent, for instance whether no order is received before it is approved.

13. From pandas to PySpark

The Sprint 1 deliverable asks for the analysis in a Jupyter Notebook with Apache Spark. Pandas is convenient for the first exploration, because it is fast to write and the sample fits in memory, but Spark is the engine that the platform will use when the data grows. The procedure does not change between the two. Each check has a direct equivalent in the DataFrame API of PySpark, and the notebook of the deliverable can follow the same eight headings.

PySpark · inventory, grain, completeness, profile and orphans
from pyspark.sql import SparkSession, functions as F

spark = SparkSession.builder.appName("eda").getOrCreate()
sales = spark.read.csv("data/sale_line.csv", header=True, inferSchema=True)
stock = spark.read.csv("data/stock_position.csv", header=True, inferSchema=True)
products = spark.read.csv("data/product.csv", header=True, inferSchema=True)

sales.count(); sales.printSchema()                                    # step 2
stock.groupBy("store_id", "product_id", "date").count().filter("count > 1").show()  # step 3
stock.select([F.avg(F.col(c).isNull().cast("int")).alias(c)
              for c in stock.columns]).show()                                 # step 4
sales.approxQuantile("quantity", [0.25, 0.75], 0.01)                     # step 5
sales.join(products, "product_id", "left_anti").count()                  # step 7

Two differences deserve attention. Spark computes quantiles approximately on large data, with a relative error that the analyst chooses, so the IQR fences may differ slightly from those of pandas. Spark also evaluates operations lazily, which means that nothing is computed until an action such as count or show is called, and an error in an early transformation may only appear at the action.

14. The Data Lake: zones, buckets and naming

A Data Lake stores data in its original or lightly processed form in an object store, which can be MinIO running in Docker during development or a bucket in a cloud provider. The value of the lake depends on its organisation. Without a convention, files accumulate under arbitrary names, and after a few weeks nobody can tell which extract is current, which system produced a file or whether two files contain the same data.

The initial structure of this lesson separates three zones. The landing zone receives files exactly as delivered, which preserves the evidence of what the partner sent. The raw zone holds the sample of each extract in Parquet, partitioned by ingestion date. The sandbox zone holds samples and intermediate files of the analysis, which may be deleted without loss. Lesson 3 reorganises these zones into the Bronze, Silver and Gold layers of the medallion architecture, and the form of the raw zone, whether an exact copy of the extract or a typed copy, is one of the decisions revisited there.

Convention · buckets and paths
<project>-landing/                         # files exactly as received
  pos/sale_line/2026-10-19/sale_line.csv

<project>-raw/                             # sample in Parquet
  <source>/<entity>/ingestion_date=YYYY-MM-DD/
  pos/sale_line/ingestion_date=2026-10-19/part-0.parquet
  erp/stock_position/ingestion_date=2026-10-19/part-0.parquet

<project>-sandbox/                         # samples and notebook outputs

Each part of the path carries information. The source names the system of origin, the entity names the information object of the canvas, and the ingestion date records when the data entered the platform. The form key=value is recognised as a partition by pandas, Spark and most query engines, which can then read only the dates that a query needs. The lineage of any file can therefore be read from its location, which anticipates the lineage field of the canvas.

15. Storing the sample in Parquet

Apache Parquet is a columnar file format. Instead of storing each row contiguously, as CSV does, it stores the values of each column together, along with the schema of the data and statistics for each block of values. Four consequences follow. A query that needs two columns of a wide table reads only those two columns. Dates and numbers keep their types, while in CSV every value is text that must be parsed again. Values of the same column, being similar, compress well. Finally, the statistics of each block allow readers to skip blocks that cannot satisfy a filter, which is called predicate pushdown.

pandas + pyarrow · write partitioned Parquet and read it back
sales["ingestion_date"] = "2026-10-19"

sales.to_parquet("lake/raw/pos/sale_line",   # local stand-in for the <project>-raw bucket
                 engine="pyarrow",
                 partition_cols=["ingestion_date"],
                 index=False,
                 existing_data_behavior="delete_matching",
                 basename_template="part-{i}.parquet")

back = pd.read_parquet("lake/raw/pos/sale_line")
display(back.dtypes)                     # compare with the inventory of step 2
len(back) == len(sales)                  # no rows lost

The two last arguments make the write idempotent. With existing_data_behavior="delete_matching", the partition of the day is replaced instead of receiving a new file, and basename_template gives the files a fixed name, so a notebook executed twice leaves the same rows in the lake instead of duplicating them and inflating every count read from it.

Reading the file back verifies the conversion. The types of the columns are compared with those recorded in the inventory of step 2, and the number of rows is compared with the original. A difference indicates a conversion problem, such as a date column stored as text, which is easier to correct now than after the Bronze layer depends on it. When the partition column is read back, pandas returns it as a categorical column, which is expected and does not indicate an error.

In Spark the same operation uses df.write.mode("overwrite").partitionBy("ingestion_date").parquet(path) with the setting spark.sql.sources.partitionOverwriteMode equal to dynamic, which replaces only the partitions present in the data and keeps the others. The resulting folder can be read by either library. This interoperability is one reason why Parquet is the common format of the module.

16. The group practice of the session

The session reserves 45 minutes for each group to complete Steps 3 to 8 of the procedure. The group first runs the cells on the synthetic data of the starter notebook, where the defects are known, and then applies the same cells to one table of the partner dataset that supports an analytical question of block 2 of the canvas. A table chosen without a question would turn the practice into the inventory that Lesson 1 warned against, and the synthetic run ensures that the code works before it meets the partner data.

The practice has three products. In the notebook, the group tests the grain, measures completeness, profiles the columns, examines the relationships and checks the consistency across tables, as in sections 8 to 11. In the repository, the group records one row of the data quality log for each finding, with its volume, its probable cause, the decision taken and the canvas block it affects, using the template of section 12. In the Data Lake, the group writes the explored table as partitioned Parquet with the idempotent code of section 15 and reads it back to compare types and row counts.

The results of the practice are the material of the presentations that follow it, described in section 17. The steps that the group does not finish in class are completed before the Sprint Review on Friday, when the canvas and the analysis in Spark are delivered.

17. Presenting your results

The session closes with a presentation by each group of what it achieved on the partner data. The presentation is short, about four minutes per group followed by questions, and its purpose is to expose the findings to the class while they can still change the canvas, and before the Sprint Review on Friday. Presenting also forces the group to select, from everything the notebook computed, the findings that matter for the partner, which is the same selection that the data quality log requires.

Each presentation covers the same elements, so that the class can compare the groups. The group shows three findings with their volume, one invariant violation with its probable cause, the canvas block that each finding changes, the Parquet sample written to the raw zone with its path and row count, and the next step planned for the Friday deliverable. The figures are read from the notebook and the log, and not reconstructed from memory.

After each presentation, the class asks one question to the group. A useful question asks for the evidence behind a finding, for the decision attached to it or for the reason why a defect was attributed to one cause and not another. The professor uses the presentations to point out findings that recur across groups, which often indicate a property of the partner extract that should be confirmed with the partner.

18. Recurring mistakes

The most frequent mistake is to start the notebook with charts. Charts produced before the grain and the completeness are known may show duplicated data or gaps in the extract as if they were behaviour of the business, and the conclusions drawn from them must later be withdrawn. The order of the procedure exists to prevent this.

The second mistake is to correct the data during the exploration. Removing outliers, filling missing values or dropping orphan rows in the notebook hides the findings from the partner and introduces decisions that nobody recorded. The exploration measures and records, and the corrections are written later as rules of the Silver layer, where they can be reviewed and tested.

The third mistake is to keep the findings only in the notebook. A notebook is read from top to bottom and its outputs change at each execution, so it is a poor place for decisions. The data quality log, linked to the canvas, is where the findings become durable. The fourth mistake, finally, is to store the sample without a convention, under names such as final_v2.csv. The convention of section 14 costs a few minutes today and saves the reconstruction of lineage in later sprints.
