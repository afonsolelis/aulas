2. Two readers of the same DataApp

A DataApp has two kinds of reader, and each needs a different kind of figure. The person who maintains it, in the group or at the partner, needs to know what runs, in which order, from which object to which, how large the model is and whether the last run worked; the figure for this reader is a technical infographic, which describes the system. The person who uses it needs the answer to a question about the business, such as which cards are worth the most or how the value of a set evolved; the figure for this reader is an analytical view, which describes the data.

The app of this lesson has one tab for the first reader and two for the second. Both kinds of figure obey the same rule: every number shown comes from the warehouse at the moment the page is opened, and none is typed by hand. A diagram drawn in a presentation tool describes the DataApp on the day it was drawn; a diagram generated from the catalogue and from the run log describes the DataApp that ran, and changes when the code changes.

3. The question chooses the chart

A chart is selected by the job that the data must do in the answer, not by the variety of forms that a library offers. Comparing magnitudes, showing a change over time, showing the share of a whole, descending a hierarchy and stating one number are different jobs, and each has a form that the eye reads with the least effort and the least error. The table below applies this rule to the questions of the DataApp.

Job of the dataQuestion in the DataAppFormAvoid
compare magnitudeswhich sets hold the most expensive cards?horizontal bars, ranked, from zeropie with seven slices; bars that start above zero
change over timehow did the value of a set evolve?line with one series highlightedseven coloured lines and a legend
part of a wholewhat share of the market is one set?one sentence, or a single stacked bardonut with labels outside it
hierarchyinside a set, which rarity, and inside it which card?bars with drill-down and roll-upa treemap read by colour
one numberhow many prices does the fact hold?the number and its labela gauge
how the system workswhat runs, in which order, from where to where?graph of tasks; graph of lineagea diagram drawn by hand

Horizontal bars are preferred for rankings because the names of sets, rarities and cards are long and fit on the left, where they are read in the same order as the bars. A pie is avoided because the comparison of angles is less precise than the comparison of lengths, and the precision drops further when the slices are many and similar.

4. What the eye reads first

Cleveland and McGill (1984) measured how precisely people compare quantities encoded in different ways, and found an order that still guides the design of charts: position on a common scale is read most precisely, followed by length, then angle and slope, then area, and colour last. A chart therefore places the quantity that carries the message in position or length, and reserves colour for pointing at what matters.

Three practices follow from this order and are applied throughout the app. The first is highlight and context: the series that carries the message is drawn in the accent colour of the palette, #2f8f78, and every other series stays grey, as context, so seven sets never require seven colours that a reader with colour blindness could not separate. The second is direct labelling: the value is written at the end of each bar and the name at the end of the highlighted line, which removes the legend and the travel of the eye between the legend and the mark. The third is a recessive frame: the grid and the axes are pale, because they help to read the marks and should not compete with them, in the sense in which Tufte (1983) asks for the ink of a chart to be spent on data.

The same principles explain what the app never does. A chart with two y axes lets the author choose the scales so that two series cross where it is convenient; a bar axis that does not start at zero exaggerates differences; a rainbow palette suggests an order that does not exist; 3D adds area and angle where only length was needed. Each of these choices changes the conclusion that a reader draws from the same data, which is the subject of section 16.

Part IIThe queries

5. A view layer that can be tested

The first step writes no chart. The queries of the app live in views/dashboard.py, a module of pure functions that receives a DuckDB connection and returns rows, without importing Streamlit. The separation has the same justification as the layers of Lesson 7: the queries can be tested alone, over the fake warehouse of the tests, in a fraction of a second, and the app is left with the drawing, which is harder to test and changes more often.

The connection of the app is opened with read_only=True. The view layer reads gold, the marts, the reports and the run log, and it is not able to change them: a DROP VIEW sent through this connection fails, and a test proves it. The explorer receives from the app the dimensions, the measure and the values chosen by the user, and the module accepts only dimensions and measures from fixed lists and passes every value as a parameter of the query, so that a set called x' OR '1'='1 returns no rows instead of every row.

views/dashboard.py · explore
def explore(con, source: str, dims: list[str], measure: str, filters: dict | None = None,
            suffix: str | None = None, limit: int = 15) -> dict:
    """Ranked groups of the explorer, with the SQL that produced them.

    The dimensions and the measure come from fixed lists and the filter values
    are parameters, so a value chosen in the app never becomes SQL.
    """
    if source not in SOURCES:
        raise ValueError(f"unknown source {source!r}")
    if measure not in MEASURES:
        raise ValueError(f"unknown measure {measure!r}")
    filters = filters or {}
    for d in list(dims) + list(filters):
        if d not in DIMENSIONS:
            raise ValueError(f"unknown dimension {d!r}")
    if source == "frozen" and not re.fullmatch(r"\d{4}_\d{2}", suffix or ""):
        raise ValueError("a frozen source needs a suffix YYYY_MM")
    table = SOURCES[source].format(suffix=suffix)
    label, expression = MEASURES[measure]
    group = ", ".join(dims)
    where = " AND ".join(f"{d} = ?" for d in filters) or "true"
    select = f"{group}, " if dims else ""
    sql = (f"SELECT {select}{expression} AS value\nFROM {table}\nWHERE market_price IS NOT NULL AND {where}\n"
           + (f"GROUP BY {group}\n" if dims else "") + f"ORDER BY value DESC\nLIMIT {int(limit)}")
    rows = _rows(con, sql, list(filters.values()))
    captured_at = con.execute(f"SELECT max(captured_at) FROM {table}").fetchall()[0][0]
    return {"sql": sql, "params": list(filters.values()), "rows": rows, "label": label,
            "captured_at": captured_at, "table": table}

6. The infographic is drawn from metadata

The technical infographic draws two graphs, and both are generated from information that the warehouse already holds or that the pipeline records. The lineage of the warehouse comes from the catalogue of DuckDB: duckdb_views() returns the SQL of every view, and searching it for the names of the other objects gives the edges, so that gold.fact_price is found to read db_ingestion, gold.dim_set and gold.dim_product. A table created by CREATE TABLE AS, however, keeps only its columns and forgets the query that created it. For the frozen reports, freeze_month now writes the source in the comment of the table, which duckdb_tables() returns.

The graph of the pipeline comes from the run log. Drawing it by importing pipeline.py would make the view layer depend on the module that sits above all layers, which inverts the direction that Lesson 7 established. The runner therefore records the graph of each run in a new table, ops.pipeline_tasks, next to ops.pipeline_runs, and the app reads both. On the warehouse of the rehearsal the lineage has 13 objects and 20 edges, and the graph of the last run has 12 tasks.

processors/gold.py · the comment of a frozen table
run(con, f"COMMENT ON TABLE report.{name} IS 'frozen from {source}, last capture of {month}'")
views/dashboard.py · lineage
def lineage(con) -> dict:
    """Objects of the warehouse, their rows and the objects each one reads.

    The edges of a view come from its own SQL in the catalogue (duckdb_views); a
    frozen table keeps its source in a comment, written by freeze_month.
    """
    views = _rows(con, "SELECT schema_name, view_name AS name, sql FROM duckdb_views() "
                       "WHERE schema_name IN ('gold', 'mart_collectors', 'report')")
    tables = _rows(con, "SELECT schema_name, table_name AS name, comment FROM duckdb_tables() "
                        "WHERE schema_name IN ('main', 'report') ORDER BY schema_name, table_name")
    names = ["db_ingestion"] + [f"{v['schema_name']}.{v['name']}" for v in views] + \
            [f"{t['schema_name']}.{t['name']}" for t in tables if t["schema_name"] == "report"]
    edges = []
    for v in views:
        target = f"{v['schema_name']}.{v['name']}"
        for source in names:
            if source != target and re.search(rf"(?<![\w.]){re.escape(source)}(?!\w)", v["sql"]):
                edges.append((source, target))
    for t in tables:
        match = re.search(r"frozen from ([\w.]+)", t["comment"] or "")
        if match:
            edges.append((match.group(1), f"{t['schema_name']}.{t['name']}"))
    nodes = []
    for name in names:
        rows = con.execute(f"SELECT count(*) FROM {name}").fetchall()[0][0]
        kind = "table" if name == "db_ingestion" or name.startswith("report.mv_") else "view"
        layer = "etls" if name == "db_ingestion" else ("views" if name.startswith("report.") else "processors")
        nodes.append({"name": name, "rows": rows, "kind": kind, "layer": layer})
    return {"nodes": nodes, "edges": sorted(set(edges))}
Part IIIStreamlit and the infographic

7. The execution model of Streamlit

A Streamlit app is a Python script that runs from top to bottom each time the user changes a widget. The model is simple to write, because the page is a sequence of calls such as st.metric and st.altair_chart, and it has two consequences that shape the code. What must survive between runs, such as the path of a drill-down, is kept in st.session_state; and what is expensive to create, such as the connection to the warehouse, is created once with st.cache_resource and reused by every run and every user.

PieceIn tcg-dataappWhy

st.tabsinfographic, ranking, prices over timeone question per tab

The app is started by a new command of the package, tcg-dataapp app, which runs python -m streamlit run on the file views/app.py of the installed package. Streamlit and Altair are an optional extra (pip install -e '.[app]'), so the pipeline still installs and runs on a machine that never shows the app, such as the server that runs it every day.

8. The theme of the design system

The theme of a Streamlit app is configuration, not code. The file .streamlit/config.toml, read from the folder where the app is started, sets the colours, the fonts and the radius of every component, and the reference package applies the palette and the typography of the Inteli design system: the accent #2f8f78, the ink #2e2640 for text, the greys #e6eaeb and #caced6 for backgrounds and borders, Inter for text and JetBrains Mono for code. The same colours are repeated as constants at the top of views/app.py, because the marks of Altair are drawn by the code of the app and not by the theme.

The status of a task is written as text (ok, FAILED, skipped) and the border of the box only repeats it. The seconds come from Unix times recorded in whole seconds, so a task that took less than one second is written as < 1 s.

views/app.py · the graph of the pipeline
def dot_pipeline(tasks: list[dict]) -> str:
    """The DAG of the last run, with the status written in each node and not only coloured."""
    lines = ['digraph { rankdir=LR; bgcolor="transparent";',
             f'node [shape=box, style="rounded,filled", fillcolor="white", color="{CONTEXT}", '
             f'fontname="Inter", fontsize=11, fontcolor="{INK}"]; edge [color="{TEXT}", arrowsize=0.6];']
    for t in tasks:
        mark = {"success": "ok", "failed": "FAILED", "skipped": "skipped"}.get(t["status"], t["status"] or "-")
        border = ACCENT if t["status"] == "success" else INK
        lines.append(f'"{t["task"]}" [label="{t["task"]}\\n{mark} · {seconds(t["seconds"])}", color="{border}", penwidth=1.4];')
        for d in t["depends_on"]:
            lines.append(f'"{d}" -> "{t["task"]}";')
    return "\n".join(lines + ["}"])
Part IVRanking and drill-down

10. The explorer of Lesson 6 in the app

The second tab repeats, in Streamlit, the explorer of the lab of Lesson 6. The user chooses the source (the report frozen in September or the live view of the last capture), the measure (highest price, average price, market value or number of prices) and the dimensions of the grouping (set, rarity, card and variant), and the app draws the groups as horizontal bars ranked from the largest value, with the value written at the end of each bar. A click on a bar keeps its values as filters and descends one level of the hierarchy set › rarity › card; a row of buttons rolls back up.

Every view that does not use the card is checked against the cube of Lesson 6. A grouping rolls up the dimensions that it does not use, and grouping(set_name, rarity, variant) encodes them as bits worth 4, 2 and 1; grouping by set therefore reads the cells with grouping_id 2 + 1 = 3, and grouping by set and rarity, the cells with grouping_id 1. The app reports in one sentence whether the bars agree with those cells, and shows the SQL of the view with its parameters.

views/dashboard.py · cube_check
def cube_check(con, result: dict, dims: list[str], measure: str, filters: dict | None = None) -> dict | None:
    """Reads the same groups from gold.agg_price_cube and says whether they agree.

    The cube has no card, so the check exists only when neither the grouping
    nor the filters use it.
    """
    filters = filters or {}
    used = set(dims) | set(filters)
    if "card" in used:
        return None
    grouping_id = sum(bit for d, bit in CUBE_BITS.items() if d not in used)
    where = " AND ".join([f"{d} = ?" for d in filters] + ["grouping_id = ?", "date_unix = ?"])
    cube = _rows(con, f"SELECT {', '.join(dims) + ', ' if dims else ''}{CUBE_MEASURES[measure]} AS value "
                      f"FROM gold.agg_price_cube WHERE {where}",
                 list(filters.values()) + [grouping_id, result["captured_at"]])
    key = lambda r: tuple(r[d] for d in dims)  # noqa: E731
    cube_by_key = {key(r): round(float(r["value"]), 2) for r in cube}
    agree = all(abs(cube_by_key.get(key(r), float("nan")) - round(float(r["value"]), 2)) < 0.01
                for r in result["rows"])
    return {"grouping_id": grouping_id, "cells": len(cube), "agree": agree}

11. A click that changes the state of the app

Since version 1.35, st.altair_chart returns the selection of the user when it is called with on_select="rerun" and the chart declares a selection parameter. The click arrives, however, in the run in which the checkboxes of the grouping were already drawn, and Streamlit does not allow the state of a widget to change after the widget exists in the run. The app therefore stores the click as a pending change, calls st.rerun(), and applies the change at the top of the tab, before the widgets are created.

A second detail prevents a loop. The chart of the new level would start with the selection of the previous one, which would fire the drill-down again; the key of the chart includes the depth of the path, so each level is a new chart without a selection.

Part VTime, accessibility and ethics

13. Time zones and Unix time

The warehouse keeps every date as Unix time in UTC, as decided in Lesson 6, and the app converts it to a calendar day only when it draws it. The conversion must also be done in UTC. A browser formats a date in the time zone of the computer unless the chart says otherwise, and in São Paulo, three hours behind UTC, the capture at 00:00 UTC of 01/09/2026 would be drawn at 21:00 of 31/08/2026, in the wrong month. The app converts with pd.to_datetime(unit="s", utc=True), declares the scale of the axis as utc and shows the Unix time in the tooltip.

14. Storytelling: the sentence before the chart

Knaflic (2015) proposes that a chart for communication starts from the sentence it must support, and not from the data available. The app opens with one sentence built from the warehouse: on 07/11/2026 the most valuable card is Mew - R/RGB, of ME: 30th Celebration, in Holofoil, at US$ 4,492.45, and that set holds 65.3% of the market value of the seven sets. Each view repeats the practice in smaller scale, with a caption that states the conclusion of the chart, such as the first and the last value of the highlighted series.

The tab of prices over time applies highlight and context. By default it highlights the series with the largest value, which on the warehouse of the rehearsal is ME: 30th Celebration, whose market value went from US$ 1,349.93 on 01/09/2026 to US$ 12,403.41 on 07/11/2026; the other six sets remain as thin grey lines. The user can highlight another series, or switch to the five most valuable cards of one set, where the same rule applies.

16. Ethics of the chart

A chart can be accurate in every number and still lead to a wrong conclusion, through the choice of the scale, of the period or of what is compared (Cairo, 2019). The app adopts five rules. Every bar starts at zero, so the length of a bar is proportional to its value. The source and the date of the capture are written under each chart. Every capture of the warehouse is drawn, and no period is cut to make a trend look stronger. The check with the cube and the SQL of each view are visible, so a reader can verify how the number was obtained.

The fifth rule concerns interpretation. ME: 30th Celebration was released on 16/09/2026, and its first capture, on 01/09/2026, holds prices from before the release; the jump of its market value to 07/11/2026 reflects the launch and the arrival of its cards in the market, not the appreciation of the same cards. The sentence of a view must say what the data supports, and the comparison of appreciation in Lesson 6 required at least two captures of the same card for this reason.

   - task_graph(con): the tasks of the last run with their dependencies,
     final status, attempts and seconds.
   - lineage(con): every object of db_ingestion, gold, mart_collectors and
     report, its rows, its kind (table or view) and its layer, and the
     edges source -> target found in the SQL of each view (duckdb_views()).
   - explore(con, source, dims, measure, filters, suffix): ranked groups
     of the frozen report report.mv_card_price_<suffix> or of the live view
     report.v_card_price_latest, returning the rows and the SQL.
   - cube_check(con, result, dims, measure, filters): the same groups read
     from gold.agg_price_cube at the right grouping_id, and whether they
     agree; None when the card is used, because the cube has no card.
   - price_history(con, level, highlight): market value of each set on
     every capture, or the five most valuable cards of one set.
2. Two small changes below the views, so the app can draw from metadata:
   - pipeline.py keeps the graph of each run in ops.pipeline_tasks
     (run_id, task, depends_on VARCHAR[]);
   - freeze_month writes COMMENT ON TABLE report.mv_... IS 'frozen from
     <source>, last capture of <month>', because a table does not remember
     the query that created it.
3. tests/test_dashboard.py over the FakeClient of conftest.py.

21. Mistakes found in the rehearsal

The problems below appeared while the app was rehearsed on 08/11/2026, and the reference package and the prompts already carry the corrections.

Labels that disappear

The first version of the ranking passed the height only to the Altair chart, and Streamlit drew it with its default height; the bars became thin and Vega omitted every other label of the axis to avoid overlap, so two sets had no name. The height is now passed to st.altair_chart as well, proportional to the number of groups, with theme=None so that the configuration of the app is not replaced by the theme of Streamlit.

Deprecated parameters

Streamlit 1.67 warns that use_container_width will be removed, and agents trained on older code still write it. The app uses width="stretch".

Decimal values

DuckDB returns DECIMAL columns as Python Decimal, which Altair does not treat as numbers. The app converts them to float when it builds the data frame, and the module of queries keeps the exact values.

The direction of the layers

Asked to draw the DAG, an agent imports pipeline.build_tasks into the view layer, which makes the views depend on the module that sits above all layers. The graph of the run is recorded in ops.pipeline_tasks instead, and the views read the warehouse only.

24. Checklist

  • The queries of the app live in a module without Streamlit, and are tested.
  • The connection of the app is read-only.
  • Dimensions and measures come from fixed lists; values are parameters.
  • The infographic is generated from the catalogue and the run log.
  • Each view opens with a sentence that states its conclusion.
  • One y axis, one accent colour, bars from zero.
  • Every figure has an alternative text and a table view.
  • Dates are converted from Unix time in UTC only when drawn.
  • The drill-down agrees with the cube.
  • The app runs in an AppTest.
