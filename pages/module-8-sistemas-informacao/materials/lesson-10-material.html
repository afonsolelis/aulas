2. Why a DataApp needs metrics

The package of Lesson 7 records every attempt of every task in ops.pipeline_runs, which explains a run once someone decides to look at it. A DataApp that runs every day at six in the morning, however, fails at a moment when nobody is looking, and the failure that matters most is often the one that leaves no record: a scheduler that stopped calling the run, or a source that answers but has not published new prices. Metrics address this gap because they are numbers kept over time and evaluated by a machine, so the question of whether the data is right is asked every fifteen seconds, and a person is called only when the answer is no.

3. Metrics, logs and traces

Telemetry is the data that a system emits about its own behaviour, and it is usually divided into three signals. Logs are records of events, each with its context, and the run log of Lesson 7 is one of them. Traces follow one request through the components that served it, and are most useful in systems of many services. Metrics are numeric measurements aggregated over time, cheap to store and to evaluate, which makes them the signal on which alerts are built. OpenTelemetry, the subject of the third self-study, standardises the three signals; Prometheus specialises in metrics and defines the format that most tools read.

A DataApp has, besides the health of its processes, the health of its data, which the literature on data observability describes in five dimensions. This session measures three of them directly and leaves two for the next lessons.

Part IIPrometheus

4. Targets, scrapes and time series

Prometheus collects by pulling. Every scrape_interval, fifteen seconds in this lab, it sends an HTTP request to the endpoint /metrics of each target and stores each line of the answer as a sample of a time series. A series is identified by a metric name and a set of labels, and a sample is a value with a timestamp. The same name with a different value of a label is another series, which is what makes the model dimensional: tcg_task_rows{task="extract_sets"} and tcg_task_rows{task="extract_products"} are two series of the same metric.

Pulling has a property that pushing lacks. Because Prometheus initiates the scrape, it knows when a target did not answer, and it records that in the series up, which is 1 when the last scrape worked and 0 otherwise. A target that dies therefore produces a signal, whereas a process that pushes and dies simply stops sending, which looks the same as a process that has nothing to say.

5. Metric types

The type of a metric declares how its value may change, and therefore which operations make sense over it. A counter only grows and returns to zero when the process restarts, so its absolute value means little and it is read through its rate of growth with rate() or increase(). A gauge can go up and down and is read as it is. A histogram counts observations in cumulative buckets and also keeps their sum and their number, so that means and quantiles can be computed in the server. A summary computes quantiles in the process itself, which is precise for that process but cannot be combined across instances, because quantiles are not additive; for this reason the package uses histograms.

Gaugeany value, up or downtcg_task_rows, tcg_run_success, the timestamps, everything the exporter reads

6. Names, labels and cardinality

The conventions of Prometheus make a metric readable without its documentation. The name starts with a prefix of the application, tcg_, so that it does not collide with metrics of other systems; it ends with the unit in base units, _seconds and never milliseconds; and the name of a counter ends in _total. Timestamps are gauges in Unix seconds whose names end in _timestamp_seconds, so that time() - metric gives an age in seconds.

Labels are where a design usually fails. Each distinct combination of label values creates a series that Prometheus indexes and keeps in memory, so the number of series, the cardinality, is the product of the number of values of each label. The four labels of the package (task, status, endpoint and measure) have at most a dozen values each. A label with the identifier of the run would create a new series at every run, and a label with the product would create one series per card, 1,490 of them for one metric; both are kept out of the metrics and stay in the run log and in the gold layer, which are the right places for them.

Part IIIMetrics of the run

7. The telemetry module

The first step adds one module to the package and leaves the three layers as they were. telemetry.py owns every metric, in a registry of its own instead of the global registry of the library, so that the tests can create as many runs as they need without the metrics of one leaking into the next. RunMetrics holds the metrics of one run; InstrumentedClient wraps the client of tcgcsv.com and times each call; WarehouseCollector, described in Part IV, reads the warehouse at each scrape.

src/tcg_dataapp/telemetry.py
"""Metrics of the DataApp in the Prometheus format.

Two ways of reaching Prometheus, because the DataApp has two kinds of process:

    RunMetrics   the batch run (tcg-dataapp run) lives for about forty seconds,
                 shorter than the scrape interval, so it records its metrics while
                 it runs and pushes them to a Pushgateway at the end; it also writes
                 them to out/metrics.prom, in the text format.
    WarehouseCollector
                 the exporter (tcg-dataapp metrics) is a long-running process that
                 Prometheus scrapes; at every scrape it reads the state of the
                 warehouse (freshness, volume, grain, last run) from the DuckDB file.

Every timestamp is Unix time in seconds, which is also what Prometheus uses.
Every metric lives in a registry of its own, never in the global one, so the
tests can create as many as they need.
"""
from __future__ import annotations

import time
from pathlib import Path

import duckdb
from prometheus_client import CollectorRegistry, Counter, Gauge, Histogram, disable_created_metrics, generate_latest
from prometheus_client.exposition import pushadd_to_gateway
from prometheus_client.core import GaugeMetricFamily

# The *_created series (when each counter started) only add noise to a job that lives forty seconds.
disable_created_metrics()

JOB = "tcg_dataapp"
SOURCE_BUCKETS = (0.1, 0.25, 0.5, 1, 2, 4, 8, 16)


class RunMetrics:
    """The metrics of one run of the pipeline."""

    def __init__(self, run_id: str):
        self.run_id = run_id
        self.registry = CollectorRegistry()
        r = self.registry
        self.task_attempts = Counter("tcg_task_attempts", "Attempts of each task in this run, by outcome",
                                     ["task", "status"], registry=r)
        self.task_duration = Gauge("tcg_task_duration_seconds", "Duration of the last attempt of each task",
                                   ["task"], registry=r)
        self.task_rows = Gauge("tcg_task_rows", "Rows written to db_ingestion by each extraction task", ["task"], registry=r)
        self.source_latency = Histogram("tcg_source_request_duration_seconds",
                                        "Duration of the requests to tcgcsv.com, by kind of request",
                                        ["endpoint"], buckets=SOURCE_BUCKETS, registry=r)
        self.source_errors = Counter("tcg_source_request_errors", "Requests to tcgcsv.com that raised an error",
                                     ["endpoint"], registry=r)
        self.quality = Gauge("tcg_quality_value", "Numbers measured by check_quality", ["measure"], registry=r)
        self.run_success = Gauge("tcg_run_success", "1 when every task of the run succeeded, 0 otherwise", registry=r)
        self.run_duration = Gauge("tcg_run_duration_seconds", "Duration of the whole run", registry=r)
        self.run_failed_tasks = Gauge("tcg_run_failed_tasks", "Tasks that failed or were skipped in the run", registry=r)
        self.run_completion = Gauge("tcg_run_last_completion_timestamp_seconds",
                                    "Unix time at which the last run ended, successful or not", registry=r)
        # Pushed only after a successful run, so a failure does not erase it.
        self.success_registry = CollectorRegistry()
        self.run_last_success = Gauge("tcg_run_last_success_timestamp_seconds",
                                      "Unix time at which the last successful run ended",
                                      registry=self.success_registry)
        self.succeeded = False
        self._started = time.perf_counter()

    # hooks called by the pipeline
    def attempt(self, task: str, status: str, seconds: float | None = None, result: object = None) -> None:
        self.task_attempts.labels(task=task, status=status).inc()
        if seconds is not None:
            self.task_duration.labels(task=task).set(seconds)
        if status == "success" and task.startswith("extract_") and isinstance(result, int):
            self.task_rows.labels(task=task).set(result)
        if status == "success" and task == "check_quality" and isinstance(result, dict):
            for measure in ("fact_rows", "fact_grain_keys", "fact_without_set", "dates", "cube_cells"):
                if measure in result:
                    self.quality.labels(measure=measure).set(result[measure])

    def finish(self, failed: list[str]) -> None:
        now = time.time()
        self.run_duration.set(time.perf_counter() - self._started)
        self.run_failed_tasks.set(len(failed))
        self.run_success.set(0 if failed else 1)
        self.run_completion.set(now)
        self.succeeded = not failed
        if self.succeeded:
            self.run_last_success.set(now)

    # the client of the source, wrapped so that every request is measured
    def instrument(self, client):
        return InstrumentedClient(client, self)

    # exposition
    def text(self) -> str:
        body = generate_latest(self.registry)
        if self.succeeded:
            body += generate_latest(self.success_registry)
        return body.decode()

    def write(self, path: Path) -> Path:
        path.parent.mkdir(parents=True, exist_ok=True)
        path.write_text(self.text(), encoding="utf-8")
        return path

    def push(self, gateway: str, instance: str = "local") -> None:
        """Push to a Pushgateway, in the group job=tcg_dataapp, instance=<instance>.

        pushadd (HTTP POST) replaces only the metrics with the names being pushed, so
        tcg_run_last_success_timestamp_seconds, pushed only after a success, keeps
        the time of the last good run when a run fails.
        """
        key = {"instance": instance}
        pushadd_to_gateway(gateway, job=JOB, registry=self.registry, grouping_key=key, timeout=10)
        if self.succeeded:
            pushadd_to_gateway(gateway, job=JOB, registry=self.success_registry, grouping_key=key, timeout=10)


class InstrumentedClient:
    """Same methods as TcgcsvClient; times each call into tcg_source_request_duration_seconds."""

    METHODS = {"groups": "groups", "products": "products", "prices_today": "prices", "prices_archive": "archive"}

    def __init__(self, client, metrics: RunMetrics):
        self._client = client
        self._metrics = metrics

    def __getattr__(self, name):
        target = getattr(self._client, name)
        endpoint = self.METHODS.get(name)
        if endpoint is None or not callable(target):
            return target

        def call(*args, **kwargs):
            t0 = time.perf_counter()
            try:
                return target(*args, **kwargs)
            except Exception:
                self._metrics.source_errors.labels(endpoint=endpoint).inc()
                raise
            finally:
                self._metrics.source_latency.labels(endpoint=endpoint).observe(time.perf_counter() - t0)

        return call


class WarehouseCollector:
    """A custom collector: reads the warehouse at each scrape, as an exporter does.

    The DuckDB file accepts one writer process at a time, so while a run is
    writing the scrape cannot open it; the collector then reports
    tcg_warehouse_readable 0 instead of failing the whole scrape. The same
    happens when the file exists but the gold layer was never built.
    """

    def __init__(self, db_path: Path):
        self.db_path = Path(db_path)

    def collect(self):
        readable = GaugeMetricFamily("tcg_warehouse_readable", "1 when the exporter could read the DuckDB file at this scrape")
        if not self.db_path.exists():
            readable.add_metric([], 0)
            yield readable
            return
        try:
            con = duckdb.connect(str(self.db_path), read_only=True)
        except duckdb.Error:
            readable.add_metric([], 0)
            yield readable
            return
        try:
            families = list(self._read(con))
        except duckdb.Error:  # a warehouse without the gold layer yet, after a run that failed early
            families = []
        finally:
            con.close()
        yield from families
        readable.add_metric([], 1 if families else 0)
        yield readable

    def _read(self, con):
        rows = GaugeMetricFamily("tcg_ingestion_rows", "Rows of db_ingestion, by data tag", labels=["data_tag"])
        last = GaugeMetricFamily("tcg_ingestion_last_timestamp_seconds",
                                 "Unix time of the newest record of db_ingestion, by data tag", labels=["data_tag"])
        batches = GaugeMetricFamily("tcg_ingestion_batches", "Distinct capture timestamps, by data tag", labels=["data_tag"])
        for tag, n, newest, distinct in con.execute(
                "SELECT data_tag, count(*), max(timestamp), count(DISTINCT timestamp) FROM db_ingestion GROUP BY 1 ORDER BY 1").fetchall():
            rows.add_metric([tag], n)
            last.add_metric([tag], newest)
            batches.add_metric([tag], distinct)
        yield rows
        yield last
        yield batches

        fact_rows, fact_keys = con.execute(
            "SELECT count(*), count(DISTINCT (date_unix, product_id, variant)) FROM gold.fact_price").fetchone()
        g = GaugeMetricFamily("tcg_gold_fact_rows", "Rows of gold.fact_price")
        g.add_metric([], fact_rows)
        yield g
        g = GaugeMetricFamily("tcg_gold_fact_grain_keys", "Distinct keys (date, product, variant) of gold.fact_price")
        g.add_metric([], fact_keys)
        yield g

        status = GaugeMetricFamily("tcg_pipeline_last_run_tasks", "Task attempts of the last run in ops.pipeline_runs, by status",
                                   labels=["status"])
        ended = GaugeMetricFamily("tcg_pipeline_last_run_end_timestamp_seconds", "Unix time of the end of the last run")
        last_run = con.execute("SELECT run_id FROM ops.pipeline_runs ORDER BY started_at DESC, ended_at DESC LIMIT 1").fetchone()
        if last_run:
            for st, n in con.execute("SELECT status, count(*) FROM ops.pipeline_runs WHERE run_id = ? GROUP BY 1 ORDER BY 1",
                                     [last_run[0]]).fetchall():
                status.add_metric([st], n)
            ended.add_metric([], con.execute("SELECT max(ended_at) FROM ops.pipeline_runs WHERE run_id = ?",
                                             [last_run[0]]).fetchone()[0])
        yield status
        yield ended


def exporter_registry(db_path: Path) -> CollectorRegistry:
    registry = CollectorRegistry()
    registry.register(WarehouseCollector(db_path))
    return registry


def serve(db_path: Path, port: int, addr: str = "0.0.0.0"):
    """Start the HTTP endpoint /metrics of the exporter; returns the server and its thread."""
    from prometheus_client import start_http_server

    return start_http_server(port, addr=addr, registry=exporter_registry(db_path))

The wrapper keeps the direction of the layers. The ETL layer does not import prometheus_client: the pipeline, which already sits above the layers, gives the extraction a client that has the same methods as TcgcsvClient and measures each call on the way. A test of the extraction can therefore still use the fake client of Lesson 7 without any metric.

8. The pipeline calls the metrics

The pipeline creates a RunMetrics at the start of the run and calls it at three moments: after each attempt of a task, with its outcome, its duration and its result; when a task is skipped because a dependency failed; and at the end, with the list of failed tasks. The result of an extraction is the number of rows it wrote, which becomes tcg_task_rows, and the result of check_quality is the dictionary of measured numbers, which becomes tcg_quality_value.

The time of the last success lives in a second registry, set only when the run succeeds. The separation matters at the moment of the push, described in Part IV: a failed run sends its failure without touching the time of the last good run, which is what the alert on a missing run needs.

src/tcg_dataapp/pipeline.py
"""The pipeline: tasks with dependencies, run in order, with retries and a log of every run.

Each task is a function of the run context. A task runs only after all the
tasks it depends on succeeded; a failure is retried, and a task that still
fails stops every task that depends on it. Every attempt is recorded in
ops.pipeline_runs, with Unix times, so a run can be audited afterwards.

Lesson 10: the run also records its metrics in a telemetry.RunMetrics object
(attempts, durations, rows, requests to the source, the numbers of the quality
check and the outcome of the run), which the command line pushes to a
Pushgateway and writes to out/metrics.prom.
"""
from __future__ import annotations

import time
import uuid
from dataclasses import dataclass, field
from typing import Callable

import duckdb

from tcg_dataapp.config import Settings
from tcg_dataapp.etls import extract
from tcg_dataapp.etls.tcgcsv import TcgcsvClient
from tcg_dataapp.processors import gold, quality
from tcg_dataapp.telemetry import RunMetrics
from tcg_dataapp.views import report

LOG_DDL = """
CREATE SCHEMA IF NOT EXISTS ops;
CREATE TABLE IF NOT EXISTS ops.pipeline_runs (
    run_id     VARCHAR,
    task       VARCHAR,
    attempt    INTEGER,
    status     VARCHAR,
    started_at BIGINT,
    ended_at   BIGINT,
    detail     VARCHAR
);
"""


@dataclass
class Task:
    name: str
    run: Callable[["Context"], object]
    depends_on: tuple = ()
    retries: int | None = None


@dataclass
class Context:
    settings: Settings
    con: duckdb.DuckDBPyConnection
    client: TcgcsvClient
    run_id: str
    captured_at: int
    metrics: RunMetrics | None = None
    results: dict = field(default_factory=dict)


def build_tasks(settings: Settings, with_today: bool = False) -> list[Task]:
    tasks = [
        Task("extract_sets", lambda c: extract.extract_sets(c.con, c.client, c.settings.sets, c.captured_at)),
        Task("extract_products", lambda c: extract.extract_products(c.con, c.client, c.settings.sets, c.captured_at),
             depends_on=("extract_sets",)),
    ]
    price_tasks = []
    for day in settings.price_dates:
        name = f"extract_prices_{day}"
        tasks.append(Task(name, lambda c, d=day: extract.extract_prices_archive(c.con, c.client, c.settings.sets, d),
                          depends_on=("extract_products",)))
        price_tasks.append(name)
    if with_today:
        tasks.append(Task("extract_prices_today",
                          lambda c: extract.extract_prices_today(c.con, c.client, c.settings.sets, extract.today()),
                          depends_on=("extract_products",)))
        price_tasks.append("extract_prices_today")
    tasks += [
        Task("build_gold", lambda c: gold.build_gold(c.con), depends_on=tuple(price_tasks), retries=0),
        Task("check_quality", lambda c: quality.check_gold(c.con), depends_on=("build_gold",), retries=0),
        Task("freeze_reports", lambda c: gold.freeze_month(c.con, c.settings.frozen_month),
             depends_on=("check_quality",), retries=0),
        Task("export_marts", lambda c: [p.as_posix() for p in report.export_marts(c.con, c.settings.out_dir)],
             depends_on=("check_quality",)),
        Task("write_report", lambda c: report.write_report(c.con, c.settings.out_dir, c.run_id).as_posix(),
             depends_on=("freeze_reports", "export_marts")),
    ]
    return tasks


def order(tasks: list[Task]) -> list[Task]:
    """Topological order of the tasks; raises on an unknown dependency or a cycle."""
    by_name = {t.name: t for t in tasks}
    for t in tasks:
        for d in t.depends_on:
            if d not in by_name:
                raise ValueError(f"task {t.name} depends on unknown task {d}")
    done, ordered, visiting = set(), [], set()

    def visit(t: Task):
        if t.name in done:
            return
        if t.name in visiting:
            raise ValueError(f"cycle at task {t.name}")
        visiting.add(t.name)
        for d in t.depends_on:
            visit(by_name[d])
        visiting.discard(t.name)
        done.add(t.name)
        ordered.append(t)

    for t in tasks:
        visit(t)
    return ordered


def _log(con, run_id, task, attempt, status, started, ended, detail):
    con.execute("INSERT INTO ops.pipeline_runs VALUES (?, ?, ?, ?, ?, ?, ?)",
                [run_id, task, attempt, status, started, ended, str(detail)[:500]]).fetchall()


def run(settings: Settings, tasks: list[Task] | None = None, client: TcgcsvClient | None = None,
        con: duckdb.DuckDBPyConnection | None = None, with_today: bool = False,
        echo: Callable[[str], None] = print, metrics: bool = True) -> Context:
    own = con is None
    if own:
        settings.db_path.parent.mkdir(parents=True, exist_ok=True)
        con = duckdb.connect(str(settings.db_path))
    for statement in con.extract_statements(LOG_DDL):
        con.execute(statement).fetchall()
    run_id = uuid.uuid4().hex[:12]
    m = RunMetrics(run_id) if metrics else None
    source = client or TcgcsvClient(settings.base_url, settings.category)
    ctx = Context(settings=settings, con=con, client=m.instrument(source) if m else source,
                  run_id=run_id, captured_at=extract.now_unix(), metrics=m)
    failed: set[str] = set()
    try:
        for task in order(tasks or build_tasks(settings, with_today)):
            if any(d in failed for d in task.depends_on):
                failed.add(task.name)
                _log(con, ctx.run_id, task.name, 0, "skipped", extract.now_unix(), extract.now_unix(), "a dependency failed")
                echo(f"  skip  {task.name}  (a dependency failed)")
                if m:
                    m.attempt(task.name, "skipped")
                continue
            attempts = 1 + (settings.retries if task.retries is None else task.retries)
            for attempt in range(1, attempts + 1):
                started = extract.now_unix()
                t0 = time.perf_counter()
                try:
                    result = task.run(ctx)
                except Exception as error:  # noqa: BLE001 - every failure is logged and retried
                    _log(con, ctx.run_id, task.name, attempt, "failed", started, extract.now_unix(),
                         f"{type(error).__name__}: {error}")
                    if m:
                        m.attempt(task.name, "failed", time.perf_counter() - t0)
                    echo(f"  fail  {task.name}  attempt {attempt}/{attempts}: {type(error).__name__}: {error}")
                    if attempt == attempts:
                        failed.add(task.name)
                    else:
                        time.sleep(settings.retry_delay * attempt)
                    continue
                ctx.results[task.name] = result
                _log(con, ctx.run_id, task.name, attempt, "success", started, extract.now_unix(), result)
                if m:
                    m.attempt(task.name, "success", time.perf_counter() - t0, result)
                echo(f"  ok    {task.name}  {time.perf_counter() - t0:5.2f} s  {result}")
                break
    finally:
        if own:
            con.close()
    ctx.results["_failed"] = sorted(failed)
    if m:
        m.finish(ctx.results["_failed"])
    return ctx

Part IVPush and exporter

10. Why a batch job pushes

The run lasted 25.1 seconds in the rehearsal and about 40 seconds in Lesson 7, while Prometheus scrapes every 15 seconds. A run that exposed an endpoint would be scraped once or twice, at random moments of its execution, and would disappear before the final numbers existed. The documentation of Prometheus prescribes, for this case of a batch job at the level of a service, a Pushgateway: the job sends its metrics when it ends, the Pushgateway keeps the last values of each group, and Prometheus scrapes the Pushgateway as an ordinary target.

Two details of the configuration decide whether the result is correct. The push uses pushadd, an HTTP POST that replaces only the metrics with the names being sent, and not push, a PUT that replaces the whole group: with a PUT, a failed run would erase tcg_run_last_success_timestamp_seconds, and the alert on a missing run would lose its reference. On the side of Prometheus, the job of the Pushgateway declares honor_labels: true, which keeps the labels job="tcg_dataapp" and instance of the push instead of replacing them with the labels of the Pushgateway itself.

tcg-dataapp run --push: what goes to the Pushgateway
POST /metrics/job/tcg_dataapp/instance/local   the metrics of the run (always)
POST /metrics/job/tcg_dataapp/instance/local   tcg_run_last_success_timestamp_seconds (only after a success)

The Pushgateway has a known cost, which the alerts compensate. It keeps the last values indefinitely, so Prometheus cannot distinguish a job that died from a job that has not run yet; up refers to the Pushgateway, not to the job. The answer is to alert on the age of the last success, which grows whether the job failed, died or was never called. The Pushgateway also adds to each group the series push_time_seconds, the moment of the last push, successful or not.

11. An exporter of the warehouse

Some numbers belong to the data and not to a run: the age of the newest price, the rows of the landing table, the agreement between the rows and the keys of the fact. They exist between runs and should be read whenever Prometheus asks. An exporter is a long-running process that translates the state of another system into metrics at each scrape, in the same way that postgres_exporter reads PostgreSQL. tcg-dataapp metrics is a small exporter of the DuckDB file: at each scrape, its custom collector opens the file read-only, reads db_ingestion, gold.fact_price and ops.pipeline_runs, and closes it.

12. A finding of the rehearsal: one writer and no reader

DuckDB allows one process to open a file for writing, and while that process holds it, no other process may open it, even for reading. The rehearsal made this visible: of three scrapes taken during a run, the first answered and the next two could not open the file. A collector that raised the error would make the whole scrape fail, and Prometheus would mark the exporter as down during every run. The collector instead reports tcg_warehouse_readable 0 and no other metric, and does the same when the file exists but the gold layer was never built, which happened after the failed run of the rehearsal and made the first version of the exporter answer with an HTTP error.

The alert TcgExporterDown waits two minutes before firing, longer than a run holds the file. In a production warehouse with concurrent readers, such as the ClickHouse of the class or a PostgreSQL, the restriction does not exist; it is a property of an embedded database, and it is the kind of constraint that only appears when monitoring and processing run at the same time.

14. Answering questions in PromQL

PromQL selects series by name and labels and operates on whole vectors of series at once. A selector such as tcg_task_rows{task=~"extract_prices_.*"} returns one series per matching task; an aggregation such as sum or topk combines them; and an arithmetic operator between two vectors matches series with the same labels, which is how tcg_gold_fact_rows - tcg_gold_fact_grain_keys compares two metrics of the exporter. time() returns the moment of the evaluation, so subtracting a timestamp gives an age. 15. Histograms, quantiles and recording rules

A histogram keeps only how many observations fell at or below each bound, so a quantile is estimated. histogram_quantile finds the bucket in which the quantile falls and interpolates linearly inside it. For the groups, a single request of 0.70 seconds lies in the bucket from 0.5 to 1 second, and the 95th percentile is placed at 95% of that bucket, 0.5 + 0.95 × 0.5 = 0.975 seconds; for the archives, five requests between 2 and 4 seconds give 3.9 seconds. The estimate is as precise as the buckets allow, which is why the bounds were chosen around the times observed in Lesson 7.

A pushed histogram holds only the last run, since each push replaces it, so rate() over it has no meaning and the quantile is taken directly over the buckets. In a service that lives longer than the scrape the usual form is histogram_quantile(0.95, sum by (le) (rate(..._bucket[5m]))), which estimates the quantile of the last five minutes.

A recording rule evaluates an expression at every interval and stores the result as a new series, named by the convention level:metric:operation. The lab records two: the freshness of the prices and the p95 of the requests. The freshness is clamped at zero because of a finding of the rehearsal: the prices of today are stored at 12:00 UTC of the day, so a run with --with-today before noon stores a price in the future, and the raw age measured was −1,841 seconds.

the recording rules of stack/prometheus/rules.yml
# Lesson 10 · recording and alerting rules of the DataApp.
# Check with: promtool check rules rules.yml
groups:
  - name: tcg_dataapp_recording
    rules:
      # Seconds since the newest price was captured. Written once, reused by the
      # dashboard and by the alert below. The prices of today are stored at noon

16. Alerting rules

An alerting rule is a PromQL expression that, when it returns any series, creates an alert with the labels of that series. An alert calls a person, so each rule should describe a symptom that someone must act on, and each threshold should come from how the DataApp runs rather than from a round number. for: asks the condition to hold for a period before the alert fires, which filters a single bad scrape; an alert in that period is pending.

23. What the rehearsal revealed

Three problems appeared only when the stack ran against real runs, and the prompts and the reference already carry their corrections.

An exporter that failed after a failed run

The run against a closed port created the DuckDB file and the run log, but no landing table and no gold layer. The first version of the collector queried db_ingestion, received an error and answered the scrape with an HTTP 500. The collector now reads everything inside one guarded block and reports tcg_warehouse_readable 0 when any table is missing.

A price in the future

The run with --with-today at 11:29 UTC stored the prices of the day at 12:00 UTC, a decision of Lesson 7 that keeps one price per product per day. The age of the newest price came out at −1,841 seconds, about half an hour in the future. The recording rule clamps the age at zero, so that a run in the morning reads as fresh data instead of as an impossible value.

Labels, counters and the global registry

Agents tend to put the identifier of the run in a label, which creates a new series at every run, and to register metrics in the global registry of the library, which makes the second test fail with a duplicated metric. The prompts forbid both. Agents also tend to push with PUT, which erases the time of the last success when a run fails; the test of the push catches it.

24. The second hour

In the second hour each group instruments one service of its own DataApp, the pipeline packaged in Lesson 7 or the flow orchestrated in Lesson 8, with the four prompts adapted to the partner data. The result expected at the end of the session is the metrics of each run pushed to a Pushgateway, a measure of the freshness and the volume of the partner data, read by an exporter or by a query, a Grafana dashboard provisioned from files and at least three alerting rules, each with a promtool test. The stack of lab/lesson-10/stack/ is the starting point, and the run log of Lesson 7 is the source of the numbers that already exist.

26. Checklist

  • Every metric has the prefix of the application and its unit in the name.
  • No label takes an identifier of run, product or user.
  • The batch run pushes with POST, and the time of the last success survives a failure.
  • The freshness and the volume of the data are measured outside the run.
  • Prometheus scrapes the Pushgateway with honor_labels: true.
  • Every alert describes a symptom, and every threshold has a reason.
  • Every alert has a promtool test.
  • The dashboard and the datasource are provisioned from files.
  • Every image of the stack is pinned to a version.
