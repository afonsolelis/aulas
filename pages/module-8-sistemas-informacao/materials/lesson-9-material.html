2. Why a DataApp needs automated tests

A DataApp runs every day without a person, and each property that someone once checked by reading a result, such as a grain that holds, a rerun that duplicates nothing or a frozen report that never changes, remains true only while the code that guarantees it is not changed. An automated test turns such a property into code that checks it at every change, so that a change that breaks it fails before it reaches the main branch. In Lesson 7 the package received nine tests of this kind, which run in about two seconds without the network.

A test also has two roles beyond regression. It is a specification: test_a_month_with_two_captures_freezes_only_the_last states the semi-additive rule of Lesson 6 in a form that a machine checks. And it constrains the design, because only decoupled code can be tested in isolation; the ETL layer of the package receives its client as a parameter, which is what allows the tests to replace the source by a fake one.

The nine tests of Lesson 7, however, cover the behaviours that the author remembered while writing the package. The question that this session answers is different: which behaviours does the partner depend on, and which of them are tested? Answering it requires deriving the tests from the quality attributes that the business requires, which is what the ATAM does.

3. Levels of test

Tests differ in the size of what they exercise. The test pyramid, popularised by Mike Cohn, recommends many fast tests at the base, which exercise one function, and few slow tests at the top, which exercise the whole system; the lower the level, the more precisely a failure points to its cause, and the higher the level, the closer the test is to what the user observes. In a data pipeline, two further kinds are frequent: contract tests, which check the shape of an output that other systems read, and performance tests, which check a measure of time under a given volume.

The quality gates of Lesson 7 are themselves tests of the data, which run in production on every run. The tests of this session check that those gates stop the run when they must, and that they do not stop it when the data is sound.

4. pytest: Arrange, Act, Assert

A test in pytest is a function whose name starts with test_, in a file whose name starts with test_. It follows the pattern Arrange, Act, Assert: it prepares the situation, performs one action and checks the outcome with plain assert statements, which pytest rewrites to report the values that differed when a check fails. The test below is one of the test cases of scenario S04 of the reference.

tests/scenarios/test_correctness.py
@pytest.mark.scenario("S04")
def test_s04_renamed_price_field_stops_the_run(settings):
    """TC04.1 a renamed price field stops the run"""
    prices = copy.deepcopy(PRICES)
    for rows in prices["2026-09-01"].values():
        for r in rows:
            r["market_price"] = r.pop("marketPrice")
    ctx = pipeline.run(settings, client=FakeClient(prices=prices), echo=quiet)
    assert "check_quality" in ctx.results["_failed"]
    con = duckdb.connect(str(settings.db_path), read_only=True)
    detail = con.execute("SELECT detail FROM ops.pipeline_runs WHERE task = 'check_quality'").fetchone()[0]
    assert "null market price" in detail

Part IIThe ATAM

5. The ATAM and what this session keeps of it

The Architecture Tradeoff Analysis Method was developed at the Software Engineering Institute of Carnegie Mellon University to evaluate a software architecture against the quality attributes that its business goals require (Kazman, Klein and Clements, 2000). In its full form, an evaluation team, the architects and the stakeholders meet over several days: the business drivers and the architecture are presented, the architectural approaches are identified, a utility tree is built and prioritised, the approaches are analysed against the scenarios of highest priority, the stakeholders propose further scenarios, and the results are presented as risks, non-risks, sensitivity points and tradeoffs.

This session keeps the artefacts of the method and replaces the analysis by discussion with execution. Each scenario receives a response measure that a test can check, and the result of the test is the evidence that the architecture achieves the response or fails to achieve it. A scenario whose measure is not checked by a test remains a hypothesis about the architecture.

6. Business drivers and quality attributes

A business driver states what the system exists for and what the organisation needs from it, and each driver has consequences for the architecture. The quality attributes follow from the drivers: an attribute that no driver justifies is not analysed, because nothing in the business depends on it. The five drivers of the reference were written from the README of the package and from the conditions of the source.

CodeDriverConsequence for the architecture
BD1Collectors and analysts decide purchases from the answers of the report; a wrong number costs more than a late one.The run must stop before it publishes a number it cannot vouch for.
BD2The frozen monthly report is cited after the month ends.A frozen report is never rebuilt, whatever arrives later.
BD3The source is a free public mirror without a service level.Failures of the source are expected events, handled by retries, gates and checks of freshness.
BD4The DataApp runs every day without a person, on modest hardware.Each run is idempotent and logged, and the processing fits a small machine.
BD5The team changes the model every sprint.The tests run in seconds, without the network.

From these drivers come eight quality attributes: correctness, reliability, auditability, interoperability, timeliness, performance, testability and modifiability. Security is absent from the reference because the DataApp reads public data and publishes nothing personal; in a DataApp that handles data of people, it would follow from a driver and would have its own branch of the tree, which Lesson 13 discusses.

7. The utility tree

The utility tree organises the quality attributes in levels. The root is the utility of the system; the first level holds the attributes, the second their refinements, and each leaf is a concrete scenario. Each leaf receives two ratings, each H, M or L: its importance for the business drivers and the difficulty, for the architecture, of achieving it. The pair orders the analysis, starting from the leaves rated (H,H) and (H,M); a leaf rated (L,L) can wait, and a leaf rated (L,H) deserves the question of why it is in the tree at all.

A leaf names a situation that can happen to the system, such as "the source renames a field", and never a wish, such as "the system is robust". The difference is practical: only a situation can be reproduced by a test.

8. Quality attribute scenarios in six parts

A leaf of the tree is still a sentence. The quality attribute scenario, in the form of Bass, Clements and Kazman (2021), makes it precise in six parts: the source that generates a stimulus; the stimulus that reaches the system; the artifact that receives it; the environment, or state of the system, when it happens; the response of the system; and the response measure, which states how the response is checked. The measure is the part that connects the scenario to a test, because it becomes the assertions of the test.

9. Risks, non-risks, sensitivity points and tradeoffs

KindDefinitionExample in the reference
riskan architectural decision that may prevent the system from achieving a responsethe inner join of gold.fact_price drops a price whose product is not in the catalogue, and no check notices (S03)
non-riska decision that the analysis showed to be soundreading the JSON by field name makes a new field of the source change no number (S04, TC04.2)
sensitivity pointa parameter or decision on which a response dependsthe timestamp of noon UTC decides what is the same batch; another hour breaks the idempotency of S01
tradeoffa decision that improves one attribute and worsens anothera stricter quality gate publishes fewer wrong numbers and causes more failed runs: correctness against availability (S02 to S04)

The classification is the output of the method. A list of passed and failed tests says what happened; the classification says what it means for the next decision of the team, and it keeps the tradeoffs that were accepted on purpose apart from the risks that were found by accident.

Part IIIFrom scenarios to tests

10. Deriving test cases

A test case fixes the abstract parts of a scenario as concrete data. The stimulus becomes something the test can produce, such as a fake source that renames a field; the environment becomes a fixture, such as a warehouse after a successful run; and the response measure becomes the assertions. A scenario whose measure has several conditions, or whose stimulus has variants, yields more than one test case. Every test case traces to exactly one scenario, and a test case that traces to none is not written, because nothing in the business depends on it.

11. Traceability in the code

The link between a test and its scenario is a marker, registered in pyproject.toml with --strict-markers, so that a misspelt marker fails the collection. The first line of the docstring carries the id of the test case. A small plugin in tests/conftest.py reads docs/scenarios.toml, refuses a test that declares a scenario that does not exist, records the outcome of each traced test, prints one line per scenario at the end of the run and writes out/traceability.json. The option --scenario S04 runs only the tests of one scenario.

tests/conftest.py · traceability
# --------------------------------------------------------------- traceability
SCENARIOS: dict[str, dict] = {}
OUTCOMES: dict[str, list[tuple[str, str, str]]] = {}
STARTED = [0.0]


def pytest_addoption(parser):
    parser.addoption("--scenario", action="append", default=[],
                     help="run only the tests of this ATAM scenario (repeatable), e.g. --scenario S04")


def pytest_configure(config):
    path = Path(config.rootpath) / "docs" / "scenarios.toml"
    SCENARIOS.update({s["id"]: s for s in tomllib.loads(path.read_text(encoding="utf-8"))["scenario"]})
    STARTED[0] = time.perf_counter()


def _scenario_of(item):
    mark = item.get_closest_marker("scenario")
    return mark.args[0] if mark else None


def pytest_collection_modifyitems(config, items):
    for item in items:
        sid = _scenario_of(item)
        if sid is not None and sid not in SCENARIOS:
            raise pytest.UsageError(f"{item.nodeid} declares scenario {sid}, which is not in docs/scenarios.toml")
    wanted = set(config.getoption("--scenario"))
    if wanted:
        keep = [i for i in items if _scenario_of(i) in wanted]
        config.hook.pytest_deselected(items=[i for i in items if i not in keep])
        items[:] = keep


def pytest_runtest_logreport(report):
    if report.when == "call" or (report.when == "setup" and report.outcome != "passed"):
        sid = dict(report.user_properties).get("scenario")
        if sid:
            case = dict(report.user_properties).get("case", "")
            OUTCOMES.setdefault(sid, []).append((report.nodeid.split("::")[-1], case, report.outcome))


@pytest.hookimpl(tryfirst=True)
def pytest_runtest_setup(item):
    sid = _scenario_of(item)
    if sid:
        doc = (item.function.__doc__ or "").strip().splitlines()
        item.user_properties.append(("scenario", sid))
        item.user_properties.append(("case", doc[0] if doc else ""))


def pytest_terminal_summary(terminalreporter, config):
    if not OUTCOMES:
        return
    elapsed = time.perf_counter() - STARTED[0]
    tr = terminalreporter
    tr.section("ATAM traceability")
    rows = []
    selected = set(config.getoption("--scenario")) or set(SCENARIOS)
    for sid, s in SCENARIOS.items():
        if sid not in selected:
            continue
        results = OUTCOMES.get(sid, [])
        passed = sum(1 for *_, o in results if o == "passed")
        status = "NOT COVERED" if not results else ("PASS" if passed == len(results) else "FAIL")
        rows.append({"id": sid, "attribute": s["attribute"], "refinement": s["refinement"],
                     "priority": f"({s['importance']},{s['difficulty']})", "tests": len(results),
                     "passed": passed, "status": status,
                     "cases": [{"test": t, "case": c, "outcome": o} for t, c, o in results]})
        name = f"{s['attribute']} · {s['refinement']}"
        tr.write_line(f"{sid}  {rows[-1]['priority']}  {name:48.48} {passed}/{len(results)}  {status}")
    tr.write_line(f"suite time {elapsed:.2f} s")
    out = Path(config.rootpath) / "out"
    out.mkdir(exist_ok=True)
    (out / "traceability.json").write_text(json.dumps({"suite_seconds": round(elapsed, 2), "scenarios": rows},
                                                      indent=2), encoding="utf-8")

12. A fake source and a suite without network

All tests run against a fake client of tcgcsv with two sets, four products and prices on two dates. The parameter prices lets a test change what the source publishes, which is how the stimuli of S03, S04 and S05 are produced, and fail_times makes the first calls fail, which produces the stimuli of S06 and S07. An autouse fixture replaces the connection of every socket by an error, so that a test that tries to reach the network fails instead of passing slowly; scenario S13 checks that this block is in force.

tests/conftest.py · the fake source and the block of the network
class FakeClient:
    """The source of the tests. prices can replace PRICES to simulate a change of the source."""

    def __init__(self, fail_times: int = 0, prices: dict | None = None):
        self.fail_times = fail_times
        self.calls = 0
        self.prices = copy.deepcopy(PRICES) if prices is None else prices

    def groups(self):
        self.calls += 1
        if self.calls <= self.fail_times:
            raise ConnectionError("tcgcsv is down")
        return list(SETS.values()) + [{"groupId": 99, "name": "Other", "abbreviation": "OT", "publishedOn": "2020-01-01T00:00:00"}]

    def products(self, group_id):
        return PRODUCTS[group_id]

    def prices_archive(self, day, group_ids):
        return {g: self.prices[day].get(g, []) for g in group_ids}

    def prices_today(self, group_id):
        return self.prices["2026-09-01"].get(group_id, [])

13. Three scenarios as tests

The scenario S02 requires that a broken grain stop the run before anything is published. Its test first runs the pipeline successfully, keeps the bytes of the report, simulates a defective extractor that loads the prices of a day twice, and runs again.

S02 · TC02.1
@pytest.mark.scenario("S02")
def test_s02_broken_grain_stops_the_run_and_keeps_the_report(settings):

15. The changes of version 0.3.0

Each risk of high importance received the smallest change that closes it. The quality gate now compares, capture by capture, the prices of the landing table with the prices that reached the fact, and stops the run when more than 1 % of a capture is lost or when more than 10 % of its market prices are null. The vacuous check was removed. The freshness of the data became a function and a command, tcg-dataapp freshness --max-age-days 2, which returns exit code 1 when the last capture is older than the limit.

src/tcg_dataapp/processors/quality.py
"""Checks that stop the pipeline when the gold layer is wrong, and the check of freshness.

Version 0.3.0 adds two checks found by the ATAM scenarios of Lesson 9:
S03, prices of the landing table that never reach the fact, and S04, a
capture whose market prices became null because the source renamed a
field. The check of 0.1.0 that counted prices without a set was removed:
gold.fact_price is an inner join with gold.dim_set, so it could never fail.
"""
from __future__ import annotations

import duckdb

from tcg_dataapp.etls.landing import run

MAX_DROPPED_SHARE = 0.01  # S03: share of the prices of a capture that may miss the fact
MAX_NULL_SHARE = 0.10     # S04: share of null market prices in a capture (real maximum 1.7 %)


class QualityError(RuntimeError):
    pass


class StaleDataError(RuntimeError):
    pass


def check_gold(con: duckdb.DuckDBPyConnection, max_dropped_share: float = MAX_DROPPED_SHARE,
               max_null_share: float = MAX_NULL_SHARE) -> dict:
    """Return the measured numbers, or raise QualityError naming the check that failed."""
    m = {}
    for tag in ("tcgplayer.set.v1", "tcgplayer.product.v1", "tcgplayer.price.v1"):
        m[tag] = run(con, "SELECT count(*) FROM db_ingestion WHERE data_tag = ?", [tag])[0][0]
        if m[tag] == 0:
            raise QualityError(f"db_ingestion has no rows of {tag}")
    rows, keys = run(con, "SELECT count(*), count(DISTINCT (date_unix, product_id, variant)) FROM gold.fact_price")[0]
    m["fact_rows"], m["fact_grain_keys"] = rows, keys
    if rows != keys:
        raise QualityError(f"grain of gold.fact_price broken: {rows} rows for {keys} keys")

    # S03: every price of the landing table reaches the fact, capture by capture
    per_capture = run(con, """
        WITH landing AS (SELECT timestamp // 86400 * 86400 AS date_unix, count(*) AS n
                         FROM db_ingestion WHERE data_tag = 'tcgplayer.price.v1' GROUP BY 1),
             fact AS (SELECT date_unix, count(*) AS n,
                             count(*) FILTER (WHERE market_price IS NULL) AS nulls
                      FROM gold.fact_price GROUP BY 1)
        SELECT l.date_unix, l.n, coalesce(f.n, 0), coalesce(f.nulls, 0)
        FROM landing l LEFT JOIN fact f USING (date_unix) ORDER BY 1""")
    m["prices_not_in_fact"] = sum(n - in_fact for _, n, in_fact, _ in per_capture)
    for date_unix, n, in_fact, nulls in per_capture:
        dropped = (n - in_fact) / n
        if dropped > max_dropped_share:
            raise QualityError(f"{n - in_fact} of {n} prices of the capture {date_unix} did not reach "
                               f"gold.fact_price ({dropped:.1%} > {max_dropped_share:.0%})")
        null_share = nulls / in_fact if in_fact else 1.0
        if null_share > max_null_share:
            raise QualityError(f"{nulls} of {in_fact} prices of the capture {date_unix} have a null market price "
                               f"({null_share:.1%} > {max_null_share:.0%}); did the source rename a field?")
    m["max_null_price_share"] = round(max((nulls / in_fact for _, _, in_fact, nulls in per_capture if in_fact),
                                          default=0.0), 4)
    m["dates"] = run(con, "SELECT count(*) FROM gold.dim_date")[0][0]
    m["cube_cells"] = run(con, "SELECT count(*) FROM gold.agg_price_cube")[0][0]
    return m


def check_freshness(con: duckdb.DuckDBPyConnection, now: int, max_age_days: float = 2) -> float:
    """S11: age in days of the last capture; raise StaleDataError when it is older than max_age_days."""
    last = run(con, "SELECT max(timestamp) FROM db_ingestion WHERE data_tag = 'tcgplayer.price.v1'")[0][0]
    if last is None:
        raise StaleDataError("db_ingestion has no prices")
    age = (now - last) / 86400
    if age > max_age_days:
        raise StaleDataError(f"last capture {last} is {age:.1f} days old (limit {max_age_days:g} days)")
    return round(age, 2)

Each student, alone, applies the six steps of the method to the DataApp of the group: the business drivers and quality attributes, the rated utility tree, the scenarios in six parts, the test cases traced to them, the tests implemented and run on the code as it is, and the findings read back into the tree. 20. Recurring mistakes

Changing the assertion until the test passes

When a test fails on the first run, coding agents tend to adjust the assertion or the fixture until it passes. A failure in step 05 is a finding about the architecture and must be kept; the prompt of step 05 forbids changing the assertion, and step 06 decides what to do about the failure.

Measures that cannot be checked

A measure such as "the pipeline is reliable" or "the report is fast" cannot become an assertion. The measure needs a number or a verifiable condition, such as "exit code 1" or "less than 10 s on 100,000 prices", and a number taken from the real data is measured before it is written.

Leaves that are wishes, and everything rated H

A tree whose leaves are qualities ("robust", "scalable") has no scenario to test, and a tree in which every leaf is rated (H,H) gives no order of analysis. The ratings are relative: within one DataApp, some leaves matter more than others.

Tests that reach the network

A test that calls the real source is slow, fails when the source is down and passes or fails for reasons outside the code. The fixture that blocks the network turns such a test into an immediate failure, which shows where the fake source is missing.
