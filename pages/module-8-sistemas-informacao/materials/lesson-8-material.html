2. From a runner to an orchestrator

The runner of Lesson 7, in pipeline.py, did three jobs: it sorted the twelve tasks so that each one came after its dependencies, it retried a failed task with a growing pause, and it wrote every attempt to ops.pipeline_runs. These jobs are the same in every pipeline, which is why they are the core of the tools called orchestrators. An orchestrator does them for any graph of tasks and adds what a runner written in class does not have: tasks that run at the same time when nothing orders them, options of retry and cache chosen task by task, a schedule kept outside the code, and a server that keeps the history of every run and shows it in an interface.

The three layers of the package do not change. The flow is a new module, flows.py, which calls the same functions of etls/, processors/ and views/ that the runner called, and the runner itself stays in the package so that the two can be compared on the same data.

3. The pipeline as a directed acyclic graph

A pipeline can be described as a graph in which each task is a node and each edge states that a task needs the output, or the effect, of another. The graph is directed, because a dependency has a sense: the gold layer needs the loaded prices, and no load needs the gold layer. It is acyclic, because a cycle would have no first task and could never start. These two properties are what allow a topological order to exist, and an orchestrator only needs that order and the states of the tasks to decide what to run next.

The graph also says what may run at the same time: two tasks without a path between them do not depend on each other, and an orchestrator can run them in parallel. A false edge, which states a dependency that the data does not have, therefore costs time without adding safety. In Lesson 7 each extraction of prices waited for the extraction of the products, although a price archive does not need the catalogue; the only task that needs both is build_gold, which joins them. Removing that edge lets the five archives download at once, and the run falls from about forty seconds to about nine seconds of tasks.

The extraction of prices of Lesson 7 is split in two tasks in the flow, a download and a load. The split is not cosmetic: the download only reads from the network, while the load writes to the warehouse, and Part III shows that the two need opposite options of cache.

Part IITasks and flow

4. Tasks, flows and futures in Prefect 3

In Prefect a flow is a Python function decorated with @flow, and a task is a function decorated with @task. A task called inside a flow becomes a task run, with its own state, retries, cache and logs. Calling .submit() on a task sends it to the task runner and returns a future at once; passing that future as an argument to another task makes the second wait for the first and receive its result, and passing it in wait_for makes the second wait without receiving anything. The graph is therefore not declared in a separate structure, as in the runner of Lesson 7: it is the trace of the calls that the flow makes, which also allows loops and conditions in ordinary Python, such as one download per capture date and one extra task when with_today is true.

PieceIn flows.pyWhat it does

future as argumentload_prices.submit(s, day, raw)the load waits for raw and receives its result

The default task runner of Prefect 3 runs the submitted tasks in a pool of threads. A DuckDB connection must not be used by two threads at the same time, so each task opens its own connection through the context manager warehouse(settings) and closes it at the end. In one process, connections to the same file share one database instance, and the loads of different batches, which delete and insert different rows, do not conflict.

5. The flow of the reference package

The module below is the whole of the orchestration. Each task is a thin wrapper over a function of a layer; the options of each task, discussed in Part III, are in its decorator; and the flow reads the settings from the environment, because a deployment runs it in another process that receives only environment variables and the parameters of the deployment.

src/tcg_dataapp/flows.py
"""The pipeline of Lesson 7 as a Prefect flow.

The hand-written runner of pipeline.py ordered the tasks, retried them and
logged them. Here Prefect does those three jobs: each step is a task, the
dependencies are the futures passed from one task to the next (or wait_for),
retries and their pauses are options of the task, and every state of every
run goes to the Prefect server, which shows them in its UI. The layers below
(etls, processors, views) are the same functions of Lesson 7.

Two rules decide the options of each task:

- a task that writes to the warehouse is never cached, because skipping it
  would skip the write; it is idempotent instead, so a retry or a rerun is safe;
- the download of a past day is cached by its inputs, because the archive of
  a past day never changes, so a rerun does not download it again.
"""
from __future__ import annotations

import datetime
from contextlib import contextmanager

import duckdb
from prefect import flow, get_run_logger, task
from prefect.cache_policies import INPUTS, NO_CACHE, TASK_SOURCE
from prefect.futures import wait
from prefect.runtime import flow_run

from tcg_dataapp.config import Settings
from tcg_dataapp.etls import extract
from tcg_dataapp.etls.landing import load_batch
from tcg_dataapp.etls.tcgcsv import TcgcsvClient
from tcg_dataapp.pipeline import LOG_DDL
from tcg_dataapp.processors import gold, quality
from tcg_dataapp.views import report


def make_client(settings: Settings) -> TcgcsvClient:
    """The source; the tests replace this function with a fake TCGplayer."""
    return TcgcsvClient(settings.base_url, settings.category)


@contextmanager
def warehouse(settings: Settings):
    """One connection per task: tasks run in threads, and a DuckDB connection must not be shared between them."""
    settings.db_path.parent.mkdir(parents=True, exist_ok=True)
    con = duckdb.connect(str(settings.db_path))
    try:
        yield con
    finally:
        con.close()


def _unix(moment: datetime.datetime | None) -> int | None:
    return int(moment.timestamp()) if moment else None


def log_state(tsk, task_run, state) -> None:
    """State hook: one row of ops.pipeline_runs per task run, as the runner of Lesson 7 wrote."""
    settings = Settings()
    with warehouse(settings) as con:
        for statement in con.extract_statements(LOG_DDL):
            con.execute(statement).fetchall()
        con.execute(
            "INSERT INTO ops.pipeline_runs VALUES (?, ?, ?, ?, ?, ?, ?)",
            [str(task_run.flow_run_id).replace("-", "")[:12], task_run.name if tsk.task_run_name else tsk.name,
             task_run.run_count, state.type.value.lower(), _unix(task_run.start_time),
             extract.now_unix(), (state.message or "")[:500]],
        ).fetchall()


def not_a_quality_error(tsk, task_run, state) -> bool:
    """Retry condition: a wrong model does not become right by running again."""
    try:
        state.result()
    except quality.QualityError:
        return False
    except Exception:  # noqa: BLE001 - any other failure (network, timeout) is worth a retry
        return True
    return True


WRITES = dict(cache_policy=NO_CACHE, on_completion=[log_state], on_failure=[log_state])


@task(name="extract_sets", retries=3, retry_delay_seconds=[2, 4, 8], **WRITES)
def extract_sets(settings: Settings, captured_at: int) -> int:
    with warehouse(settings) as con:
        return extract.extract_sets(con, make_client(settings), settings.sets, captured_at)


@task(name="extract_products", retries=3, retry_delay_seconds=[2, 4, 8], **WRITES)
def extract_products(settings: Settings, captured_at: int) -> int:
    with warehouse(settings) as con:
        return extract.extract_products(con, make_client(settings), settings.sets, captured_at)


@task(name="fetch_prices_archive", task_run_name="fetch_prices_{day}", retries=3, retry_delay_seconds=[2, 4, 8],
      cache_policy=INPUTS + TASK_SOURCE, persist_result=True)
def fetch_prices_archive(base_url: str, category: int, sets: tuple, day: str) -> list[dict]:
    """Download the archive of one past day and keep the prices of the sets; no write, so it can be cached."""
    client = make_client(Settings(base_url=base_url, category=category))
    by_set = client.prices_archive(day, list(sets))
    return [price for set_id in sets for price in by_set.get(set_id, [])]


@task(name="load_prices", task_run_name="load_prices_{day}", retries=3, retry_delay_seconds=[1, 2, 4], **WRITES)
def load_prices(settings: Settings, day: str, records: list[dict]) -> int:
    with warehouse(settings) as con:
        return load_batch(con, "tcgplayer.price.v1", extract.unix(day), records)


@task(name="extract_prices_today", retries=3, retry_delay_seconds=[2, 4, 8], **WRITES)
def extract_prices_today(settings: Settings) -> int:
    with warehouse(settings) as con:
        return extract.extract_prices_today(con, make_client(settings), settings.sets, extract.today())


@task(name="build_gold", **WRITES)
def build_gold(settings: Settings) -> str:
    with warehouse(settings) as con:
        return gold.build_gold(con)


@task(name="check_quality", retries=2, retry_condition_fn=not_a_quality_error, **WRITES)
def check_quality(settings: Settings) -> dict:
    with warehouse(settings) as con:
        return quality.check_gold(con)


@task(name="freeze_reports", **WRITES)
def freeze_reports(settings: Settings) -> dict:
    with warehouse(settings) as con:
        return gold.freeze_month(con, settings.frozen_month)


@task(name="export_marts", retries=2, retry_delay_seconds=1, **WRITES)
def export_marts(settings: Settings) -> list[str]:
    with warehouse(settings) as con:
        return [p.as_posix() for p in report.export_marts(con, settings.out_dir)]


@task(name="write_report", **WRITES)
def write_report(settings: Settings, run_id: str) -> str:
    with warehouse(settings) as con:
        return report.write_report(con, settings.out_dir, run_id).as_posix()


@flow(name="tcg-dataapp", log_prints=True)
def tcg_pipeline(with_today: bool = False) -> dict:
    """Extract, load, build the gold layer, check it, freeze the month and write the reports."""
    logger = get_run_logger()
    settings = Settings()
    run_id = (flow_run.id or "local").replace("-", "")[:12]
    captured_at = extract.now_unix()
    with warehouse(settings) as con:
        for statement in con.extract_statements(LOG_DDL):
            con.execute(statement).fetchall()
    logger.info("db %s · sets %d · dates %s", settings.db_path, len(settings.sets), ", ".join(settings.price_dates))

    # the network tasks take their retries from the settings, with a pause that doubles: 2, 4, 8 s by default
    net = dict(retries=settings.retries,
               retry_delay_seconds=[settings.retry_delay * 2 ** i for i in range(max(settings.retries, 1))])

    # the catalogue: products after sets, so a missing set stops the run before 1,490 products are loaded
    sets_f = extract_sets.with_options(**net).submit(settings, captured_at)
    products_f = extract_products.with_options(**net).submit(settings, captured_at, wait_for=[sets_f])

    # the prices: the downloads depend on nothing and start at once, in parallel; each load waits for its download
    loads = []
    for day in settings.price_dates:
        raw = fetch_prices_archive.with_options(**net).submit(
            settings.base_url, settings.category, settings.sets, day)
        loads.append(load_prices.submit(settings, day, raw))
    if with_today:
        loads.append(extract_prices_today.with_options(**net).submit(settings, wait_for=[products_f]))

    # the model: one chain, and the two outputs of the checks in parallel
    gold_f = build_gold.submit(settings, wait_for=[products_f, *loads])
    quality_f = check_quality.submit(settings, wait_for=[gold_f])
    freeze_f = freeze_reports.submit(settings, wait_for=[quality_f])
    marts_f = export_marts.submit(settings, wait_for=[quality_f])
    report_f = write_report.submit(settings, run_id, wait_for=[freeze_f, marts_f])

    futures = {"extract_sets": sets_f, "extract_products": products_f, "build_gold": gold_f,
               "check_quality": quality_f, "freeze_reports": freeze_f, "export_marts": marts_f,
               "write_report": report_f}
    futures.update({f"load_prices_{d}": f for d, f in zip(settings.price_dates, loads)})
    if with_today:
        futures["extract_prices_today"] = loads[-1]
    wait(list(futures.values()))

    results, failed = {}, []
    for name, future in futures.items():
        if future.state.is_completed():
            results[name] = future.result()
        else:
            failed.append(name)
    if failed:
        raise RuntimeError(f"run {run_id} failed: {', '.join(sorted(failed))}")
    logger.info("run %s: OK · %s", run_id, results["check_quality"])
    return results


def serve(cron: str = "0 6 * * *") -> None:
    """A deployment of the flow on a schedule; needs a Prefect server (prefect server start)."""
    tcg_pipeline.serve(name="daily", cron=cron, parameters={"with_today": True},
                       description="TCGplayer prices of the 2026 sets, every day at 06:00 UTC",
                       tags=["m8-si", "lesson-8"])

At the end, the flow waits for every future and reads its final state. When any task did not complete, the flow raises an error that names those tasks, so the flow run ends Failed and its message says where the run stopped; when all completed, it returns the results of the tasks, which the command tcg-dataapp flow prints.

Part IIIFailures and cache

7. States of a task run

Prefect records every change of state of every task run in its server, and the final state of a task decides what happens downstream. A task whose upstream tasks all ended in a Completed state runs; a task with an upstream in any other state does not run and ends Pending with the type NotReady, which the log shows as Upstream task run did not reach a COMPLETED state. Cached is a Completed state whose result came from an earlier run, so it counts as success for the tasks downstream.

A task that raises an exception with retries left goes to AwaitingRetry and starts again after its pause, and the number of runs of the task grows by one at each attempt. Without retries left, it ends Failed. The distinction between Failed and NotReady matters when reading a failed run: the failed tasks are where the cause is, and the NotReady tasks are only its consequence.

8. Retries and the retry condition

A retry is worth its cost only when the cause of the failure can disappear by itself, as in a network that drops a connection or a source that answers with an error for a few seconds. The network tasks of the flow take their number of retries from TCG_RETRIES and a pause that doubles at each attempt from TCG_RETRY_DELAY, 2, 4 and 8 seconds by default, which gives a source that is restarting time to come back without delaying a run much when it does not. The tasks that build the model have no retries, because a wrong model does not become right by running again on the same data.

check_quality sits between the two cases. It can fail because the file of the warehouse is momentarily locked, which a retry solves, or because the grain broke, which a retry does not solve. The option retry_condition_fn receives the failed state and decides: the function not_a_quality_error refuses the retry when the exception is a QualityError and accepts it for any other.

the retry condition of check_quality
def not_a_quality_error(tsk, task_run, state) -> bool:

        state.result()
    except quality.QualityError:
        return False
    except Exception:
        return True
    return True

9. Cache and idempotency

A cached task does not run: Prefect computes a key from the cache policy, finds a result stored under that key and returns it. The policy INPUTS + TASK_SOURCE computes the key from the arguments of the task and from its source code, so the key changes when the date changes and also when someone edits the task, which avoids reusing a result produced by an older version of the code. The result must be persisted, with persist_result=True, for a later run to find it; by default Prefect writes it under ~/.prefect/storage.

The archive of a past day never changes, so its download is cached, and the second run of the rehearsal read the five archives from the cache instead of the network. A write is the opposite case. If the load of a day were cached, a run after the file of the warehouse was deleted would report the load as Cached and leave the table empty. Every task that writes therefore uses NO_CACHE, and what makes it safe to repeat is idempotency: load_batch replaces its batch, the dimensions keep the last version of each member, and the frozen report is created only once. Cache avoids repeating work; idempotency makes repeating a write harmless.

10. State hooks and the run log

The server of Prefect keeps the history of the runs, but the warehouse kept its own log in Lesson 7, and tcg-dataapp status reads it. The flow keeps that table through state hooks: the function log_state, attached to the tasks that write with on_completion and on_failure, receives the task, the task run and the final state, and writes one row with the identifier of the flow run, the name of the task, the number of runs of the task as the attempt, the state and the start and end in Unix time. A hook runs only on a final state, so the log has one row per task run instead of one per attempt, and a NotReady task, which never ran, has no row.

Part IVTests

12. Testing the flow without the network

The nine tests of Lesson 7 test the layers and the runner, and they keep passing. The flow has five tests of its own, which run it over the same fake TCGplayer of two sets in tests/conftest.py. Three choices make these tests isolated and fast enough. The fixture prefect_test_harness(), with the scope of the session, starts one temporary Prefect server and database for all the tests, so nothing is written to the Prefect of the user. The settings are passed by environment variables with monkeypatch.setenv, as a deployment would pass them. And the result storage of Prefect points to a temporary folder in each test, because otherwise the cache of the downloads of one test would be found by the next.

Part VDeployment and monitoring

13. Server, deployment and the serving process

Running every day without a person requires three pieces. The server keeps the state of every run in its database and serves the UI. The deployment is the record, in the server, of what to run, when and with which parameters: the deployment daily of the flow tcg-dataapp has the cron 0 6 * * * and the parameter with_today set to true. The process started by flow.serve() registers the deployment, polls the server and runs each flow run that is due, and it is the only one of the three that executes code of the DataApp; when it stops, the scheduled runs wait.

three terminals, in the folder of the project, with the virtual environment active
# 1 · the server and the UI at http://127.0.0.1:4200
prefect server start

# 2 · the deployment 'daily', served by this process (Ctrl+C stops it)
prefect config set PREFECT_API_URL=http://127.0.0.1:4200/api
tcg-dataapp serve                          # cron 0 6 * * *, with_today=True

# 3 · a run now, without waiting for the schedule
prefect deployment run 'tcg-dataapp/daily'
prefect flow-run ls --limit 5

In the rehearsal, the run triggered by hand had 18 task runs, the five downloads Cached and the prices of today added as a sixth capture: 7,782 prices, 697 cells in the cube, the same numbers as tcg-dataapp run --with-today in Lesson 7. The list of flow runs showed it Completed, followed by the next three runs of the deployment, Scheduled for 06:00 UTC of the following days.

14. The schedule and its time zone

A cron expression has five fields, minute, hour, day of the month, month and day of the week, and 0 6 * * * means minute zero of hour six of every day. The schedule of the deployment has no time zone, so Prefect reads it in UTC, and the run starts at 03:00 in São Paulo. The choice of the hour follows the source: tcgcsv publishes the archive of each day after the end of that day, so a run in the early morning finds the data of the day before complete. For a group whose partner data changes once a week, a weekly cron such as 0 6 * * 1 fits better, because a daily run would only repeat the same work.

For a demonstration in class, tcg-dataapp serve --cron "*/15 * * * *" serves the same deployment every fifteen minutes, which shows scheduled runs becoming running and completed runs in the UI during the session.

15. Monitoring in the UI

The UI of the local server, at http://127.0.0.1:4200, lists the flow runs with their states and durations, and the page of a flow run draws the graph of its task runs over a time axis, so the five downloads appear side by side and the chain of the model after them. Each task run shows its state, its number of runs and its logs, and a failed run shows the exception of the failed task and the NotReady tasks that followed it. The page of the deployment shows its schedule, its parameters and its next runs, and a run can be triggered from it with other parameters.

The UI answers the questions that the log of Lesson 7 answered only with SQL: which run failed, at which task, after how many attempts, and how long each task took. It does not replace the quality gates, which check the data; the UI shows the execution, and the gates decide whether the result can be published.

The three run the same graph, and they differ in where the graph is declared, in what must be running before the first task and in where the history is kept. Airflow was built to run many pipelines of many teams on a shared platform, which justifies a scheduler and a database that are always running. 20. Recurring mistakes of agents

The traps below were met or avoided while the flow was rehearsed on 08/11/2026, and the prompts already carry the corresponding adjustments.

One connection for every task

An agent that opens one DuckDB connection in the flow and passes it to the tasks makes threads share it, which fails at random when two tasks run at the same time. Each task opens and closes its own connection.

Cache on a write

Agents tend to add a cache to every task to make the second run faster. A cached load reports success without writing, which is invisible while the warehouse exists and wrong as soon as it is rebuilt. Only the downloads are cached.

Settings as parameters

Agents tend to pass the object Settings as a parameter of the flow, which works when the flow is called from Python. The parameters of a deployment, however, are stored in the server as JSON and validated against the signature of the flow, so the flow of the reference package receives only with_today and reads the rest from the environment, as the process that serves the deployment does.

The cache between tests

The persisted result of a download is found by the next test with the same inputs, so a test that counts downloads passes or fails depending on the order of the tests. Each test points the result storage to its own temporary folder.

Reading a failed run

A NotReady task never ran and is not a cause. The tasks that need attention are the Failed ones, whose logs carry the exception. In the version of the rehearsal, a NotReady task does not show its custom run name, so the loads that waited for a failed download appear as load_prices-c26 and not as load_prices_2026-03-01.

22. Checklist

  • The graph of the pipeline is written down, with the reason of each edge.
  • Tasks without a dependency between them run in parallel.
  • Each task opens its own connection to the warehouse.
  • Retries are set only where the cause of a failure can disappear by itself.
  • A retry condition refuses to retry a broken model.
  • Only what never changes is cached; every write is idempotent and not cached.
  • The tests run the flow on a temporary server, without network.
  • A deployment has a cron that fits the source, read in UTC.
  • A failed run can be read in the UI: the Failed task, its exception and the NotReady tasks after it.
