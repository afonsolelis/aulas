Module 8 · Information Systems · Lesson 4

Lesson plan · ETL: Object Storage to Data Warehouse

Session in which the groups build, in four rounds of prompts to a coding agent, the pipeline that extracts the Bronze layer of the pharmacy chain from a local MinIO in JSON, Parquet and CSV, conforms it with every rejected row in quarantine and loads it into a DuckDB warehouse as the Silver layer in full and incremental modes, while the slides explain each mechanism with measured examples.

About this session

ETL: Object Storage to Data Warehouse · 29/10/2026 · Prof. Afonso

Learning objective

By the end of the session, students should be able to build with a coding agent an ETL pipeline that extracts JSON, Parquet and CSV files from a local MinIO, cleans, formats, converts and enriches them with every rejected row in quarantine, and loads the Silver layer of a DuckDB warehouse in full and incremental modes, justifying each choice with measurements.

Session strategy

Practice and theory interleaved. The groups send four prompts to a coding agent (specification, extraction, transformation and load), and while the agent writes each step the professor explains its mechanism with animations and measured examples. Each round ends with a review against the expected counts, and the session closes with the verification of accounting, idempotency and privacy.

Session structure

  1. Daily — 15 min
  2. Running case, target architecture and local MinIO with the Bronze layer — 10 min
  3. Round 1: prompt for spec, plan and tasks; ETL and ELT and the Bronze to Silver contract — 15 min
  4. Round 2: prompt for the extraction; Object Storage, file formats and partitions — 17 min
  5. Round 3: prompt for the transformation; cleaning, formatting, type conversion, enrichment and quarantine — 18 min
  6. Round 4: prompt for the load; Data Warehouse and Data Lake, full and incremental loads — 20 min
  7. Verification: accounting, idempotency, privacy and lineage — 12 min
  8. Quality attribute scenarios, closing and self-study — 13 min

2. Learning objective

By the end of the session, students should be able to build with a coding agent an ETL pipeline that extracts JSON, Parquet and CSV files from a local MinIO, cleans, formats, converts and enriches them with every rejected row in quarantine, and loads the Silver layer of a DuckDB warehouse in full and incremental modes, justifying each choice with measurements.

Observable outcomes

  • Distinguish ETL from ELT by the place where the transformation runs, and explain what that place decides about computation, the content of the warehouse and the correction of a rule.
  • State what the Silver layer guarantees that Bronze does not (grain, declared types, quarantine with a reason, removal of sensitive fields and lineage) and why Bronze is read-only.
  • Explain how a query engine reads Object Storage, and why Parquet lets DuckDB read only the footer and a few column chunks while CSV and JSON are read whole.
  • Configure the readers of CSV, JSON Lines and Parquet with the options that each file does not declare about itself, reading as text and attaching the source file and the partition to every row.
  • Write the incremental extraction as an explicit list of the files of new partitions, and justify the choice with the measured requests and bytes.
  • Apply cleaning, formatting, type conversion and enrichment in SQL, in the order that keeps keys and rules comparable, with one quarantine reason per rejected row.
  • Close the accounting of rows for each entity, so that the rows left after deduplication equal the rows in Silver plus the rows in quarantine.
  • Choose among full rebuild, append, incremental merge and partition overwrite, and verify that the incremental load is idempotent and arrives at the same Silver as a full load.
  • Express the quality of the pipeline as scenarios with a stimulus, a measurable response and the evidence of the group's own run.

3. Session products

Specification of the pipeline

The files specs/spec.md, specs/plan.md and specs/tasks.md, written by the agent from prompt 1 and reviewed by the group against the facts measured in the Bronze, including the requirement that every row read ends in Silver or in quarantine.

Extraction, transformation and load

The modules src/extract.py, src/transform.py, src/load.py and src/pipeline.py with their tests, and a first full load whose counts match the verification slide: 20,891 sale lines, 3,346 stock positions and 258 deliveries in Silver.

Decision record and scenarios

The ADR docs/adr/ADR-001-full-and-incremental-load.md, comparing the two load modes with the group's own measurements, and the six quality attribute scenarios with evidence, both completed during the week before Lesson 5.

Continuity

The folder lesson_04_etl/ is the same one that Lessons 5 and 6 extend. Lesson 5 models the Silver layer as a Data Warehouse and Lesson 6 builds the cubes of the Gold layer over it, and during the week each group also points the same pipeline at a sample of the partner data.

6. Facilitation script

  1. Run the daily with the timer of slide 2 and then present the agenda of slide 3, making clear that each round starts with a prompt, continues with the explanation while the agent works and ends with a review against expected counts.
  2. Present the three sources and their defects on slide 4 and the target architecture on slide 5, then guide the setup of slide 6: the folder lesson_04_etl/, the .env ignored by Git, the MinIO started with Docker Compose, the generator and the agent opened with AGENTS.md.
  3. Read the table of slide 7 with the class and show that the planted defects are the expected result of the pipeline, ending with the accounting that the pipeline must close for sale lines, stock and deliveries.
  4. Ask the groups to send prompt 1 and, while the agent writes the specification, explain ETL and ELT with the animation of slide 9 and the comparison of slide 10, and the guarantees of the Silver layer on slide 11.
  5. Present the measurement of slide 12, in which ELT landed 1,120,749 raw lines with the CPF, and open the reflection of slide 13 on returning customers, asking which data viewpoint of Lesson 3 records the decision.
  6. Close round 1 with the synthesis of slide 14 and ask each group to answer the review questions of slide 8 before sending prompt 2.
  7. During round 2, explain the properties of Object Storage (slide 16), the reading of CSV and Parquet (slides 17 and 18) and the two measurements of slides 19 and 20, from which the rule of reading an explicit list of new files comes.
  8. Present the three engines for large volumes on slide 21 and the reflection on 300 small files a day on slide 22, then ask the groups to compare the staging counts with the generator and to check the cedilla of the supplier name.
  9. During round 3, follow the resent day of JUN-04 in the animation of slide 25, relate each transformation technique to a defect of the case on slide 26 and read the SQL of slide 27, insisting that formatting and conversion run before deduplication and validation.
  10. Compare the groups' counts by entity and reason with the table of slide 28 and open the reflection of slide 29 on the 68 lines whose products arrived late in the master file.
  11. During round 4, present lake and warehouse on slide 32, the animation of the watermark on slide 33 and the four strategies of slide 34, then read the measurement of slide 35, in which deleting and merging into the full tables cost about ten times more than rebuilding them.
  12. Present the integrity checks of slide 36 and the reflection of slide 37 on a rule that was wrong for ten days, and ask the groups to run full, generate 26/10, run incremental twice and full again.
  13. Run the verification of slide 39 on the projector and ask each group to compare its counts with the table, confirming that the second incremental run changes nothing and that no table holds a CPF.
  14. Present the six scenarios of slide 40, list on slide 41 what must exist at the end of the session and what remains for the week, and close with the self-study of slide 42.

7. Methodology

The session interleaves practice and theory inside each of the four rounds. The prompt is sent first, and the time in which the coding agent writes the files is used to explain the mechanism that those files implement, so that the explanation arrives when the group is about to review the code that depends on it. The prompts follow the CREATE structure of the module and bring facts measured in the Bronze of the lab, which makes the requirements and the tests refer to data that exists, and each round closes with review questions that the group answers before moving on.

The generator of the lab is deterministic and prints how many defects it planted, so every rule of the transformation has a count that the group can check. For this reason the verification relies on numbers rather than on the appearance of the result: the accounting of rows, the equality between the incremental and the full load and the absence of the CPF are the evidence that the agent followed the rules. The reflection slides of each block take the same pipeline to situations the lab does not cover, such as a new indicator over personal data or a rule that was wrong for ten days, and prepare the decisions that the groups will meet when they point the pipeline at the partner data.

8. Assessment of learning

Group deliverable

The session has no graded activity in class. The evidence of learning is the folder lesson_04_etl/ in the group repository, with AGENTS.md, specs/, src/, passing tests in tests/ and the ADR comparing full and incremental loads, completed by Lesson 5 on 05/11. The warehouse file and .env are not committed, because anyone rebuilds the warehouse with the generator and a full load.

The checklist of section 20 of the material states what the deliverable must satisfy:

  • .env and warehouse/ are ignored by Git, and the output of the generator is kept in the folder and referenced by the tests.
  • The specification has requirements for the accounting of rows, for the resend of JUN-04 and for the audit corrections.
  • Every staging row has source_file and ingestion_date, the supplier name keeps its cedilla and the incremental extraction reads an explicit list of files.
  • For each entity, the rows after deduplication equal the rows in Silver plus the rows in quarantine, with no dirty store code and with sold_at of BAU-05 at the local time of its text.
  • No table of the warehouse has a CPF column, quarantine included.
  • The second incremental run changes nothing, the full and incremental loads arrive at the same counts, and the ADR compares the two modes with the group's own measurements.

10. Risks and contingencies

Environment not ready at the start

The MinIO, the virtual environment or the agent may not start on some machines. The console of the MinIO can be reached through the forwarded port of a Codespace, and any coding agent serves, because the rules are the same AGENTS.md.

Agent that infers types

The agent may write the readers without options, which aborts the run on the price of SOR-03 or reads the date of BAU-05 with the month first without any error. The review of each round asks for counts and for the local time of BAU-05, and section 17 of the material lists this and the other recurring mistakes.

Rounds exceeding the time

The four prompts fit the session only if each review is short. What does not fit continues during the week with the material and the lab script; the minimum at the end of the session is the specification, the extraction and the transformation with tests passing and a first full load.

Silent encoding error in the supplier file

Read with the default encoding, the supplier name appears corrupted and nothing fails. The review of round 2 asks explicitly for the cedilla in Distribuição, so that the error is caught before the transformation.

Incremental extraction that opens every file

A filter on the partition column looks correct but, with JSON, the engine still opened every file in the measurement of slide 20. The test counts the files passed to the reader or reads the HTTP log of DuckDB.

Tests written with the lab numbers

An assertion with the number 20,891 passes on the lab data and has no meaning for the partner data. The groups compare the pipeline with the counts that the generator prints or with invariants such as the accounting of rows.
