Lesson plan · DataApp Package with Layered Architecture

Plan of the session in which the professor turns the model of Lesson 6 into an installable Python package in three layers, with an idempotent load, quality gates and a pipeline of twelve tasks with retries and a run log, built live with a coding agent, after which each student packages the DataApp of the group in the graded DataApp Packaging activity.

About this session

DataApp Package with Layered Architecture · 27/11/2026 · Prof. Afonso

Learning objective

By the end of the session, students should be able to structure a DataApp as an installable Python package in three layers (Views, Processors and ETLs), with an idempotent load, quality gates and a pipeline of tasks with dependencies, retries and a run log that goes from the extraction to the gold layer in one command, and to package the DataApp of the group in the same way.

Session strategy

Demonstration followed by a graded activity. In the first hour the professor builds the package live with a coding agent in four steps (package and layers, ETLs, processors, pipeline and views), pasting each CREATE prompt and comparing each step with the reference package, while the slides explain the concept of the step; the package then runs end to end and its tests run without the network. In the second hour each student packages the DataApp of the group in the graded DataApp Packaging activity and delivers it by pull request.

Session structure

  1. Daily — 15 min
  2. From the lab to a package; the three layers — 5 min
  3. Step 01: pyproject.toml, src layout and the layers — 8 min
  4. Step 02: ETLs and the idempotent load — 10 min
  5. Step 03: the gold layer as package data and quality gates — 8 min
  6. Step 04: pipeline, views, run and tests — 14 min
  7. Graded DataApp Packaging activity — 60 min

2. Learning objective

By the end of the session, students should be able to structure a DataApp as an installable Python package in three layers (Views, Processors and ETLs), with an idempotent load, quality gates and a pipeline of tasks with dependencies, retries and a run log that goes from the extraction to the gold layer in one command, and to package the DataApp of the group in the same way.

Observable outcomes

  • Explain why each manual step of the lab of Lesson 6 becomes a function that can run, fail, be retried and be tested when the DataApp runs every day without a person.
  • Divide a DataApp into views, processors and ETLs and justify the single direction of the imports (views → processors → etls).
  • Declare a package in pyproject.toml with src layout, dependencies, an entry point and package data, and install it in editable mode.
  • Read the settings of the DataApp from environment variables with defaults.
  • Write an idempotent load that replaces a batch identified by tag and timestamp inside one transaction.
  • Keep only the last version of each member of a dimension that is captured at every run (slowly changing dimension, type 1).
  • Write quality gates that stop the run when a tag is empty, when the grain breaks or when a price has no set.
  • Freeze the report of a month once, from the last capture of that month.
  • Order the tasks of a pipeline topologically, retry the ones that can improve, skip the dependents of a task that keeps failing and log every attempt.
  • Test the pipeline with a fake source, without the network.

3. Session products

Reference package

The package tcg-dataapp 0.1.0 of lab/lesson-7/tcg_dataapp/, whose command tcg-dataapp run executes twelve tasks in about 40 s and whose nine tests pass in about 2 s without the network.

Package of each student (graded)

The DataApp of the group packaged by each student with the same architecture, on a branch graded-activity-package/student-name and documented in a pull request whose link is submitted on Adalove by the end of the day.

Outputs of a run

The file out/report.md with the five questions of Lesson 6 recomputed at every run, three Parquet files of the marts and the log of every attempt in ops.pipeline_runs.

Continuity

Lesson 8 replaces the hand-written runner of pipeline.py with a Prefect flow, keeping the three layers unchanged, and Lesson 9 derives automated tests for the DataApp from its quality attributes.

6. Facilitation script

  1. Run the daily with the timer of slide 2.
  2. Present the agenda of slide 3, stating from the start that the second hour is the individual graded DataApp Packaging activity.
  3. Read with the class the table of slide 4, asking which manual step of Lesson 6 each module of the package replaces, and present on slide 5 the three layers and the reason for a single direction of imports.
  4. Open the lab of slide 6 and show the path of the data from the requests to tcgcsv.com to the files of out/, which the next four steps build.
  5. Paste prompt 01, approve the plan of the agent and, while it writes, explain on slide 8 the pieces of pyproject.toml; review the install in a new virtual environment and the docstring of each layer.
  6. Paste prompt 02 and, while the agent writes the ETL layer, explain on slide 10 the batch as the unit of load, the timestamp of noon UTC for the prices of today and the open results of DuckDB 2.0; review the five counts of prices and the test of a batch loaded twice.
  7. Paste prompt 03 and explain on slide 12 the dimension that keeps the last version, the quality gates and the report frozen once; compare the first and the second run in the table of the slide.
  8. Paste prompt 04 and present on slide 14 the graph of twelve tasks, the retries, the skips and the run log, stressing that the gold layer and the checks are not retried.
  9. Run tcg-dataapp run end to end, read the output of slide 15 and run pytest, reading on slide 16 what each of the nine tests proves.
  10. At 15:00, present slide 17 and the statement of the activity on Adalove: individual work on the branch graded-activity-package/student-name, a pull request with the documentation of the package, and only the link submitted by the end of the day.
  11. Circulate among the students, checking first that the package installs, that the layers respect the direction of imports and that the tests do not use the network.
  12. Close by pointing to the self-study of slide 18 and to Lesson 8, which replaces the runner with Prefect.

7. Methodology

The first hour is a demonstration in which the professor builds the package with a coding agent in four steps, each opened by a CREATE prompt that carries the numbers measured in the rehearsal and closed by a review against the reference package. The time in which the agent plans and writes is used to explain the concept of the step, such as the editable install, idempotency or the quality gate, so that each idea is presented next to the code that implements it. Because the package automates the model that the class already built by hand in Lesson 6, the attention of the class goes to the engineering decisions of a daily run and not to the model itself.

The second hour is the graded activity, in which each student applies the same architecture to the DataApp of the group with the prompts adapted to the partner data. The activity is individual so that each student is accountable for a package that installs, loads idempotently and is tested without the network, and the pull request documents the decisions in a form that the professor can review. The prompts ask the agent to show its plan before editing, which gives the student a point at which to check the direction of the layers and the behaviour of a rerun before the code is written.

8. Assessment of learning

Graded DataApp Packaging activity

The main evidence of learning is the DataApp Packaging activity, done individually in the second hour. Its statement and its criteria are those published on Adalove and are not kept in this public repository.

As presented on slide 17, the activity asks each student to package the DataApp of the group with the architecture of the session: three layers in one direction, an installable package with a command, an idempotent load of the partner data, the gold layer that the group built in Lesson 6 and tests that run without the network. The work is delivered on the branch graded-activity-package/student-name, documented in a pull request whose link is the only thing submitted, by Friday, 27/11/2026, the day of the session.

10. Risks and contingencies

Agent slower than the slot of the step

The reference package has every file of each step, which can be copied so that the demonstration keeps its time; the output of the agent is compared with it afterwards.

tcgcsv.com unavailable during the demonstration

The run of slide 15 and the lab of slide 6 show the result recorded in the rehearsal, and the nine tests run without the network, so the behaviour of the pipeline can still be shown.

Errors that appear only on the second run

Loading the prices of today with the moment of the run, or reading every version of the catalogue in the dimensions, passes the first run and breaks the second. The test that runs the pipeline twice exposes both, and the professor asks the students to run their package twice before opening the pull request.

DuckDB 2.0 and open results

A result of execute() left unread makes the next statement fail with a ResourceInUse error; the package reads every result through the function run(con, sql), which the students should keep in their own package.

Inverted layers or tests that use the network

Agents tend to import a report from the extraction and to call the network inside the tests. The prompts ask for a fake client and for each layer to declare what it may import, and the professor checks both while circulating.

Student without the gold layer of the group

The student uses the gold layer of the group as it stands at the start of the session and records in the pull request what remains to be completed, so that the structure of the package can be delivered on time.

11. Closing

The session closes with the opening of the pull requests of the graded activity and with the self-study of the week on the medallion architecture and on Python packaging. The checklist of the material summarises what the class should retain: the package installs and has a command, each layer imports only from the layers below it, the settings come from environment variables, every load replaces its batch, the dimensions keep the last version of each member, a quality gate stops the run when the grain breaks, a frozen report is created once from the last capture of its month, every attempt of every task is logged in Unix time, and the tests run without the network.

Lesson 8 takes the package of each group as its starting point and replaces the hand-written runner with an orchestrator.
