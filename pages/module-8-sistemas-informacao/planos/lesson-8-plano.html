Lesson plan · DAG Automation

Plan of the session in which the professor turns the hand-written runner of the tcg-dataapp package into a Prefect 3 flow, live and with a coding agent, with downloads in parallel, retries and a cache chosen task by task, tests on a temporary server and a scheduled deployment visible in a UI, after which each group orchestrates its own DataApp in the same way.

About this session

DAG Automation · 02/12/2026 · Prof. Afonso

Learning objective

By the end of the session, students should be able to structure the pipeline of a DataApp as a DAG in Prefect, with tasks and flows whose dependencies are explicit, choose for each task its retries, retry condition and cache policy, test the flow without the network, and schedule it as a deployment monitored in the Prefect UI.

Session strategy

Demonstration followed by group work. In the first hour the professor turns the hand-written runner of the tcg-dataapp package of Lesson 7 into a Prefect 3 flow, live and with a coding agent, in four steps guided by CREATE prompts (tasks and flow, failures and cache, tests, deployment), and compares each step with the reference package 0.2.0 and with the numbers measured in the rehearsal. In the second hour each group orchestrates the DataApp it packaged in Lesson 7 with the same method, writing the graph of its tasks, the options of each task with their reasons, tests with a fake source and a scheduled deployment.

Session structure

  1. Daily — 15 min
  2. From a runner to an orchestrator; the pipeline as a DAG — 7 min
  3. Step 01: tasks, flow and futures; the downloads in parallel — 10 min
  4. Step 02: retries, retry condition, cache and idempotency, state hooks — 10 min
  5. Step 03: tests with prefect_test_harness — 6 min
  6. Step 04: deployment with cron, local server and UI; comparison with Airflow — 12 min
  7. Second hour: each group orchestrates its DataApp with Prefect (prompt 05) — 60 min

2. Learning objective

By the end of the session, students should be able to structure the pipeline of a DataApp as a DAG in Prefect, with tasks and flows whose dependencies are explicit, choose for each task its retries, retry condition and cache policy, test the flow without the network, and schedule it as a deployment monitored in the Prefect UI.

Observable outcomes

  • List the jobs that the runner of Lesson 7 did by hand and the ones that an orchestrator adds, such as parallelism, a cache, a schedule and a UI.
  • Represent a pipeline as a directed acyclic graph and identify a false edge and its cost in time.
  • Wrap the functions of the three layers in Prefect tasks and submit them in a flow whose edges are built by futures and wait_for.
  • Open one DuckDB connection per task, because tasks run in threads.
  • Read the states of a task run (Completed, Cached, AwaitingRetry, Failed, NotReady) and explain what each one means for the tasks downstream.
  • Choose retries and a pause only for tasks that can fail for an external reason, and a retry condition that refuses to retry a broken model.
  • Cache only what never changes, such as the archive of a past day, and keep every write idempotent and uncached.
  • Test the flow on a temporary server with prefect_test_harness and a fake source injected by monkeypatch.
  • Serve a deployment with a cron, read in UTC, and follow its runs in the UI of the local server.
  • Compare the runner of Lesson 7, Prefect 3 and Apache Airflow in how the graph is declared, what must run before the first task and where the history is kept.

3. Session products

Reference flow

The package tcg-dataapp 0.2.0 of lab/lesson-8/tcg_dataapp/, whose flow runs 17 task runs in about 9 s of tasks, against about 40 s of the runner of Lesson 7, and whose 14 tests pass in about 13 s without the network.

Flow of each group

The file docs/dag.md with the graph of the pipeline of the group and the reason of each edge, flows.py over the existing layers, the options of each task with their reasons and tests/test_flows.py with a fake source.

Deployment of each group

A deployment served with a cron that fits the partner data, with one run triggered and seen in the UI, and the cron chosen recorded with its reason.

Continuity

The activity of the second hour is not graded; its tests and its graph are the starting point of Lesson 9, the graded Automated Testing activity, in which each student derives quality scenarios of the DataApp with the ATAM and turns them into test cases.

6. Facilitation script

  1. Run the daily with the timer of slide 2.
  2. Present the agenda of slide 3 and the starting point: a copy of the package of Lesson 7 with Prefect installed.
  3. Read the table of slide 4 with the class, asking which jobs of the runner were written by hand and which an orchestrator adds.
  4. On slide 5, present the pipeline as a directed acyclic graph and ask the class to find the edge of Lesson 7 that no price needed, before showing that removing it lets the five downloads start at once.
  5. Paste prompt 01, approve the plan of the agent and, while it writes, explain on slide 7 how a future passed to another task creates an edge and why each task opens its own DuckDB connection.
  6. Run tcg-dataapp flow and compare the result on slide 8 with the runner, checking that the five downloads start in the same second and that check_quality still gives 5,951 rows for 5,951 keys and 524 cells.
  7. Paste prompt 02 and present on slides 10 and 11 the states of a task run and the rule that downloads are cached and writes are idempotent.
  8. Run the three runs of slide 12: the first, the second with the downloads Cached, and the run with TCG_BASE_URL=https://tcgcsv.invalid, reading in the log the retries, the Failed tasks and the NotReady tasks downstream.
  9. Paste prompt 03, run the 14 tests and explain on slide 14 why the settings come from the environment and why each test points the result storage to its own folder.
  10. Paste prompt 04, start the server, the serving process and a run triggered by hand in three terminals, and show in the UI the graph of the run, its 18 task runs and the next three runs Scheduled at 06:00 UTC.
  11. Present the comparison of slide 17 and the reason for using Prefect in this module.
  12. At 15:00, present slide 18 and prompt 05, asking each group to write the graph in docs/dag.md before any code, and to answer the four questions of the slide.
  13. Circulate among the groups, checking first that every write is uncached and idempotent, that retries are set only where the cause can disappear by itself and that the credentials stay in environment variables.
  14. Close with the link to Lesson 9 and the self-study of slide 19.

7. Methodology

The first hour is a demonstration in which the professor turns the runner of the package of Lesson 7 into a Prefect flow with a coding agent, in four steps opened by CREATE prompts and compared with the reference package 0.2.0 and with the numbers measured in the rehearsal. Since the three layers of the package stay unchanged, each step isolates one concern of orchestration (the graph, the behaviour under failure, the tests and the schedule), and the time in which the agent works is used to present the concept that the step implements. The three runs of step 02 make the states of a task run observable, so the class sees a retry, a cache hit and a task that never ran before it is asked to choose these options for its own pipeline.

The second hour transfers the method to the DataApp of each group. Prompt 05 asks first for the graph with the reason of each edge, because false edges and tasks that can run in parallel appear only when the graph is written down, and then for the options of each task with a reason, in the terms of retries, retry conditions and cache presented in the first hour. The activity is not graded, and its tests and graph are reused in Lesson 9, which gives the group a reason to finish them.

8. Assessment of learning

Work of the groups (not graded)

The session has no graded activity. The evidence of learning is what each group produces with prompt 05: the graph of its pipeline with the reason of each edge, the flow over the existing layers, the options of each task with their reasons, the tests with a fake source and a deployment with one run seen in the UI.

The professor reviews the work against the four questions of slide 18 and the checklist of the material.

  • Which edge of the graph of the group is false, and what does it cost?
  • Which task writes, and is it idempotent?
  • Which failure is worth a retry, and which is not?
  • How often does the source of the partner change, and does the cron of the deployment follow it, read in UTC?

10. Risks and contingencies

Agent slower than the slot of the step

The reference package 0.2.0 has the files of each step, which can be copied so that the demonstration keeps its time, and the lab of the session replays the four steps in the browser.

Network or tcgcsv.com unavailable

The lab shows the runs recorded in the rehearsal, and the tests of step 03 run without the network, so the behaviour of the flow can still be shown and discussed.

Connection shared between tasks

An agent that opens one DuckDB connection in the flow and passes it to the tasks makes threads share it, which fails at random. The prompt asks for one connection per task, and the review of step 01 checks it.

Cache added to every task

Agents tend to cache every task to make the second run faster, which makes a load report success without writing. The professor checks that only the downloads are cached in the flow of each group.

Settings passed as parameters of the flow

The parameters of a deployment are stored as JSON and validated against the signature of the flow, so the flow should receive only simple parameters and read the rest from the environment, as the reference package does.

Local server that does not start

tcg-dataapp flow starts a temporary server by itself, so the flow can still run; the deployment is then demonstrated with the lab and with the output recorded in the material.

11. Closing

The session closes with the four questions of the second hour and the self-study of the week on directed acyclic graphs and on Prefect. The checklist of the material summarises what the class should retain: the graph is written down with the reason of each edge, independent tasks run in parallel, each task opens its own connection, retries are set only where the cause of a failure can disappear by itself, a retry condition refuses to retry a broken model, only what never changes is cached, the tests run the flow on a temporary server without the network, the cron of the deployment fits the source and is read in UTC, and a failed run is read in the UI from its Failed task.

The flow, the graph and the tests of each group are taken to Lesson 9, on the following day, as the starting point of the graded Automated Testing activity.
