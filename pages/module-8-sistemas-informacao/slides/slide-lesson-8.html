0:18 · Theory
A pipeline is a directed acyclic graph

Each task is a node, and each edge says that one task needs the output of another. The graph is directed, because a dependency has a sense, and acyclic, because a task cannot wait for itself. Two tasks without a path between them can run at the same time.

Directed

The edge has a sense

build_gold needs every price loaded; nothing in the loads needs the gold layer. The edge goes from the load to the model and never back.

Acyclic

No task waits for itself

A cycle has no first task, so it cannot start. The runner of Lesson 7 refused it before running; Prefect cannot even express it, because a future exists only after its task was submitted.

Only true edges

A false edge costs time

In Lesson 7 each price waited for the products, which no price needs. Without that edge, the five downloads start at once, and the run falls from about 40 s to about 9 s of tasks.

Step 01 · Theory
Tasks, flows and futures in Prefect 3

A flow is a Python function decorated with @flow, and a task is a function decorated with @task. Calling .submit() on a task returns a future at once, and passing that future to another task is what creates the edge of the graph.

PieceIn flows.pyWhat it does
@taskten tasks, one per stepa unit with its own state, retries and cache
@flowtcg_pipeline(with_today)the run: parameters, logs, final state
.submit()every task of the flowsends the task to the task runner and returns a future
future as argumentload_prices.submit(s, day, raw)the load waits for raw and receives its result
wait_for=[...]build_gold, write_reportan edge without data: wait, but receive nothing
wait()end of the flowwaits for every future before reading the states
flows.py · the edges
sets = extract_sets.submit(s, now)
prods = extract_products.submit(
    s, now, wait_for=[sets])
loads = []
for day in s.price_dates:
    raw = fetch_prices_archive.submit(
        s.base_url, s.category,
        s.sets, day)
    loads.append(
        load_prices.submit(s, day, raw))
gold = build_gold.submit(
    s, wait_for=[prods, *loads])
Threads and DuckDBThe default task runner of Prefect 3 runs tasks in threads. A DuckDB connection must not be shared between threads, so each task opens its own with warehouse(settings); in one process they share the same database, and the loads of different batches do not conflict.

Step 02 · Theory
Every task run passes through states

Prefect records each change of state of each task run in its server. The final state decides what the tasks downstream do: they run only after a Completed state, and after any other they end NotReady without running.

Completed · Cached

The task delivered a result

Cached is a Completed state whose result came from an earlier run with the same cache key. Downstream, both count as success.

Retrying · Failed

The task raised an exception

With retries left, the run goes to AwaitingRetry and starts again after the pause; the source of the rehearsal was retried after 1 s and 2 s. Without retries left, it ends Failed.

NotReady

The task never ran

Its upstream did not complete, so it stays Pending with the type NotReady. In the rehearsal, a source down left the eleven tasks downstream NotReady and wrote nothing.

A retry conditionretry_condition_fn receives the failed state and decides whether a retry can help. check_quality retries a broken connection, but not a QualityError: a grain that broke breaks again on the same data.
Step 02 · Theory
Cache the downloads, never the writes

A cached task does not run: its result is read from the result storage. That saves the download of an archive that cannot change, and it would also skip a write that the warehouse needs, which is why the two rules below go together.

TaskWrites?OptionReason
fetch_prices_<day>nocache_policy=INPUTS + TASK_SOURCE, persist_result=Truethe archive of a past day never changes; a change in the code of the task invalidates the cache
load_prices_<day>yesNO_CACHE, 3 retriesload_batch replaces the batch, so repeating it is safe
extract_prices_todayyesNO_CACHE, network retriestoday's prices change during the day
build_gold, freeze_reports, write_reportyesNO_CACHE, 0 retriesa wrong model does not become right by running again
Cache and idempotency are different answersIdempotency makes a repeated write harmless; cache avoids repeating work. If the warehouse file is deleted, a cached load would report success and leave the table empty. The downloads are cached and the loads are idempotent.

0:55 · Comparison
Prefect, Airflow and the runner of Lesson 7

The three run the same graph. They differ in how the graph is declared, in what must be running before the first task, and in where the history is kept.

Runner of Lesson 7Prefect 3Apache Airflow
the grapha list of tasks with names of dependenciesPython calls; the graph appears as the flow runs, so loops and if are alloweda DAG file parsed by the scheduler; operators or the TaskFlow API
to run oncethe commandthe function; a temporary server starts by itselfa scheduler, a metadata database and an executor
schedulecrontab, outside the codethe deployment, separate from the flowpart of the DAG definition
passing dataa shared contextresults of futures, in memory or persistedXCom, meant for small values
history and UIa table and statusserver with UI; Prefect Cloud as a serviceweb server with UI; managed services in the clouds
Why Prefect in this moduleThe DataApp is a Python package that already runs on a laptop. Prefect adds the orchestration without a change in the layers and without infrastructure to install before the first run, which suits a pipeline of one team; Airflow suits many pipelines of many teams on a shared platform.

About this session

DAG Automation · 02/12/2026 · Prof. Afonso

Learning objective

By the end of the session, students should be able to structure the pipeline of a DataApp as a DAG in Prefect, with tasks and flows whose dependencies are explicit, choose for each task its retries, retry condition and cache policy, test the flow without the network, and schedule it as a deployment monitored in the Prefect UI.

Session strategy

Demonstration followed by group work. In the first hour the professor turns the hand-written runner of the tcg-dataapp package of Lesson 7 into a Prefect 3 flow, live and with a coding agent, in four steps guided by CREATE prompts (tasks and flow, failures and cache, tests, deployment), and compares each step with the reference package 0.2.0 and with the numbers measured in the rehearsal. In the second hour each group orchestrates the DataApp it packaged in Lesson 7 with the same method, writing the graph of its tasks, the options of each task with their reasons, tests with a fake source and a scheduled deployment.
