0:15 · Why automated tests
Why a DataApp needs automated tests

A DataApp runs every day without a person. Each claim that someone checked once by reading a result (the grain holds, a rerun duplicates nothing, a frozen report never changes) must become code that checks it at every change, or it stops being true without anyone noticing.

Regression

What worked keeps working

The nine tests of Lesson 7 run in two seconds at every change; a change that breaks the idempotent load fails before it reaches the main branch.

Specification

The test states the rule

test_a_month_with_two_captures_freezes_only_the_last is the semi-additive rule of Lesson 6, written so that a machine can check it.

Design

Testable code is decoupled code

The fake source of the tests exists because the ETL layer receives its client as a parameter; a layer that opened the network by itself could not be tested offline.

The question of this sessionLesson 7 wrote tests for the behaviours the professor remembered. Which behaviours does the partner depend on, and which of them are tested? The ATAM answers this question systematically.
0:18 · Levels of test
Levels of test, from one function to the whole run

The test pyramid orders the tests by the size of what they exercise. The lower the level, the faster the test and the more precisely a failure points to its cause; the higher the level, the closer the test is to what the user sees.

LevelExercisesIn the reference packageTime
unitone function, without I/Oorder() rejects a cycle; freeze_month rejects a month that is not YYYY-MMmilliseconds
integrationone layer with a real DuckDB in memorya batch loaded twice is replaced; the gates of check_goldtens of ms
contractthe shape of an output that others readthe Parquet marts against docs/contracts/marts.jsontenths of a second
end to endthe whole pipeline with a fake sourcea full run, a rerun, a source down, a renamed fieldtenths of a second
performancea measure of time under a given volume100,000 synthetic prices from build_gold to write_reportabout 1.3 s
A data pipeline also tests its dataThe quality gates of Lesson 7 are tests that run in production on every run; the tests of this session check that those gates stop the run when they must.
0:21 · pytest
pytest: Arrange, Act, Assert, fixtures and markers

Each test prepares a situation, performs one action and checks its outcome. pytest finds the functions named test_*, injects the fixtures they ask for and reports each failure with the values that differed.

tests/scenarios/test_correctness.py
@pytest.mark.scenario("S04")                      # marker
def test_s04_renamed_price_field_stops_the_run(settings):  # fixture
    """TC04.1 a renamed price field stops the run"""
    prices = copy.deepcopy(PRICES)                # Arrange
    for rows in prices["2026-09-01"].values():
        for r in rows:
            r["market_price"] = r.pop("marketPrice")
    ctx = pipeline.run(settings,                  # Act
                       client=FakeClient(prices=prices))
    assert "check_quality" in ctx.results["_failed"]   # Assert
ResourceUse
fixturethe environment of the scenario: settings with a temporary folder; no_network, applied to every test
parametrizethe same test over several stimuli
markerscenario("S04") ties the test to its scenario
monkeypatchreplaces the clock or an environment variable
--junitxmlthe report that a CI server reads
0:25 · The ATAM
The ATAM in six steps, from drivers to findings

The Architecture Tradeoff Analysis Method, of the Software Engineering Institute, evaluates an architecture against the quality attributes that its business drivers require. This session condenses it into six steps, each one producing a file of the repository.

01Business driverswhat the partner needs; the quality attributes that follow
02Utility treeattributes, refinements and leaves rated (I,D)
03Scenarioseach leaf in six parts, with a measurable response
04Test caseseach scenario as one to three verifiable cases
05Testseach case as a pytest function, run on the code as it is
06Findingsrisks, non-risks, sensitivity points and tradeoffs
What changes in relation to an ATAM with stakeholdersThe original method gathers architects and stakeholders for days and evaluates by analysis. Here the analysis is checked by execution: a scenario whose response is not measured by a test stays a hypothesis.
0:28 · Utility tree
Leaves rated by importance and difficulty

The root is the utility of the system. Each leaf is a concrete scenario rated twice, from H to L: how much the business drivers depend on it, and how hard it is for the architecture to achieve it. Leaves rated (H,H) and (H,M) are analysed and tested first.

0:35 · Findings
What the results say about the architecture

The ATAM does not end in a list of passed tests. Each result is read back into the tree and classified, so that the next decision of the team is based on the risks it found and on the tradeoffs it accepted.

Risk

A decision that may prevent a response

The inner join of gold.fact_price drops a price whose product is not in the catalogue, and no check notices (S03).

Non-risk

A decision shown to be sound

Reading the JSON by field name makes a new field of the source change no number (S04, TC04.2).

Sensitivity point

A parameter on which a response depends

The timestamp of noon UTC decides what is the same batch; another hour breaks the idempotency of S01.

Tradeoff

One attribute improves, another worsens

A stricter quality gate publishes fewer wrong numbers and causes more failed runs: correctness against availability (S02 to S04).

Prompt 03 · CREATE 
[C] Character
You are the same architect. The utility tree and the order of analysis are
in docs/utility_tree.md and docs/scenarios.toml.

[R] Request
For every leaf rated (H,H), (H,M) or (M,H), and then for as many of the
others as time allows, write the quality attribute scenario in six parts
in docs/scenarios.toml:
- source: who or what generates the stimulus;
- stimulus: the event that reaches the system;
- artifact: the part of the DataApp that receives it (a file, a table,

- response: what the DataApp must do;
- measure: how the response is measured, with a number or a

Step 05 · 1:20 · Tests · alone

Implement the tests and run them on the code as it is

The suite is written in Arrange, Act, Assert, with the traceability plugin of the reference. It runs first on the code as it is: a failing test at this point is a finding about the architecture.

Produces

tests/scenarios/, the plugin and the fixture without network in conftest.py, the marker in pyproject.toml, out/junit.xml.

Done when
  • Does pytest end with the table "ATAM traceability"?
  • Was the first run kept, with its failures?
  • Does python tools/traceability.py print the tree?
Prompt 05 · CREATE 
[C] Character
You are the same test engineer. The test cases are in docs/test_cases.md.

[R] Request
1. Copy into tests/conftest.py the traceability plugin of the reference
   package (lab/lesson-9/tcg_dataapp/tests/conftest.py, section
   "traceability"), the fixture that blocks the network, and adapt the
   fake source to the data of the DataApp.
2. Register the marker in pyproject.toml:
   markers = ["scenario(id): the ATAM scenario of docs/scenarios.toml
   that the test covers"] and addopts = "--strict-markers".
3. Implement each test case as one function in tests/scenarios/, marked
   with @pytest.mark.scenario("Sxx") and with the id of the test case as
   the first line of its docstring, following Arrange, Act, Assert.
4. Run pytest against the code AS IT IS, without fixing anything, and
   keep the output: the passed and failed tests and the table "ATAM
   traceability".
5. Run pytest --junitxml=out/junit.xml and
   python tools/traceability.py (copied from the reference).

[E] Example
@pytest.mark.scenario("S04")
def test_s04_renamed_price_field_stops_the_run(settings):
    """TC04.1 a renamed price field stops the run"""
    prices = rename(PRICES, "marketPrice", "market_price")            # Arrange
    ctx = pipeline.run(settings, client=FakeClient(prices=prices))   # Act
    assert "check_quality" in ctx.results["_failed"]                 # Assert

[A] Adjustments
- A failing test is a result, not a bug of the test: do not change the
  assertion to make it pass, and do not fix the DataApp in this step.
- Use fixtures for the environment and parametrize for variations of the
  same stimulus.
- The whole suite must run without the network.

[T] Type of output
The tests, the output of pytest with the traceability table, and the
utility tree printed by tools/traceability.py.

[E] Extras
Show the plan before editing. Record this prompt in docs/prompts.md.
Stop at the end.

About this session

Automated Testing · 03/12/2026 · Prof. Afonso

Learning objective

By the end of the session, students should be able to derive the automated tests of a DataApp from its quality attributes with the ATAM, building the business drivers, a rated utility tree and quality attribute scenarios in six parts, implementing test cases traced to the scenarios as pytest tests in Arrange, Act, Assert, and reading the results back into the tree as risks, non-risks, sensitivity points and tradeoffs.

Session strategy

Short exposition followed by individual work graded in class. In 25 minutes the professor presents automated testing with pytest (levels of test, Arrange, Act, Assert, fixtures, parametrize and markers) and the ATAM, applied in full to the package of Lesson 7, whose first run failed 5 of 29 tests in three scenarios. Each student then applies the six steps alone to the DataApp of the group, with the CREATE prompts of the lab and a coding agent, while the professor circulates; this work is the in-class graded activity, whose statement and criteria are delivered in class.

Session structure

  1. Daily — 15 min
  2. Automated tests, levels of test and pytest — 10 min
  3. The ATAM: drivers, utility tree, six-part scenarios and findings; the reference — 15 min
  4. Steps 01–02 alone: drivers, attributes and utility tree — 15 min
  5. Step 03 alone: scenarios in six parts — 15 min
  6. Steps 04–05 alone: test cases, tests and first run — 35 min
  7. Step 06 alone: findings, second run and delivery — 15 min
