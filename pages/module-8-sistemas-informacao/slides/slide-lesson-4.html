Running case · Problem
Three sources, three formats, one Silver layer

The pharmacy chain of the module has six stores and forty products. Lesson 3 defined the contracts of each layer, and this session builds the step that turns what arrived in Bronze into the conformed entities that Silver promises.

POS · JSON

Sale lines, every night

One file per day with about 1,500 lines. BAU-05 sends dates as dd/mm/yyyy, SOR-03 sends prices as text with a comma, and JUN-04 lost its connection on 17/10 and resent the whole day the next morning.

ERP · Parquet

Stock positions, every night

240 keys per day, already typed. Audits correct the count of two days earlier, and the correction arrives in a later extract. JUN-04 often closes the day without a count.

Supplier · CSV

Deliveries, every morning

Separator ;, Latin-1 encoding, Portuguese headers, decimal comma and dates as dd/mm/yyyy. Some rows arrive without a quantity.

Result of the sessionA DuckDB warehouse with the schema silver: store, product, sale_line, stock_position and delivery, each with a declared grain and its lineage, plus quarantine and load_log. Every row read from Bronze ends in one of these tables, and none of them stores the customer CPF.

Block 1 · ETL and ELT
Where the transformation runs decides five things

Both approaches extract, transform and load. They differ in the place where the transformation runs, and that place determines who pays for the computation, what the warehouse stores and how an error is corrected.

AspectETL · transform, then loadELT · load, then transform
Computationan engine outside the warehouse (Python, Spark, Dask, DuckDB)the warehouse itself, in SQL (Redshift, ClickHouse, BigQuery, Snowflake)
What the warehouse storesonly conformed dataraw data and conformed data, with the sensitive fields of the raw
Correcting a rulererun the engine from Bronze, which must still existrerun the SQL over the raw tables, without a new extraction
Fits whenthe warehouse is expensive per byte or per query, data must be masked before landing, or the logic needs code beyond SQLthe warehouse scales cheaply, analysts own the SQL (dbt), and the raw data may be kept under the same governance
Main riskthe engine becomes a second platform to operatethe warehouse becomes a lake of raw tables nobody conforms
In this sessionThe medallion architecture already keeps the raw data, in Bronze, in Object Storage. The pipeline transforms with DuckDB before the warehouse, which is ETL from the point of view of the warehouse and ELT from the point of view of the lake. The second view explains why Lesson 3 called the medallion a form of ELT.
Block 1 · Medallion architecture
What Silver guarantees that Bronze does not

A layer is defined by the guarantee it gives to the next one. The transition from Bronze to Silver is the point where data stops being what the source sent and becomes an entity the organisation can trust.

The last row is the reason why Bronze is read-only. If the pipeline altered Bronze, a wrong rule in Silver could no longer be corrected by recomputing it.

Block 2 · while the agent writes the extraction
Object Storage as the foundation of the lake

Lesson 2 of the module wrote the Parquet sample to the raw zone. The extraction now reads that kind of storage at scale, and three properties of object storage shape how it should be read.

Flat namespace

Keys, not folders

bronze/source=pos/entity=sale_line/ingestion_date=2026-10-17/batch_2300.json is one key. The slashes and the name=value segments are a convention that engines read as Hive partitions, so the layout of the keys is the index of the lake.

Whole objects

Write once, read by range

An object is replaced, never edited. Reads can ask for a byte range with the Range header, which is what lets an engine read the footer and a few columns of a Parquet file without downloading it.

Cost per request

LIST, HEAD and GET are billed

On Amazon S3 each request has a price and a latency of tens of milliseconds. Thousands of small files cost more to list and open than a few large ones with the same bytes.

Why it is the foundation of a lakeStorage is separated from computation, so DuckDB on a laptop, Spark on a cluster and Redshift Spectrum read the same objects. Capacity grows without a schema, which is why Bronze can keep every delivery. Durability is a property of the service, and the price per GB is lower than that of a database disk, which makes it cheap to keep history.

Block 2 · File formats
CSV, JSON and Parquet, read by DuckDB

Each format of the case needs different options in the reader. The options that matter are the ones that tell the engine what the file does not say about itself.

FormatWhat the file carriesWhat the reader must be toldReader in the case
CSVtext by rows; no types, no encoding, no schema beyond the headerseparator, header, encoding, decimal and date formats; read as text to avoid wrong inferenceread_csv(files, delim=';', encoding='latin-1', all_varchar=true)
JSON Linesone object per line; field names and a few types (number, string)that it is newline-delimited, and the columns, because inference from a sample fails when one terminal sends a price as textread_json(files, format='newline_delimited', columns={...})
Parquetschema, types, row groups, column chunks, min and max of each chunk, compressionnothing about the content; only the files and the partitioningread_parquet(files, hive_partitioning=true)
Lineage

filename='source_file' adds the key of the object to each row. Without it, a wrong row in Silver cannot be traced to its delivery.

Partitions

hive_partitioning=true turns ingestion_date=2026-10-17 in the key into a column of the row.

Text first

Reading as text moves every conversion to the transformation, where a failure becomes a quarantine reason instead of an aborted run.

Block 2 · Large volumes
When one machine stops being enough

The Adalove description of the session mentions Spark and Dask. Each answers the same question, what to do when the data does not fit in the memory of one process, in a different way.

DuckDB

One process, out of core

Executes in vectors of rows, in parallel threads, and spills to disk when an operator exceeds the memory limit. Fits the lab and most Silver loads up to hundreds of GB on one machine.

Apache Spark

A cluster of executors

Splits the files into partitions processed by executors on several machines. The self-study on RDDs explains the model: immutable partitions, lazy transformations and recomputation from lineage after a failure.

Dask

Pandas in partitions

Splits a dataframe into many pandas dataframes and schedules them on threads, processes or a cluster. Fits teams whose code is already pandas.

What changes with scaleWhat does not change
the number of machines, the size of the partitions, the cost of moving data between them (shuffle) in deduplications and joinsthe contract of Silver, the rules of the transformation, the accounting of rows and the idempotency of the load; the specification written in round 1 is valid for any of the three engines

Block 3 · Transformation techniques
Four techniques, each tied to a defect of the case

The Adalove description lists cleaning, formatting, type conversion and enrichment. In the case each technique answers a defect that the generator planted, and each defect has a count that the test can check.

Cleaning

Nulls, invalid values, duplicates

Duplicates are removed by key with a rule for which copy wins. Invalid values go to quarantine. A null is kept when it means "not measured": imputing zero to the 130 missing counts of JUN-04 would invent 130 stock-outs.

Formatting

Dates, numbers, strings

One representation per concept: store codes in upper case without spaces, one timestamp type in local time, prices with a decimal point. Formatting comes before any join or comparison.

Type conversion

Text to declared types

try_cast returns NULL instead of an error, which turns a bad value into a quarantine reason. A plain CAST would abort the run on the first price written as text.

Enrichment

Metadata and derived fields

Lineage columns, the store_id found from the code, line_amount, sold_date and is_stockout. Derived fields that every consumer would compute are computed once.

Order of the rulesFormatting and conversion run before deduplication and validation, because the key and the rules compare formatted values. A rule on the store code that ran before upper(trim()) would send 2,070 valid lines to quarantine.
Block 3 · The rules in SQL
One query that types, deduplicates and classifies
DuckDB · src/transform.py · sale lines
WITH typed AS (
  SELECT r.sale_id, s.store_id, r.terminal_id,
         try_cast(r.product_id AS INTEGER)                          AS product_id,
         try_cast(r.quantity AS INTEGER)                            AS quantity,
         try_cast(replace(r.unit_price, ',', '.') AS DECIMAL(10,2)) AS unit_price,
         coalesce(try_strptime(r.sold_at, '%Y-%m-%dT%H:%M:%S%z')::TIMESTAMPTZ
                    AT TIME ZONE 'America/Sao_Paulo',               -- ISO with offset
                  try_strptime(r.sold_at, '%d/%m/%Y %H:%M:%S'))     AS sold_at,  -- BAU-05
         r.source_file, r.ingestion_date::DATE                      AS ingestion_date,
         row_number() OVER (PARTITION BY r.sale_id
                            ORDER BY r.ingestion_date DESC, r.source_file DESC) AS rn
  FROM raw_sale r
  LEFT JOIN silver.store s ON s.store_code = upper(trim(r.store_code)))
SELECT * EXCLUDE (rn), CASE
         WHEN store_id IS NULL                       THEN 'unknown_store'
         WHEN product_id NOT IN (SELECT product_id FROM silver.product)
              OR product_id IS NULL                  THEN 'orphan_product'
         WHEN quantity IS NULL OR quantity <= 0      THEN 'invalid_quantity'
         WHEN unit_price IS NULL                     THEN 'invalid_price'
         WHEN sold_at IS NULL                        THEN 'invalid_timestamp'
       END AS reason
FROM typed WHERE rn = 1;                             -- customer_cpf is never selected

The query never loops over rows in Python. On the 1.1 million lines of the benchmark, the transformation of the three entities took 1.0 s.

Block 4 · while the agent writes the load
Data Warehouse and Data Lake in the same pipeline

The pipeline reads from a lake and writes to a warehouse. The two are complementary: the lake keeps everything that arrived, cheaply and in any format, and the warehouse serves typed tables to many concurrent queries.

AspectData Lake (MinIO, S3)Data Warehouse (DuckDB here; ClickHouse, Redshift)
Schemaon read: the reader decides the typeson write: the load fails or quarantines what does not fit
Unit of storagefiles and objectstables, columns, constraints
Updatesreplace whole objectsINSERT, UPDATE, MERGE in transactions
Who readspipelines, data scientists, enginesanalysts, BI tools, applications, through SQL
ClickHouse

Columnar and open source. Tables of the MergeTree family are sorted by an ORDER BY key and merged in the background. The key orders and indexes the data but does not enforce uniqueness, so deduplication is done in the ETL or with ReplacingMergeTree. Reads S3 directly with the s3() table function.

Amazon Redshift

Columnar, managed, massively parallel. Loads from S3 with COPY, distributes rows by a distribution key and orders them by sort keys. Primary keys are informational and not enforced, and MERGE performs the upsert of the incremental load.

Block 4 · Choosing a load strategy
Four ways of writing Silver, each with its risk
StrategyWhat it doesFits whenRisk
Full rebuildcreates the tables again from all of Bronzesmall volumes, a rule changed, or the first loadcost grows with history; must swap atomically so readers never see an empty table
Appendinserts the new rowsimmutable events that never arrive twicea resend duplicates rows; the 241 lines of JUN-04 would appear twice
Incremental merge (upsert)MERGE by key on the new partitionssources that resend and correct, as in the casedepends on a correct key and on a watermark that sees late files
Partition overwritereplaces the Silver rows of each reprocessed daydata partitioned by the same date it arrivescorrections of other days, like the audits of day − 2, are lost
Watermark

The highest ingestion_date already loaded, kept in load_log. The next run reads only what is after it.

Idempotency

Running the same input twice gives the same Silver. MERGE by key provides it; append does not.

Atomicity

One transaction per run. A failure in the third table leaves the first two as they were.

What the measurement showsThe incremental run costs the size of one day, and the full run the size of the history. Deleting row by row from tables with a primary key costs ten times more than rebuilding them, because each deletion and each merge updates the index of the key. The same index is why sale_line takes 142 MiB with its key and 23 MiB without it, and why columnar warehouses such as ClickHouse and Redshift do not enforce primary keys and leave uniqueness to the ETL.
Block 4 · Designing Silver
Tables of the Silver layer and the checks that protect them

Silver of this session is conformed, close to the shape of the sources, with each table keyed by its grain. Lesson 5 models it in Third Normal Form or Data Vault, and Lesson 6 builds the cubes of Gold on top of it.

Normalisation and denormalisation

sale_line keeps store_id and product_id and leaves names and cities in store and product, which avoids rewriting thousands of rows when a store changes name. It also keeps the derived line_amount and sold_date, a small denormalisation that every query of Gold would otherwise repeat.

Integrity checks · each must return zero rows
-- grain of stock_position
SELECT store_id, product_id, date FROM silver.stock_position
GROUP BY ALL HAVING count(*) > 1;
-- referential integrity of sale_line
SELECT sale_id FROM silver.sale_line l
ANTI JOIN silver.product p USING (product_id);
-- accounting of the last run
SELECT entity FROM silver.load_log WHERE run_id = ?
  AND rows_loaded + rows_quarantined > rows_read;
Consistency for the readerA reader of the warehouse must never see the sale lines of a run without its stock positions. Loading the three tables in one transaction gives that guarantee in DuckDB. In warehouses without multi-table transactions, the same guarantee comes from loading into staging tables and swapping them in one operation.
Block 4 · Pause for reflection
A rule was wrong for ten days

On 05/11 the team discovers that the rule of BAU-05 read dd/mm/yyyy as mm/dd/yyyy since 26/10, so sales of 05/11 were loaded as 11/05. The rule is fixed. The watermark is 05/11, so the next incremental run will not touch the ten wrong days. What should the team run?

Option A

A full load

Rebuild Silver from all of Bronze. How long does it take when the history has two years?

Option B

Move the watermark back

Set it to 25/10 and run the incremental load. Does MERGE by sale_id correct sold_at of rows that already exist?

Option C

A backfill mode

A parameter --from 2026-10-26 that reprocesses a window without moving the watermark. What does the load log record?

And Gold

Downstream

The weekly indicator of those weeks was already published. Who is told, and how does the indicator show that it changed?

Block 4 · Synthesis
Key points of block 4
  1. The lake keeps everything that arrived; the warehouse serves typed tables with constraints and transactions.
  2. The full load rebuilds, the incremental load merges the partitions after the watermark, and both must arrive at the same Silver.
  3. MERGE by the key of the grain makes the load idempotent and absorbs resends and late corrections.
  4. Constraints cost space and load time; columnar warehouses do not enforce keys, so the ETL owns uniqueness and checks it after each run.

About this session

ETL: Object Storage to Data Warehouse · 29/10/2026 · Prof. Afonso

Learning objective

By the end of the session, students should be able to build with a coding agent an ETL pipeline that extracts JSON, Parquet and CSV files from a local MinIO, cleans, formats, converts and enriches them with every rejected row in quarantine, and loads the Silver layer of a DuckDB warehouse in full and incremental modes, justifying each choice with measurements.

Session strategy

Practice and theory interleaved. The groups send four prompts to a coding agent (specification, extraction, transformation and load), and while the agent writes each step the professor explains its mechanism with animations and measured examples. Each round ends with a review against the expected counts, and the session closes with the verification of accounting, idempotency and privacy.
