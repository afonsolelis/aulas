0:15 · Why monitor a DataApp
The run log answers one run; metrics answer every run

Lesson 7 left a log of every attempt in ops.pipeline_runs, which explains a run after someone looks at it. Metrics are numbers kept over time and evaluated by a machine, so the question is asked every fifteen seconds even when nobody is looking.

0:17 · The model of Prometheus
Targets, scrapes and time series

Prometheus pulls: every fifteen seconds it reads the HTTP endpoint /metrics of each target and stores each line as a sample of a time series. A series is identified by its name and its labels, so the same name with another label value is another series.

the path of a number in this session
tcg-dataapp run ──push──▶ Pushgateway :9091 ◀─┐
                                               │ scrape every 15 s
tcg-dataapp metrics :9108 (exporter) ◀─────────┤
                                               │
                           Prometheus :9090 ───┘──▶ rules.yml ──▶ alerts
                                │
                                └──▶ Grafana :3000 (PromQL in each panel)
targetan endpoint that Prometheus scrapes; up says if the last scrape worked
seriestcg_task_rows{task="extract_sets"}: a name and its labels
samplea value and a timestamp, in Unix seconds, like every date of the module
0:19 · Metric types
Four types, chosen by how the number behaves

The type tells Prometheus and the reader how the number may change, and therefore which functions make sense over it. A counter only grows and is read with rate(); a gauge goes up and down and is read as it is.

TypeBehaviourIn tcg-dataapp
Counteronly grows, restarts at zero with the processtcg_task_attempts_total{task,status}, tcg_source_request_errors_total{endpoint}
Gaugeany value, up or downtcg_task_rows, tcg_run_success, tcg_run_last_success_timestamp_seconds, everything the exporter reads
Histogramcounts of observations per bucket, plus sum and counttcg_source_request_duration_seconds{endpoint}, buckets from 0.1 to 16 s
Summaryquantiles computed in the process itselfnot used: quantiles of a summary cannot be added across instances

Step 01 · Theory
Names, labels and cardinality

Each distinct combination of labels is a new series that Prometheus stores and indexes. A label with few values, such as the task, is cheap; a label with the run identifier or the product would create a series per run or per card, which is the classic way of bringing a Prometheus down.

tcg_task_rows{task="extract_prices_2026-11-07"} 1831.0

tcg_a prefix per application, so the names do not collide
_secondsthe unit in the name, always in base units; _total closes a counter

Step 02 · Theory
Pull for services, push for batch jobs

Pull lets Prometheus know when a target is down, because the scrape fails. A batch job has no endpoint after it ends, so the Pushgateway keeps its last values and is scraped in its place; the cost is that Prometheus can no longer tell a dead job from a quiet one, which the alert on the last success covers.

Pushgateway

pushadd, not push

A POST replaces only the metrics with the names being sent. The time of the last success is sent only after a success, so a failed run leaves it as it was; a PUT would erase it.

honor_labels

The labels of the push

Without honor_labels: true every pushed series would get job="pushgateway" and the address of the Pushgateway as instance, and the machine of the run would be lost.

Exporter

Reads, computes nothing

The collector reads db_ingestion, gold.fact_price and ops.pipeline_runs at each scrape. It reports what the pipeline already keeps, from outside the pipeline.

A finding of the rehearsalDuckDB accepts one writer process and no reader while it writes. Two of three scrapes made during a run could not open the file; the collector reports tcg_warehouse_readable 0, and the alert waits two minutes before warning.

Step 03 · Theory
Quantiles come from the buckets

A histogram does not keep the observations, only how many fell at or below each bucket bound. histogram_quantile finds the bucket where the quantile falls and interpolates inside it, so the answer is an estimate whose precision depends on the buckets chosen.

groups

p95 = 0.975 s

One request of 0.70 s, in the bucket from 0.5 to 1 s. The 95th percentile is placed at 95% of that bucket: 0.5 + 0.95 × 0.5.

archive

p95 = 3.9 s

Five archives, all between 2 and 4 s, with a mean of 2.97 s. The estimate goes towards the upper bound of the bucket.

recording rule

Computed once

tcg:source_request_duration_seconds:p95 is evaluated every 15 s and stored as a series; the dashboard reads it instead of repeating the expression.

Why there is no rate() hereA pushed histogram holds only the last run, and the next push replaces it. In a service that lives longer than the scrape, the usual form is histogram_quantile(0.95, sum by (le) (rate(…_bucket[5m]))).

Step 04 · Theory
Alert on symptoms, with a reason for each threshold

An alert calls a person, so it must describe a problem that someone has to act on. Each threshold comes from how the DataApp runs, and for: asks the condition to hold for a while before it fires, which filters one bad scrape.

AlertExpressionWhy this threshold
TcgRunFailed · criticaltcg_run_success == 0a failed run publishes nothing
TcgNoSuccessfulRun · criticallast success older than 26 ha daily run plus two hours of tolerance
TcgRunTooSlow · warningtcg_run_duration_seconds > 120three times the reference run
TcgPricesStale · warningfreshness above 36 h, for: 5mone missed day and a half
TcgGrainBroken · criticalrows ≠ keys of the grainevery sum of the cube would be wrong
TcgExporterDown · warningup == 0 or not readable, for: 2ma run holds the file for about 30 s
Who receives the alertPrometheus evaluates the rules and shows them at /alerts. Routing to e-mail or chat is the job of Alertmanager, which is the next piece of the stack and is left out of this lab.

About this session

Metrics and Telemetry · 09/12/2026 · Prof. Afonso

Learning objective

By the end of the session, students should be able to instrument a DataApp with Prometheus metrics of the appropriate types, collect them by push for batch runs and by an exporter for the state of the data, answer operational questions in PromQL, and build a Grafana dashboard and tested alerting rules for a service of the project.
