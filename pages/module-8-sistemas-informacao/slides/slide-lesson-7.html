0:17 · Architecture
Three layers, each one depending only on the layer below

A layered architecture separates what the user reads, the rules that build it and the movement of data. The dependency points one way only, so a layer can be replaced or tested without touching the layer above it.

Views

What the users read

The five questions, the report in Markdown and the Parquet files of the marts. They read the gold layer and never the landing table, so a change in the source does not reach them.

Processors

The rules of the model

The dimensions, the fact, the cube, the mart and the reports as SQL files of the package, and the checks that stop the run when the model is wrong.

ETLs

The movement of data

The client of the source, the extraction and the load into db_ingestion. Nothing is cleaned here: the record is kept as it arrived, so the model can always be rebuilt.

Why one directionIf the ETLs imported the views, a change of a report could break the extraction. With views → processors → etls, the extraction is tested alone with a fake source, and the reports are tested over a fake landing table, which is what the tests of step 04 do.

Step 02 · Theory
Idempotency: the same run twice gives the same table

A pipeline is rerun after a failure, by a scheduler or by mistake. An idempotent load makes the result independent of how many times it ran, and that is what allows a retry to be automatic.

The batch

Tag + timestamp

The records of one tag captured at one moment form a batch. load_batch deletes the batch and inserts it again inside one transaction.

The price of today

Noon UTC of the day

The prices of today are loaded with the timestamp of noon of the day, not of the run, so two runs on the same day keep one price per product.

The archive

One past day

The prices of a past date come from the daily archive of tcgcsv, a 7z file of every category, from which only the files of the seven sets are extracted.

A trap of DuckDB 2.0The result of execute() stays open until it is read, and the next statement on the same connection fails with a ResourceInUse error. The rehearsal hit it at the last task of the run; the package reads every result through a small function run(con, sql).

Step 03 · Theory
A model that runs every day

In the lab the catalogue was captured once and the model was read by a person. Running daily, the same set and product arrive again at each run, and nobody looks at the grain before the report is written.

Last version wins

Slowly changing dimension, type 1

QUALIFY row_number() OVER (PARTITION BY productId ORDER BY timestamp DESC) = 1 keeps the last version of each product. Without it, the second run doubles every price of the fact.

Quality gates

The run stops

check_gold raises an error when a tag is empty, when the grain breaks or when a price has no set. The reports that depend on it are skipped, so a wrong number is never published.

Frozen once

The last capture of the month

freeze_month creates the tables of a month only if they do not exist, from the last capture of that month, because two captures of the same card must not add up.

Step 04 · Theory
A pipeline is a graph of tasks

Each task declares the tasks it depends on, and the runner orders them so that a task starts only after all of its dependencies succeeded. A cycle or an unknown dependency is refused before anything runs.

the twelve tasks of tcg-dataapp run
extract_sets ─▶ extract_products ─┬▶ extract_prices_2026-03-01 ─┐
                                  ├▶ extract_prices_2026-05-01  │
                                  ├▶ extract_prices_2026-07-01  ├▶ build_gold ─▶ check_quality ─┬▶ freeze_reports ─┐
                                  ├▶ extract_prices_2026-09-01  │                               └▶ export_marts ───┴▶ write_report
                                  └▶ extract_prices_2026-11-07 ─┘
Retries

A failed task runs again up to TCG_RETRIES times, with a growing pause. The gold layer and the checks are not retried: a wrong model does not become right by running again.

Skips

When a task still fails, every task that depends on it is skipped and the run ends as FAILED, naming them. Nothing downstream of an error is published.

Run log

Every attempt is a row of ops.pipeline_runs, with the run, the task, the attempt, the status and the start and end in Unix time.
