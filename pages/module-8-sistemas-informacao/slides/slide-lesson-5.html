11:15 · Running case
From conformed tables to a Data Warehouse

Lesson 4 left the Silver layer of the pharmacy chain as conformed tables in a DuckDB file. That layer answers the questions of today, but it has no record of how each row arrived, no rule for how long data is kept, and no answer for the supplier that changes its file next week.

Tactical need

Purchasing asks every morning

Which lots expire in less than 90 days, store by store? The answer must come in under a second and covers recent deliveries only.

Strategic need

Data science asks once a quarter

How did 17 October of this year compare with the same day two years ago? The answer needs every year that the chain has kept, and it may run for hours.

Audit need

The partner asks after an incident

Where did this number come from, and can you rebuild it? The answer needs the source file of each record and proof that no copy was altered.

Question of the sessionHow can one Silver layer serve a query that must be fast and recent, a query that must reach decades back, and an audit that must prove every row, without keeping three different truths?
11:18 · Target architecture
One enriched table, two copies with two lifecycles

Every load writes the lake first and then loads ClickHouse from the files it has just written. ClickHouse therefore never holds a row that the lake does not hold, and it can be rebuilt from the lake at any time.

11:20 · Two lifecycles
Why the two copies keep data for different periods

The two copies answer different kinds of question, and each kind needs a different period of history and a different cost per query.

Step 01 · Theory 1
The Silver layer as a Data Warehouse

In the medallion architecture, Silver combines and cleans what arrived in Bronze and offers one corporate view of the core business entities. Inmon defined a Data Warehouse by four properties, and the Silver layer of the lab has each of them.

Subject-oriented

Organised around sales, stock, deliveries, stores and products, and not around the systems that produced them (POS, ERP, supplier).

Integrated

One store code, one date format and one decimal mark for all sources. BAU-05 dates and SOR-03 prices arrive converted.

Time-variant

Every record carries data_ingestao, so the warehouse can answer what was known at any moment, not only the current state.

Non-volatile

Loads add or replace whole files; nobody edits a row by hand. A rerun with the same Bronze gives the same Silver.

Self-service analytics

Analysts query Silver directly, because the cleaning and the integration were done once, upstream, with rules that are written down.

Foundation for Gold

The Gold layer of Lessons 6 and 7 builds marts and indicators from Silver, so an error fixed in Silver is fixed in every mart.

Step 01 · Theory 3
JSON for the content, tags for the kind

JSON lets records of different shapes share one table, and the tag says which shape each record has. Together they absorb new sources and new versions without a change of DDL.

JSON in data_linha

Flexible and still columnar

  • Holds structured rows and semi-structured payloads in the same column.
  • ClickHouse splits each JSON path into a typed subcolumn: quantity Int64, unit_price Float64, sold_at String.
  • A query reads only the paths it uses, as in any columnar table.
  • A new field is a new path, with no ALTER TABLE.
Tags in data_tag

Versioning, categorisation, filtering

  • pos.sale_line.v1 names source, entity and version of the contract.
  • A change of shape is a new version: supplier.delivery.v2.
  • Every query filters by tag first, and the table is ordered by it.
  • quarantine.v1 keeps rejected records visible, with a reason.

Step 02 · Theory 1
Three operations of enrichment

Enrichment adds to a record what it needs to be used without returning to its source. In the lab it has three operations, each measured in the Bronze of Lesson 4.

Normalise

One format and one unit

2,070 store codes trimmed and in upper case; 3,447 dates of BAU-05 converted from dd/mm/yyyy; 3,580 prices of SOR-03 converted from decimal comma; Portuguese headers of the supplier mapped to the contract.

Aggregate sources

Join what lives elsewhere

Each sale line receives city and region of the store and continuous_use of the product, which come from the master files of the ERP and not from the POS.

Derive

Fields the partner asked for

line_total = quantity × unit price for every sale line; in Step 03, days_to_expiry = expiry date − delivery date for every lot of the supplier.

Enrichment and normalisation pull in opposite directionsCopying city and region into every sale line repeats the same value 20,891 times. The enriched table accepts that repetition to answer queries without joins, and Step 04 shows the model that removes it.
Step 02 · Theory 2
The lake is written first

The order of the run decides what a failure leaves behind. Writing the lake first means that any failure afterwards leaves ClickHouse behind the lake, never ahead of it.

  1. DuckDB reads the Bronze over httpfs and builds the three columns for every tag.
  2. One Parquet file per tag and day goes to silver/enriched/, with the SHA-256 of its bytes.
  3. ClickHouse is truncated and loaded by reading those files, never the Bronze.
  4. The manifest of the run is written with status ok; if ClickHouse fails, with error_clickhouse.

Step 03 · Theory 1
Two columnar warehouses

Both store each column separately and compressed, so an analytical query reads only the columns it uses. They differ in how they are operated and paid for.

Amazon RedshiftClickHouse
Modelmanaged service of AWS, cluster or serverlessopen source server; also offered as a managed cloud
Storagecolumnar, compressed, distributed across nodes (MPP)columnar, compressed parts of a MergeTree table
Data layoutdistribution key and sort key per tablepartition key and ordering key per table
Lake accessRedshift Spectrum queries Parquet in S3s3() table function queries Parquet in S3
Semi-structuredSUPER type with PartiQLJSON type with typed subcolumns
Retentionjobs that delete or unload old dataTTL clause applied by the server during merges
In this labnot used; same role in an AWS stackthe tactical copy, in a container

The architecture does not depend on the product: the lake stays the source of truth, and the columnar engine is the fast copy that can be replaced or rebuilt.

Step 03 · Theory 2
MergeTree, partitions and TTL

Each insert writes an immutable part on disk. Background merges join parts of the same partition, and the TTL clause tells the server which rows to drop while it merges.

sql/clickhouse_enriched.sql
CREATE TABLE silver.enriched
(
    data_ingestao DateTime64(3, 'America/Sao_Paulo'),
    data_tag      LowCardinality(String),
    data_linha    JSON
)
ENGINE = MergeTree
PARTITION BY toYYYYMM(data_ingestao)  -- one month per partition
ORDER BY (data_tag, data_ingestao)    -- filter by tag first
TTL toDateTime(data_ingestao) + INTERVAL 1 YEAR;
What each clause buys
  • PARTITION BY month: a whole month expires as one unit, which makes deletion cheap.
  • ORDER BY tag and time: a query of one tag reads a contiguous range.
  • LowCardinality: seven tag values stored as a dictionary.
  • TTL: the rehearsal inserted 1,758 rows of 2024 and ClickHouse kept none, already at insert time.
Step 03 · Theory 3
Who decides how long data is kept

The TTL is one line of SQL, but the number in it carries obligations. Engineering informs the decision with cost and speed; the business makes it, and the ADR records it.

Legal and contractual

Minimum and maximum periods

Tax records, health regulation of pharmacies and the LGPD set periods that data must be kept, or must not be exceeded for personal data. That is why customer_cpf never enters the Silver layer.

Business use

How far back each decision looks

Purchasing compares weeks; a seasonal plan compares years. A window of one year serves the first and leaves the second to the lake.

Cost

Fast disk against object storage

ClickHouse keeps its data on servers that are always on; the lake keeps Parquet in object storage and pays for compute only when a job runs.

How the lab writes it"Retention of ClickHouse: 1 year. Hypothesis, to validate with the partner. Decided by the business owner of the data, informed by the measured cost of each window." The number may change; the lake keeps the history either way.

Step 04 · Theory 1
Third Normal Form

Codd's normal forms remove redundancy by making every attribute depend on the key, the whole key and nothing but the key. Each step removes one kind of anomaly that the enriched table still has.

FormRuleExample in the case
1NFatomic values, no repeating groupsone sale line per row, not a list of products per sale
2NFno attribute depends on part of a composite keyin stock (store, product, date), the product name depends only on product and leaves the table
3NFno attribute depends on another non-key attributecity and region depend on the store, not on the sale line, so they live only in store
Update anomaly

If Santos changed region, the enriched table would need 1,773 sale lines rewritten; in 3NF, one row of store.

Insert anomaly

A new store cannot appear in a table of sales until it sells something; in 3NF it exists in store from day one.

Delete anomaly

Deleting the last sale of a product would erase what is known about it; in 3NF the product survives in product.

Step 04 · Numerical example 1
The 3NF model of the case

Six views over the lake files. Each fact appears once, every foreign key resolves, and version 2 of the supplier required one new table, lot.

Step 04 · Theory 2
Data Vault: hubs, links and satellites

Linstedt designed the Data Vault for warehouses whose sources change often. It separates what identifies a business entity from how entities relate and from the attributes that describe them over time.

Hub

The business key

One row per business key: store_code, product_id, sale_id, delivery_id. It holds the hash key, load_ts and record_source, and never changes.

Link

The relationship

One row per relationship between hubs: link_sale joins sale, store and product. A new relationship is a new link, without touching the hubs.

Satellite

The attributes over time

Descriptive attributes with load_ts and a hash_diff. Rows are only inserted, so every past state remains. A new source of attributes is a new satellite.

Adaptability in dynamic environmentsHash keys let hubs, links and satellites be loaded in parallel and from different sources. When a source changes, the change stays inside one satellite, and the rest of the model keeps loading.
Step 04 · Numerical example 2
The Data Vault of the case

Eight views over the same lake files. Hubs and links did not change when the supplier sent version 2; the lot and the expiry date went into a new satellite.

Data Warehouses: the hybrid Silver layer · 05/11/2026 · Prof. Afonso

Learning objective

By the end of the session, students should be able to design the Silver layer of a Data Warehouse as an enriched table with the data_ingestao, data_linha and data_tag columns, loaded first into a long-lived lake read with DuckDB and then into ClickHouse with a one-year retention, to reconcile both copies, and to model the same data in Third Normal Form and in Data Vault, justifying the retention as a business decision.

Practice and theory interleaved.
