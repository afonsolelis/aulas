14:15 · Running case
The orders of a Brazilian marketplace

Olist connects small shops to the large marketplaces of Brazil. Its public dataset has 99,441 orders placed between September 2016 and October 2018, with the customers, sellers, products and items of each order, extracted from the transactional system without any treatment.

Tactical need

The commercial area asks every month

How many sales did each region make this month, and how does the North compare with the Southeast? The answer must come in under a second, for a dashboard.

Strategic need

Data science asks once a quarter

Is the growth of the North seasonal or structural, and which categories drive it? The answer needs every year that the platform has kept, and it may run for hours.

Audit need

The partner asks after an incident

Where did this number come from, and can you rebuild it? The answer needs the source file of each record and proof that no copy was altered.

Question of the sessionHow can one Silver layer serve a fast dashboard, a study that reaches years back and an audit that must prove every row, and how is a model of the business built on top of it to answer a question such as North against Southeast?

Step 01 · Theory 1
The Silver layer as a Data Warehouse

In the medallion architecture, Silver combines and cleans what arrived in Bronze and offers one corporate view of the core business entities. Inmon defined a Data Warehouse by four properties, and the Silver layer of the lab has each of them.

Subject-oriented

Organised around orders, items, customers, sellers and products, and not around the tables of the transactional system that produced them.

Integrated

One format for dates, one for zip prefixes and one name per category for all files. The 23,995 short zip prefixes arrive padded.

Time-variant

Every record carries data_ingestao, so the warehouse can answer what was known at any moment, not only the current state.

Non-volatile

Loads add or replace whole files; nobody edits a row by hand. A rerun with the same Bronze gives the same Silver.

Self-service analytics

Analysts query Silver directly, because the cleaning and the integration were done once, upstream, with rules that are written down.

Foundation for Gold

The star schema of Step 04 is computed from Silver, so an error fixed in Silver is fixed in every fact and every dimension.

Step 01 · Theory 3
JSON for the content, tags for the kind

JSON lets records of different shapes share one table, and the tag says which shape each record has. Together they absorb new sources and new versions without a change of DDL.

JSON in data_linha

Flexible and still columnar

  • Holds structured rows and semi-structured payloads in the same column.
  • ClickHouse splits each JSON path into a typed subcolumn: delivery_days Int64, price Float64, purchased_at String.
  • A query reads only the paths it uses, as in any columnar table.
  • A new field is a new path, with no ALTER TABLE.
Tags in data_tag

Versioning, categorisation, filtering

  • olist.order.v1 names source, entity and version of the contract.
  • A change of shape is a new version, such as olist.order_item.v2.
  • Every query filters by tag first, and the table is ordered by it.
  • quarantine.v1 keeps rejected records visible, with a reason.

Step 02 · Theory 1
Three operations of enrichment

Enrichment adds to a record what it needs to be used without returning to its source. In the lab it has three operations, each measured in the Bronze of Olist.

Normalise

One format and one unit

23,995 customer and 1,027 seller zip prefixes padded to 5 characters; every timestamp written in ISO 8601 with its offset; two misspelt headers renamed; 610 empty categories as unknown.

Aggregate sources

Join what lives elsewhere

Each order receives customer_state and customer_region from the customers file, and each product receives its category in English from the translation file.

Derive

Fields the business asked for

region from the state, delivery_days and delivered_late for every delivered order, and item_total = price + freight for every item.

Enrichment and the star pull in opposite directionsCopying the region of the customer into every order repeats the same five values 99,433 times. The enriched table accepts that repetition so that one tag answers a question without joins; the star schema of Step 04 keeps the region once, in dim_customer.
Step 02 · Theory 2
The lake is written first

The order of the run decides what a failure leaves behind. Writing the lake first means that any failure afterwards leaves ClickHouse behind the lake, never ahead of it.

  1. DuckDB reads the Bronze over httpfs, every column as text, and builds the three columns for every tag.
  2. One Parquet file per tag and day goes to silver/enriched/, with the SHA-256 of its bytes.
  3. ClickHouse is truncated and loaded with its s3() function reading those files, never the Bronze.
  4. The manifest of the run is written with status ok; if ClickHouse fails, with error_clickhouse.

Step 03 · Theory 1
Two columnar warehouses

Both store each column separately and compressed, so an analytical query reads only the columns it uses. They differ in how they are operated and paid for.

Step 03 · Theory 2
MergeTree, partitions and TTL

Each insert writes an immutable part on disk. Background merges join parts of the same partition, and the TTL clause tells the server which rows to drop while it merges.

sql/clickhouse_enriched.sql
CREATE TABLE silver.enriched
(
    data_ingestao DateTime64(3, 'America/Sao_Paulo'),
    data_tag      LowCardinality(String),
    data_linha    JSON
)
ENGINE = MergeTree
PARTITION BY toYYYYMM(data_ingestao)  -- one month per partition
ORDER BY (data_tag, data_ingestao)    -- filter by tag first
TTL toDateTime(data_ingestao) + INTERVAL 1 YEAR;
What each clause buys
  • PARTITION BY month: a whole month expires as one unit, which makes deletion cheap.
  • ORDER BY tag and time: a query of one tag reads a contiguous range.
  • LowCardinality: six tag values stored as a dictionary.
  • TTL: the server stores it as toIntervalYear(1), so a script that searches for the text INTERVAL 1 YEAR finds nothing.
Step 03 · Theory 3
Who decides how long data is kept

The TTL is one line of SQL, but the number in it carries obligations. Engineering informs the decision with cost and speed; the business makes it, and the ADR records it.

Legal and contractual

Minimum and maximum periods

Tax records set periods that sales must be kept, and the LGPD limits how long personal data may be kept. customer_unique_id, the city and the zip prefix identify a customer indirectly, so they are personal data.

Business use

How far back each decision looks

The commercial area compares months; a plan for a new region compares years. A window of one year serves the first and leaves the second to the lake.

Cost

Fast disk against object storage

ClickHouse keeps its data on servers that are always on; the lake keeps Parquet in object storage and pays for compute only when a job runs.

How the lab writes it"Retention of ClickHouse: 1 year. Hypothesis, to validate with the partner. Decided by the business owner of the data, informed by the measured cost of each window." The number may change; the lake keeps the history either way.

Step 04 · Theory 1
Dimensional modelling in four decisions

Kimball designs a model from a business process and a question, not from the tables of the source. Each decision constrains the next, and the grain is the one that is hardest to change later.

1 · Process

Selling

The process measured is the sale of the marketplace: an order placed by a customer, with one or more items from one or more sellers.

2 · Grain

One order item

Each row of the fact is one item of one order. A finer grain answers more questions; this one still lets an order be counted once with a distinct count.

3 · Dimensions

Who, what, where, when

Customer, seller, product and date describe the context of each item. Region and state live in the dimension, once per customer.

4 · Facts

What is measured

price and freight_value add across any dimension. A count of orders does not: it must be distinct, because one order has several items.

Why a star and not 3NF for this questionThird normal form removes redundancy for the systems that write the data. The star accepts some redundancy in the dimensions so that a question needs one join per dimension, which is what a dashboard and an analyst write. 3NF and Data Vault remain valid choices for the Silver layer itself.

CREATE MATERIALIZED VIEW gold.agg_sales_month_region
REFRESH EVERY 1 HOUR DEPENDS ON gold.fact_order_item
ENGINE = MergeTree ORDER BY (month, region)
AS
SELECT d.month, c.region,
       uniqExact(f.order_id) AS orders,
       count()               AS items,
       sum(f.price)          AS revenue
FROM gold.fact_order_item AS f
JOIN gold.dim_customer AS c USING (customer_id)
JOIN gold.dim_date     AS d USING (date_key)
WHERE f.order_status = 'delivered'
GROUP BY d.month, c.region;

-- How many sales were made each month in the
-- North, compared with the Southeast?
SELECT month,
       sumIf(orders, region = 'North')     AS north,
       sumIf(orders, region = 'Southeast') AS southeast,
       if(southeast = 0, NULL,
          round(100 * north / southeast, 2))
         AS north_pct_of_southeast
FROM gold.agg_sales_month_region
WHERE region IN ('North', 'Southeast')

ORDER BY month;

Data Warehouses: the hybrid Silver layer · 05/11/2026 · Prof. Afonso

Learning objective

By the end of the session, students should be able to design the Silver layer of a Data Warehouse for the Olist orders as an enriched table with the data_ingestao, data_linha and data_tag columns, loaded first into a long-lived lake read with DuckDB and then into ClickHouse with a one-year retention, to reconcile both copies, and to build over it a star schema with views and materialized views that answers how many sales the North made each month compared with the Southeast, justifying the grain, the dimensions and the retention.

Session strategy

Practice and theory interleaved. The professor builds the Silver layer and the star schema live with a coding agent in four steps (contract and decision, hybrid load, audit and lifecycle, and star schema), pasting each CREATE prompt over the raw CSV files of Olist, and while the agent works the slides explain the concept that the step implements. Each step ends with a review against counts measured in the rehearsal, and the session closes with the connection to the Data Ingestion Structure artifact.
