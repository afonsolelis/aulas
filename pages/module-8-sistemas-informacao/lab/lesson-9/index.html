ATAM tests and the GitLab pipeline

This page reproduces, in the browser, the session in which a coding agent tests the package tcg-dataapp of Lesson 7 with the method of the ATAM, and then makes the tests run on every push to the GitLab of Inteli. Six prompts go from the business drivers to the utility tree, the scenarios in six parts, the test cases, the tests and the findings; the seventh writes .gitlab-ci.yml. The panels below the editor show the utility tree with the result of each leaf, the report of each test run, and the pipelines of the merge request and of the daily schedule as GitLab presents them. Nothing runs here: the files are those of the repository, pytest ran on 12/11/2026, and the jobs of the pipelines ran on the same day in Docker, with the image and the commands of .gitlab-ci.yml.

What is real and what is simulated

The files of the editor are those of lab/lesson-9/tcg_dataapp/, and the folder starts as the package of lab/lesson-7/. Both runs of pytest are real: the first ran the tests of Lesson 9 on the code of Lesson 7, the second on version 0.3.0. Each job of the three pipelines ran in Docker on 12/11/2026, with the image, the rules, the order of stages and needs, the artifacts and the pip cache of .gitlab-ci.yml; its log is the real output of its commands. The lines of the GitLab runner around them, the output of git push and the screens of GitLab are reproductions, because the jobs did not run on a runner of git.inteli.edu.br. The agent and its messages are a staging of the session.

How to use it in class

  • Steps 01 to 04 write documents; the panel Utility tree grows with them, and a click on a leaf opens its six parts.
  • Step 05 keeps the first run, with its failures; the tree turns red where the architecture failed a scenario.
  • Step 07 shows three pipelines; click a job to read its log and press “Replay” to watch the pipeline run on its recorded clock.

Doing it for real

The README of lab/lesson-9/ lists the commands. On git.inteli.edu.br, the repository of the group needs a runner available to the project (Settings › CI/CD › Runners), the protection “Pipelines must succeed” (Settings › Merge requests) and a schedule of main (Build › Pipeline schedules). Without a runner the pipeline stays pending. The reference package passes its 29 tests in about 10 s without network.
