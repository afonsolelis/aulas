Module 5 · Software Engineering · Lesson 1

Lesson plan · Software Testing Engineering

Dialogued exposition that treats testing as the construction of evidence for the business drivers modeled by the team, moving from unit tests with AAA and parameters to black-box and end-to-end tests, realistic integrations with Testcontainers and VCR, the requirements traceability matrix and BDD in Gherkin, followed by an in-class graded activity in which each team specifies, automates and documents one test case of the project in GitLab.

2. Learning objective

By the end of the meeting, students should be able to apply the concepts of Software Testing Engineering to the project, within the scope of a risk-based test strategy, quality evidence, reliability and software test engineering.

Observable outcomes

  • Explain testing as the deliberate construction of evidence that the implemented behaviour still matches the expected behaviour defined by the business drivers.
  • Write a unit test that protects a domain rule, organised in the Arrange, Act and Assert structure.
  • Express a threshold rule as a parameterized test whose examples sit below, at and above the boundary.
  • Distinguish the white-box and black-box perspectives and reserve end-to-end tests for critical journeys, asserting business outcomes such as persisted state, emitted events and audit records.
  • Choose between mocks, Testcontainers and VCR according to the kind of confidence the test must provide.
  • Record the link between a requirement, the test that verifies it and the evidence of execution as an entry of a requirements traceability matrix.
  • Write a BDD scenario in Gherkin and explain how a library such as behave maps each step to a Python function.
  • Write a test case with objective, precondition, test procedure, expected result, obtained result and post-condition.

3. Meeting outputs

Worked examples

The credit limit rule as an AAA unit test and as a parameterized test, the password reset journey as an end-to-end test and as a Gherkin feature with behave step definitions, and the RTM with three entries.

Graded activity

One test case of the project, described in Markdown with its six fields, automated with a tool chosen by the team, linked to its requirement in an RTM entry and versioned in GitLab with at least three commits.

Submitted link

The URL of the GitLab repository that holds the Markdown report, the automated test code and the commit history of the activity.

Continuity

The test case, the RTM entry and the habit of recording evidence in the repository return in Lesson 3, where the staged Docker workflow maps each verification stage to a requirement type, and Stage 3 of that workflow runs integration tests against a real PostgreSQL container, the same kind of disposable infrastructure that Testcontainers provides.

4. Preparation

Student responsibilities

  • Read the written material of the lesson, which follows the reading guide from the meaning of testing to the graded activity.
  • Bring the business drivers and requirements already modeled by the team, since the activity starts from a requirement that matters to the project.
  • Have write access to a GitLab repository and a working environment for the chosen test tool, such as Python with pytest, requests or behave.

Instructor responsibilities

  • Publish the statement of the graded activity as written in section 13 of the material, with the expected repository contents and the minimum of three commits.
  • Prepare the code examples of the deck so that they can be shown running if the class asks for it.
  • Check that the teams know where to submit the GitLab link at the end of the activity.

6. Facilitation script

  1. Open with slide 2 and ask the class what a passing test proves, using the answers to introduce testing as evidence of expected behaviour.
  2. On slide 3, ask each team to name one critical flow, one domain rule and one operational risk of its project, which will later anchor the activity.
  3. Present the unit test as protection of a rule and read slide 5 with the class, associating fraud prevention, pricing accuracy and access control with the rule each one requires.
  4. Write the AAA example of slides 6 and 7 and ask why a test that acts several times or asserts unrelated outcomes is harder to trust.
  5. Show on slides 8 and 9 that the values 999, 1000 and 1001 were chosen because they lie below, at and above the limit, and ask the class which boundary its own project has.
  6. Contrast white-box and black-box tests on slides 10 and 11, then present end-to-end tests as a small set of critical journeys whose assertions reach state, events and audit records.
  7. Present Testcontainers and VCR as realistic alternatives for integration tests and discuss on slide 17 which assumptions a mock reproduces and which failures it hides.
  8. Build the RTM of slide 19 with the class and ask which requirement of each project still has no linked test.
  9. Read the Gherkin feature of slide 23 and show on slides 24 and 25 how behave matches each step sentence to a Python function that performs the action and the assertion.
  10. Present the six fields of a test case with the duplicate signup example, stressing that the obtained result is filled in only after execution.
  11. Read the statement of the graded activity and the submission requirements on slides 28 and 29, and follow the suggested work sequence of the material during the activity.
  12. Visit the teams during the activity, checking first whether the chosen requirement is relevant to the project and whether the automated test verifies the same behaviour as the manual test case.

7. Methodology

The meeting follows the strategy recorded for this encounter, a dialogued exposition alternated with guided application to the group project and closed with a check of understanding. Each concept of the deck is presented with a short code example drawn from two recurring cases, the credit limit rule and the password reset journey, so that the class sees the same behaviour verified at different levels: as a unit rule, as a table of boundary examples, as an end-to-end journey and as an executable Gherkin scenario.

The graded activity places the whole chain in the hands of the team. Because the team writes the manual test case before automating it, the automated test inherits an explicit objective and an expected result, and because the RTM entry and the commit history are part of the submission, the activity verifies the link between requirement, test and evidence that the lesson presents as the purpose of testing.

8. Assessment of learning

Graded activity in class

The main evidence is the GitLab repository submitted by each team, which must contain a Markdown document describing the test case with objective, precondition, test procedure, expected result, obtained result and post-condition, the automated test implementation, an RTM entry linking the requirement to the test and its evidence, and a commit history with at least three commits related to the work.

10. Risks and contingencies

Exposition exceeding the planned time

Slides 13, 14, 24 and 25 can be summarised with a pointer to sections 7 and 11 of the material, preserving the forty minutes of the graded activity.

Team without a clear requirement

The team starts from the business driver it named on slide 3 and chooses the domain rule associated with it.

Automation not finished in class

The team versions the manual test case and the partial automation before the end of the class, and the instructor records which part of the chain is missing.

Problems with GitLab access

The team keeps the files locally and pushes them as soon as access is restored, so that the commit history still reflects the work.

11. Closing

The meeting closes with the questions slide after the activity. The central proposition of the lesson is that a team decides what must be protected, why it matters, how it will be verified and where the proof will be recorded, and the RTM entry submitted by each team records the answer to those four questions for one requirement of the project.
