2. Learning objective

By the end of the meeting, students should be able to apply the concepts of Operating Systems and Virtualization to the project, within the scope of virtualization, containers and resource management in modern operating systems.

Observable outcomes

  • Describe the responsibilities of the operating system and distinguish a process from a thread, including the synchronisation concerns that shared memory introduces.
  • Compare virtual machines and containers by isolation, weight, startup time and typical use.
  • Use the --memory and --cpus flags, or mem_limit and cpus in Compose, to test the application on a constrained machine and list what to observe.
  • Classify a Docker Hub image as official, verified publisher or community and state the checks required before using a community image.
  • Compare the development, staging and production Dockerfiles and explain the multi-stage build and the non-root user of the production image.
  • Run the four stages of the staged Docker workflow (build, startup, business rules and full stack) and relate each stage to the requirement type it verifies.

3. Meeting outputs

Constrained run

The application of the group executed under a memory and CPU limit, with the observed behaviour compared with the unconstrained run.

Environment comparison

The table of development, staging and production configurations from section 5 of the material, applied to the Dockerfiles the group already has or plans to write.

Verification map

The correspondence between the four Docker stages and the requirement types of the project, following the traceability matrix of section 13 of the material.

Continuity

The staged workflow reuses the verification vocabulary of Lesson 1, since Stage 3 runs integration tests against a real database and Stage 4 runs end-to-end tests in a containerised stack. The non-root user, the official base images and the rule against secrets in the image connect with the lesson on web and cloud systems, which treats secrets management and least privilege from the security side.

4. Preparation

Student responsibilities

  • Read the written material of the lesson before the meeting.
  • Install Docker and Docker Compose and confirm that docker run works on the machine.
  • Bring the repository of the group project, with its Dockerfile if one already exists.

Instructor responsibilities

  • Prepare a small image, such as myapp:dev in the examples, to demonstrate the resource limits and the startup health check.
  • Have the PostgreSQL container and the docker-compose.test.yml of the deck ready to show Stages 3 and 4.

6. Facilitation script

  1. Open with slide 2 and ask the class which responsibility of the operating system their application depends on most, then contrast process and thread through the race conditions that shared memory introduces.
  2. Use slide 3 to compare virtual machines and containers, adding that production environments often combine both strategies.
  3. Pose the question of slide 4, whether the application would still behave correctly on a 512 MB, half-core machine, and ask each group to run its application with the flags of slide 5.
  4. Collect from the groups what changed under the limit, using the list of slide 6: slow startup, out-of-memory crashes, restart loops, queue buildup or timeouts.
  5. Present the core concepts and commands of slide 7 and the Dockerfile practices of slide 8, stressing the order of copying dependency files before the source code and the rule against storing secrets in the image.
  6. On slide 9, ask the groups to classify the base images they use and to say which checks a community image would require.
  7. Compare the three Dockerfiles of slides 10 to 12 with the environment table of section 5 of the material, and explain why the production image runs as a non-root user and excludes build tools.
  8. Walk through Stages 1 and 2 on slides 13 and 14 and ask each group which command would prove that its image builds and starts with a passing health check.
  9. Present Stage 3 on slides 15 and 16 as the place where infrastructure requirements become business constraints, and Stage 4 on slide 17 as the end-to-end test of the containerised stack.
  10. Close with slide 18, relating each stage to the requirement type of the traceability matrix in section 13 of the material, and open the questions slide.

7. Methodology

The meeting follows the strategy recorded for this encounter, a dialogued exposition alternated with guided application to the group project and closed with a check of understanding. The exposition moves from the concept to the command: each topic of the operating system is presented first as a responsibility or a trade-off, and then as a Docker flag, a Dockerfile instruction or a Compose service that the group can run on its own project.

The constrained run of slide 5 is the main moment of guided application, because the group observes on its own application the effects that the deck lists in the abstract. The staged workflow then organises the remaining content as a sequence of verifications, so that the Dockerfile is read as a record of the infrastructure requirements that the project must satisfy before deployment.

8. Assessment of learning

Formative verification

The sources record no graded activity for this meeting. Verification is formative and relies on the constrained run of each group, on the classification of the base images it uses and on its ability to say which Docker stage would verify each requirement type of the project.

10. Risks and contingencies

Docker not installed on some machines

The group runs the commands on the machine of a colleague, and the instructor demonstrates the constrained run on the projector.

Exposition exceeding the planned time

Slides 15 to 17 can be summarised with a pointer to sections 10 and 11 of the material, keeping Stages 1 and 2 and the constrained run.

Group without a Dockerfile

The group uses the TypeScript example of slide 8 as a starting point and adapts the base image to the language of the project.

11. Closing

The meeting closes with the proposition of slide 18: dockerizing early forces the team to state infrastructure requirements, dependencies and business constraints before writing code, and the same containers then serve development, CI/CD and production. The best practices summary in section 14 of the material is the reference for the groups after the meeting.
