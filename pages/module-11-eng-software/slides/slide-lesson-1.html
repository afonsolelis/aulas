1. Por Quê Spec-Driven Development?
O problema de começar a implementar antes de especificar

❌ O Problema Comum

Iniciar a implementação sem definição formal do comportamento esperado resulta em:

  • Retrabalho constante
  • Inconsistência de contratos de API
  • Desalinhamento com stakeholders
  • Testes incompletos
  • Dívida técnica acumulada

✅ A Solução: SDD

Spec-Driven Development é a metodologia onde a especificação técnica é a única fonte de verdade (Single Source of Truth — SSoT):

  • Código deriva da spec
  • Testes verificam a spec
  • Documentação reflete a spec
  • IA gera dentro da spec
Conceitos-Chave: Single Source of Truth
A especificação como documento autoritário

Single Source of Truth (SSoT)

Princípio de arquitetura da informação: cada informação relevante reside em um único artefato autoritário, do qual todas as demais representações são derivadas. Quando duas versões divergem, a fonte única prevalece; as cópias devem ser reconciliadas com ela, jamais o inverso.

Requisito Funcional (RF)

O que o sistema deve fazer: funções e comportamentos observáveis.

Ex: "O sistema deve permitir registro de usuário por nome e e-mail."

Requisito Não Funcional (RNF)

Como o sistema deve se comportar: qualidade, desempenho, segurança.

Ex: "Registro deve concluir em ≤2 segundos sob carga nominal."

SDD vs. TDD

TDD (Test-Driven Development) escreve testes antes do código — fixa correção interna. SDD descreve interfaces e contratos antes — fundamenta o TDD. SDD não substitui TDD, o TDD implementa a verdade definida pela SDD.

2. Qualidade Não Funcional: ISO 25010:2023
9 características mensuráveis de qualidade de software

As 9 Características ISO 25010

Um modelo internacional que define qualidade de forma objetiva, impedindo que requisitos permaneçam implícitos ou subjetivos:

📊 Desempenho

Tempo de resposta, uso de recursos, capacidade.

🔄 Compatibilidade

Coexistência e interoperabilidade com outros sistemas.

👤 Usabilidade

Apreensibilidade, operabilidade, proteção contra erros.

⚡ Confiabilidade

Ausência de falhas, disponibilidade, tolerância a falhas.

🔐 Segurança

Confidencialidade, integridade, autenticidade.

🔧 Manutenibilidade

Modularidade, testabilidade, modificabilidade.

📈 Flexibilidade

Adaptabilidade, escalabilidade, instalabilidade.

🛡️ Segurança Operacional

Fail-safe, alerta de perigo, recupe ração.

✅ Funcionalidade

Correção, completude, propriedade das funções.

3. Os Quatro Pilares de uma Especificação Madura
Componentes essenciais de toda especificação executável

📡 Contrato de API

Rotas, métodos HTTP, códigos de status e payloads de requisição/resposta usando OpenAPI v3.

Exemplo: GET /usuarios/{id} retorna {nome, email} ou 404.

🗄️ Schema de Dados

Tipos, chaves, índices e restrições de integridade no banco de dados.

Exemplo: users.id PK, users.email UNIQUE NOT NULL.

✅ Regras e Cenários

Critérios de aceite em linguagem Gherkin/BDD (Dado/Quando/Então).

Exemplo: "Dado saldo 100, Quando saque 30, Então saldo=70."

📏 Metas de Qualidade

Critérios mensuráveis para cada característica ISO 25010 aplicável.

Exemplo: "Latência ≤100ms p95, complexidade ciclomática ≤5."

4. Anatomia de um Spec: Estrutura Completa
Seções obrigatórias e componentes de uma especificação madura

📋 Seção 1: Visão e Escopo

Propósito: Por que esse sistema/feature existe? Quem são os usuários? Qual o problema que resolve?

Exemplo: "Sistema de cotação que reduz tempo de resposta de 24h para <5min"

📐 Seção 2: Requisitos Funcionais (RF)

Estrutura: RF-001, RF-002, … com ID único. Cada um: descrição, pré-condições, pós-condições.

Exemplo: "RF-001: Usuário cria cotação. Pré: autenticado. Pós: quoteId gerado."

⚡ Seção 3: Requisitos Não Funcionais (RNF)

Estrutura: RNF-001, RNF-002, … com métrica verificável e limite numérico.

Exemplo: "RNF-001: Latência p95 ≤100ms. Medida por Grafana. Falha se >100ms."

🔄 Seção 4: Contrato de API (OpenAPI v3)

Estrutura: Endpoint, método HTTP, parâmetros, payloads, códigos de status, exemplos.

Exemplo: POST /api/v1/quotes | 201 {quoteId, total} | 400 Bad Request

🗄️ Seção 5: Modelo de Dados (Schema DDL)

Estrutura: Entidades, atributos, tipos, chaves primárias, restrições, índices (sem tecnologia específica).

Exemplo: Quote {id:UUID PK, customerId:UUID FK, total:Decimal NOT NULL, createdAt:Timestamp}

✅ Seção 6: Cenários de Teste (Gherkin/BDD)

Estrutura: Dado/Quando/Então para cada caso de sucesso e erro. Cada cenário = critério de aceite.

Exemplo: "Dado customerId válido; Quando crio cotação; Então retorna 201 + quoteId."

5. ADR: Architecture Decision Record
Rastreabilidade de decisões arquiteturais antes de specs e código

O que é um ADR?

Documento que registra uma decisão arquitetural significativa, seu contexto, opções consideradas, decisão tomada e justificativa. É independente de tecnologia — captura o "porquê" de arquitetônico, não o "como" de implementação.

Seções do ADR

  • Título: ADR-001: Usar padrão de fila para processamento assíncrono
  • Status: Proposed | Accepted | Deprecated | Superseded
  • Context: O problema arquitetural
  • Decision: A escolha feita (sem tecnologia)
  • Rationale: Por que essa sobre outras
  • Consequences: Trade-offs e impactos

Exemplo Mínimo

ADR-001: Fila de Processamento

Decision: Processamento assíncrono de cotações via fila.

Rationale: RF-002 exige latência <2s na resposta. Cálculo de desconto é custoso. Fila desacopla lógica de negócio.

Consequences: +1 componente (fila). RNF: taxa de processamento ≥1000 msgs/min.

🎯 Por Que ADR Antes de Spec?

ADR → Spec → Implementação. ADR justifica estrutura e padrões que aparecem na spec. Sem ADR, spec parece arbitrária; com ADR, rastreabilidade é clara. Exemplo: "Por que tem fila aqui? Consulte ADR-001."

6. Documentação Técnica: Sequência Completa (Sem Tecnologia)
Problema → ADR → Spec: a jornada antes de código

1️⃣ Problem Statement (Documento de Problema)

Autoria: PM/PO e stakeholders. Conteúdo: Contexto de negócio, lacunas atuais, restrições, métricas de sucesso.

Não técnico. Foco: "O que não funciona e por quê."

2️⃣ Architecture Decision Records (ADRs)

Autoria: Arquiteto + dev leads. Conteúdo: Decisões estruturais (padrões, patterns, decomposição).

Independente de tecnologia. Responde: "Como estruturamos a solução?"

3️⃣ Specification (Spec Markdown + OpenAPI + Gherkin)

Autoria: Arquiteto + dev team. Conteúdo: RFs, RNFs, API contract, schema, cenários.

Ainda sem tecnologia. Responde: "Qual é o comportamento esperado?"

4️⃣ Technology Selection (Documentado em ADR-Tech)

Autoria: Arquiteto. Conteúdo: Linguagem, banco de dados, framework, justificativa alinhada à spec.

SÓ AGORA escolhe tecnologia. Spec não muda; tecnologia implementa spec.

5️⃣ Implementation Plan (Pseudo-código ou Arquitetura Técnica)

Autoria: Dev team com IA. Conteúdo: Classes, funções, fluxo de código (abstraído de sintaxe).

Tecnologia-agnóstica. Responde: "Quais módulos implementam a spec?"

⚠️ Invariante: Problema → ADR → Spec → Tecnologia → Implementação. Nunca pule etapas. Spec não deve conter "use Node.js" ou "use PostgreSQL" — isso vai em ADR-Tech.

7. Pipeline de Elicitação: 6 Estágios
Da análise de negócio à implementação
1️⃣ Modelagem de Processos (IDEF0): análise as-is — o que a organização faz, lacunas, atores e fluxos.
2️⃣ Modelagem Arquitetural (RM-ODP): casos de uso, entidades, diagramas de sequência, 5 viewpoints.
3️⃣ Esqueleto do Software: estrutura de diretórios, limites de módulo, Docker Compose, projeto vazio mas estruturalmente completo.
4️⃣ Documentos de Especificação (Markdown/YAML): consolidação em formatos legíveis por máquina — 100% autoria humana, IA não participa.
5️⃣ Desenvolvimento Guiado por Testes (TDD): testes que falham inicialmente, consolidando contratos comportamentais (pré-condições, pós-condições, invariantes).
6️⃣ Implementação: somente aqui — manualmente ou com IA — o código é gerado para fazer os testes passarem e atender metas de qualidade não funcional.
OpenAPI (Swagger) e Gherkin/BDD
Linguagens estruturadas para especificação executável

📡 OpenAPI v3

Especificação padronizada legível por máquina, expressa em YAML ou JSON.

Descreve rotas, métodos HTTP, parâmetros, schemas, códigos de status. Contrato explícito entre produtor e consumidor da API.

GET /usuarios/{id} → 200 {nome, email} | 404

✅ Gherkin/BDD

Linguagem estruturada de cenários: Dado/Quando/Então (Given/When/Then).

Legível por humanos e interpretável por ferramentas. Cada cenário = critério de aceite verificável.

Dado saldo 100; Quando saque 30; Então saldo=70.

RM-ODP e Viewpoints

Modelo ISO/IEC 10746 que descreve sistemas distribuídos em 5 pontos de vista complementares, evitando mistura de intenção de negócio, modelo de dados e detalhe tecnológico: Enterprise (propósito, papéis), Information (semântica, estrutura), Computational (decomposição funcional), Engineering (distribuição), Technology (escolhas concretas).

5. Spec-Driven Development e IA
Como a especificação restringe, codifica e verifica geração de código

💡 Três Papéis da Especificação Diante de Modelos Generativos

A IA gera código sintaticamente correto com facilidade, mas sem alinhamento com requisitos não funcionais quando a instrução é vaga. Uma spec bem estruturada:

🚪 Restringe

Limita o espaço de soluções possíveis, evitando decisões arquiteturais improvisadas.

📚 Codifica

Encapsula conhecimento de domínio que o modelo não possui internamente.

✅ Verifica

Define metas de qualidade verificáveis após geração.

Comportamentos que o Modelo Não Infere

Processamento de Eventos Complexos (CEP): análise de fluxos contínuos que correlacionam múltiplos eventos ao longo do tempo (sequências, ausência de eventos, agregações em janelas). Exemplo: alerta após 3 falhas de autenticação em <1 minuto. Essas janelas e ordens devem ser definidas explicitamente na especificação.

6. Verificação e Refinamento Iterativo
Como validar que o código atende a especificação
Característica Estratégia de Verificação
📊 Desempenho Perfilamento (profiling) de tempo e recursos
⚡ Confiabilidade Injeção de falhas, teste de fallback
🔐 Segurança Análise estática, auditoria de código
🔧 Manutenibilidade Complexidade ciclomática, taxa de duplicação

Ciclo de Verificação: código é gerado → verificado contra metas → desvios → relatório retorna à IA com spec original + instrução de correção → regeneração → reverificação até que todas as metas sejam atendidas (máx. N iterações).

⚠️ Importante: Verificação não é uma etapa opcional de revisão manual — é parte integrante do método. Sem verificação, a especificação permanece uma intenção não confirmada.

7. Exemplo Prático: Endpoint de Cotação
Especificação Markdown com contratos, validações e metas não funcionais
# POST /api/v1/quotes — Criar Cotação
Rota: /api/v1/quotes | Método: POST
Cabeçalho Idempotency-Key: UUID obrigatório

## Payload (JSON)
{ customerId: uuid, items: [{ productId, quantity (≥1), priceUnit (>0) }] }

## Regras de Negócio
1. customerId deve ser UUID válido e cliente ativo
2. Total = Σ(quantity × priceUnit)
3. Desconto 5% se quantity ≥ 10

## Respostas
201 Created: { quoteId, total }
400 Bad Request: payload inválido
500 Internal Server Error: erro servidor

## Metas Não Funcionais
🔐 Segurança: sem segredos no código; validação de customerId obrigatória
🔧 Manutenibilidade: lógica de desconto isolada em função
⚡ Confiabilidade: idempotência via Idempotency-Key
🔒 Fail-safe: erro DB → 500 genérico, sem stack trace

OpenAPI Complete: especificação estruturada que pode gerar documentação interativa, validadores e código-base a partir do documento.

📋 Ficha Técnica: Spec-Driven Development
Resumo executivo — o que levar para o projeto

Definição

Metodologia na qual a especificação técnica é a única fonte de verdade (SSoT), fundamentando código, testes, documentação e geração por IA.

Quando Usar

Sempre que há múltiplos stakeholders, requisitos não funcionais críticos ou envolvimento de IA na geração de código.

Os 4 Pilares

1. Contrato de API (OpenAPI)
2. Schema de Dados
3. Regras e Cenários (Gherkin)
4. Metas de Qualidade (ISO 25010)

Artefatos Principais

Documento Markdown estruturado, especificação OpenAPI v3, cenários Gherkin, testes automatizados, verificadores de qualidade.

Sequência Inviolável (Pipeline 6 Estágios)

1. Processos (IDEF0) → 2. Arquitetura (RM-ODP) → 3. Esqueleto → 4. Spec (100% humana) → 5. TDD → 6. Implementação (IA-assistida)

8. Desafio Prático: Aplique SDD Agora
Exercício para fixar o conceito — trabalho em dupla (30 min)

✅ Sua Tarefa

  1. Escolha uma funcionalidade do projeto do seu grupo (ex.: cancelamento de pedido, consulta de faturamento).
  2. Escreva uma especificação Markdown detalhando: rota, payload, validações, 3+ metas não funcionais verificáveis (não genéricas).
  3. Escreva os casos de teste Gherkin que fixam essas regras. Confirme que todos falham inicialmente.
  4. Passe a spec e os testes como contexto para Claude/Gemini gerar a implementação do endpoint.
  5. Execute análise estática (linting, segredos), perfilamento (latência) e teste de falha para validar metas não funcionais.
  6. Se algo falhar: retorne o resultado à IA e peça refinamento sem alterar a spec original.

🎯 Reflexão Final: Comparar: o código gerado com testes escritos previamente foi mais aderente ao esperado do que quando vocês programam sem essa disciplina prévia? Por quê?

📐
Spec-Driven Development
Especificação é contrato. Código é promessa. Testes são prova. IA é executor.

A disciplina de escrever especificações antes de qualquer linha de código não é overhead — é o fundamento que transforma ambiguidade em clareza, e ambição em entrega.
