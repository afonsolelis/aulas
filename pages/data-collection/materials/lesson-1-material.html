1. O problema concreto e o resultado da aula

A partir da Aula 02, cada grupo vai coletar dados de APIs e de páginas web, gravar arquivos JSON e HTML, convertê-los em Parquet e consultá-los com DuckDB. Todos esses passos precisam de um lugar comum para guardar objetos. Se cada integrante gravar no próprio Codespace, os arquivos ficam espalhados, somem quando o Codespace é apagado e ninguém consegue reproduzir a coleta do colega. O grupo precisa de um object storage compartilhado, acessível de qualquer máquina, protegido por credencial e barato o bastante para caber no crédito de avaliação do Railway.

Esse problema é pequeno, mas já tem todos os ingredientes de uma decisão arquitetural: há uma persona com uma dor, há restrições de custo e de plataforma, há atributos de qualidade em tensão (segurança contra praticidade, reprodutibilidade contra atualização) e há riscos que só aparecem quando se pergunta "e se?". Por isso ele serve como primeiro projeto de Spec-Driven Development da disciplina. O professor constrói o projeto ao vivo, etapa por etapa, e cada grupo reproduz o mesmo ciclo no próprio repositório.

Resultado esperado ao fim da manhã

Um repositório do grupo no GitHub com a pasta aula_01_minio/ contendo AGENTS.md, docs/ e specs/ preenchidos para o projeto MinIO; um MinIO no ar no Railway com os buckets raw, bronze, silver e gold; o mesmo MinIO rodando localmente por docker compose; a avaliação ATAM, os ADRs, a matriz de rastreabilidade e o histórico dos prompts enviados.

3. Arquitetura de software aplicada a dados

3.1 O que é um sistema de dados

Um sistema de dados é o conjunto de componentes que leva um fato do mundo até uma decisão. A forma mais útil de enxergá-lo é por cinco responsabilidades, que aparecem em qualquer pipeline, do script de uma tarde até uma plataforma corporativa:

FontesAPIs, páginas web, bancos operacionais, sensores, arquivos.
ColetaProgramas que buscam ou recebem os dados, em lote ou em fluxo.
ArmazenamentoObject storage, bancos relacionais, colunares, filas.
ProcessamentoLimpeza, tipagem, junção, agregação, validação.
ConsumoConsultas, painéis, modelos, APIs para outras equipes.

A disciplina percorre essas cinco responsabilidades ao longo do semestre. Esta aula constrói o armazenamento de objetos, porque é dele que as Aulas 02 a 04 dependem: a Aula 02 grava JSON bruto no bucket raw, a Aula 03 grava resultados de API e de scraping, e a Aula 04 lê o que foi gravado para montar as camadas bronze, silver e gold de um lakehouse. Os nomes dos quatro buckets seguem a arquitetura medalhão: raw guarda o dado como chegou, bronze guarda o dado bruto organizado, silver guarda o dado limpo e tipado, e gold guarda o dado pronto para uma pergunta de negócio.

Arquitetura, nesse contexto, é o conjunto de decisões que são caras de mudar depois: onde o dado fica, quem pode ler, como um componente fala com outro, o que acontece quando algo falha. Escolher a biblioteca de HTTP do coletor é uma decisão de implementação; decidir que todo dado bruto é gravado sem alteração num bucket imutável antes de qualquer transformação é uma decisão arquitetural, porque muda o que se consegue reprocessar, auditar e corrigir meses depois.

3.2 Requisitos funcionais e atributos de qualidade

Um requisito funcional diz o que o sistema faz: "gravar a resposta da API no bucket raw", "criar os quatro buckets". Um atributo de qualidade diz quão bem ele faz, sob quais condições: "a gravação continua correta quando o proxy devolve 502", "nenhum acesso anônimo é aceito". Dois sistemas com os mesmos requisitos funcionais podem ter arquiteturas completamente diferentes porque respondem a atributos de qualidade diferentes. Na prática, são os atributos de qualidade que decidem a arquitetura.

AtributoPergunta que ele fazExemplo no projeto MinIO
DisponibilidadeO serviço responde quando é chamado? O que acontece numa falha?O proxy do Railway devolve 502 esporádico; o cliente precisa tentar de novo.
LatênciaQuanto tempo uma operação leva, medida em qual percentil?Tempo de gravação de um JSON pequeno; sem meta definida, fica como hipótese.
CustoQuanto custa manter, e o que acontece quando o dinheiro acaba?Crédito único de US$ 5 no trial; volumes apagados 30 dias após o fim dos créditos.
IdempotênciaExecutar duas vezes produz o mesmo resultado que uma?Criar buckets com mc mb --ignore-existing; regravar a mesma chave de objeto não duplica.
RastreabilidadeDá para saber de onde veio um dado e por que uma decisão foi tomada?Cada requisito aponta para decisão, componente e evidência em docs/rastreabilidade.md.
Segurança e LGPDQuem acessa, com qual credencial, e onde o segredo fica?Repositório público no GitHub: nenhuma senha pode ser versionada.

Idempotência merece atenção desde já, porque ela é a condição para tentar de novo com segurança. Se o coletor da Aula 02 grava cada lote de telemetria numa chave determinada pela data, pela hora e pelo caminhão (raw/telemetria/data=2026-10-17/hora=12/caminhao=CAM-0412/lote_1200.txt), repetir a gravação depois de um 502 sobrescreve o mesmo objeto. Se a chave incluísse o instante da tentativa, cada repetição criaria um arquivo novo e a contagem de registros ficaria errada sem que nenhum erro aparecesse.

3.3 Decisões arquiteturais e trade-offs

Toda decisão arquitetural compra um atributo pagando com outro. O trabalho do arquiteto é tornar esse preço visível antes que ele seja cobrado. A tabela abaixo mostra três decisões do projeto MinIO e o que cada uma custa.

DecisãoAtributo que melhoraAtributo que piora
Fixar a imagem na tag RELEASE.2025-10-15T17-29-55ZReprodutibilidade: todo deploy roda o mesmo binário.Atualização: correções de segurança exigem trocar a tag manualmente.
Publicar só a porta 9000 (API) e deixar o console 9001 sem domínioSegurança: menor superfície exposta na internet.Usabilidade: não há interface web para o MinIO publicado; usa-se mc.

Uma análise em que nenhuma decisão custou nada indica que alguém deixou de olhar de perto. Esse é um dos sinais que o grupo deve procurar ao revisar o que o agente produzir.

3.5 ADR: registro de decisão arquitetural

Um Architecture Decision Record (ADR), formato proposto por Michael Nygard, é um arquivo curto que registra uma decisão, o contexto em que ela foi tomada, as alternativas descartadas e as consequências. O valor do ADR aparece meses depois, quando alguém pergunta "por que a imagem é da coolLabs e não a oficial?" e a resposta está escrita, com data e motivo. Na disciplina, cada ADR fica em docs/adr/ADR-NNN-titulo.md e segue o modelo do laboratório: status, contexto e forças, requisitos e cenários relacionados, alternativas, decisão com a tática aplicada, consequências positivas e negativas, riscos, evidência necessária e condição de revisão.

ADRs não são apagados. Quando uma decisão muda, cria-se um novo ADR e o anterior recebe o status "substituído por ADR-NNN". O histórico de decisões é, ele próprio, um dado do projeto.

4. ATAM: avaliar a arquitetura antes de confiar nela

O Architecture Tradeoff Analysis Method (ATAM), desenvolvido no Software Engineering Institute da Carnegie Mellon, avalia uma arquitetura confrontando suas decisões com cenários de qualidade que importam para o negócio. O método não produz nota, ranking nem selo de "arquitetura correta". Ele produz cenários mensuráveis, pontos de sensibilidade e de trade-off, riscos, não-riscos e temas de risco, além de uma lista honesta do que ainda não se sabe. Na disciplina, o ATAM é a etapa 7 do SDD: depois de implementar, o grupo pressiona o que construiu.

4.1 Drivers de negócio e utility tree

O ATAM começa pelos drivers de negócio, as forças que pressionam a arquitetura: prazo, custo, regulação, equipe, risco. No projeto MinIO, os drivers são concretos: o crédito do trial é único, o repositório é público, três aulas dependem do storage e o grupo não tem experiência prévia com operação de infraestrutura.

Os drivers são refinados numa utility tree, organizada como atributo, refinamento e cenário. Cada cenário recebe um par (importância para o negócio, dificuldade técnica). A análise começa pelos cenários (alta, alta), onde valor e incerteza se encontram.

4.2 O cenário de qualidade tem seis partes

Um cenário de qualidade transforma uma intenção vaga ("o sistema deve ser seguro") em algo verificável. Ele tem seis partes, e a ausência de qualquer uma delas, principalmente da métrica, impede a verificação.

PartePerguntaExemplo: redeploy não perde dados
FonteQuem ou o que provoca?Um integrante do grupo.
EstímuloO que acontece?Executa railway up com um Dockerfile alterado, ou railway redeploy.
AmbienteEm qual condição?Operação normal, com objetos já gravados em raw.
ArtefatoQual parte é afetada?Serviço minio e volume montado em /data.
RespostaComo o sistema reage?O novo contêiner monta o mesmo volume e os objetos continuam acessíveis.
MétricaComo saberemos que foi suficiente?Contagem de objetos de verificação antes e depois do redeploy é igual; zero objetos perdidos.

Compare duas versões do mesmo cenário. A versão fraca diz: "o storage deve ser confiável". Ela não informa quando, onde, nem como medir. A versão forte diz: "quando um integrante executa railway redeploy com objetos já gravados em raw, o serviço volta com o mesmo volume e a listagem de raw/_verificacao/ mostra os mesmos objetos de antes, verificável por um comando, com zero perdas". A segunda pode ser executada e pode falhar; por isso ela serve para verificar a arquitetura.

4.3 O vocabulário das descobertas

TermoSignificadoExemplo no projeto MinIO

A distinção que mais confunde: sensibilidade é sobre um atributo; trade-off é quando a mesma decisão puxa dois atributos em direções opostas. Todo trade-off é um ponto sensível, mas nem todo ponto sensível é trade-off.

4.4 Táticas de Len Bass

Uma tática, no catálogo de Len Bass, Paul Clements e Rick Kazman (Software Architecture in Practice), é uma decisão de projeto que influencia a resposta do sistema a um estímulo, mirando um atributo de qualidade. Descrever a decisão pela tática, e não pela ferramenta, permite discutir a análise. "Usamos MinIO" não diz qual atributo foi atendido. "Separamos o estado (volume) da computação (contêiner) para que a substituição do contêiner não afete os dados" diz, e permite perguntar qual é o custo.

Regra prática para revisar o que o agente produzir: decisão sem tática nomeada é decisão sem justificativa; tática sem cenário associado é otimização especulativa.

4.5 O que o ATAM entrega no repositório

No esqueleto SDD da disciplina, a análise vai para docs/atam.md (drivers, utility tree, cenários de seis partes, descobertas, riscos aceitos e próximos experimentos), as decisões vão para docs/adr/ e a matriz requisito, decisão, componente, evidência e estado vai para docs/rastreabilidade.md. Cada linha da matriz recebe um estado: atendido quando há evidência executável ou registrada, parcial quando a evidência cobre só parte do critério de aceite (a razão diz qual parte falta) e não atendido, com a razão. Uma linha sem evidência nunca é marcada como atendida. Essa é a mesma convenção cobrada no projeto final.

5. Spec-Driven Development

5.1 Por que especificar antes de pedir código a um agente

Um agente de código, como o Claude Code ou o Codex CLI, lê arquivos, escreve arquivos e executa comandos. Ele é rápido, mas preenche qualquer lacuna do pedido com a resposta mais provável no material em que foi treinado. Se o pedido é "suba um MinIO no Railway", o agente escolhe a imagem, a porta, onde guardar a senha e se o console fica público, e cada escolha parece razoável isoladamente. O problema é que essas escolhas não foram feitas pelo grupo, não estão registradas e não respondem a nenhum requisito. Uma delas (a senha num arquivo versionado de um repositório público, por exemplo) pode ser grave.

Spec-Driven Development inverte a ordem: antes de qualquer código, o grupo escreve, com ajuda do agente, quem é a persona, quais objetivos de negócio importam, quais requisitos o sistema cumpre e com quais critérios de aceite, qual arquitetura atende a esses requisitos e quais tarefas pequenas levam até ela. A especificação vira o contexto do agente. Cada prompt seguinte lê arquivos do repositório em vez de depender da memória da conversa, e cada artefato gerado pode ser revisado, versionado e contestado.

5.2 O ciclo da disciplina

1. PersonaQuem usa o dado, que decisão toma, qual dor.
2. ObjetivosResultados de negócio com métrica, drivers e restrições.
3. SpecRF e RNF com critérios Dado/Quando/Então.
4. PlanoC4 em Mermaid e escolhas ligadas a requisitos.
5. TarefasPequenas, cada uma com requisito e verificação.
6. ImplementaçãoUma tarefa por vez, com teste e evidência.
7. Validação ATAMCenários, descobertas, ADRs e rastreabilidade.

Cada etapa é um prompt independente no formato CREATE, copiado por inteiro. Entre uma etapa e outra, o grupo lê o que foi produzido e responde às perguntas do quadro "Revise antes de seguir". O prompt economiza digitação; a revisão decide se o artefato pode virar fonte de verdade para a etapa seguinte, e é nela que o grupo aprende a reconhecer um requisito mal escrito.

5.4 Rastreabilidade: do requisito à evidência

Rastreabilidade é a capacidade de seguir um fio do requisito até a prova de que ele foi atendido. No SDD da disciplina, o fio tem cinco pontos: o requisito em specs/spec.md, a decisão em specs/plan.md ou num ADR, a tarefa em specs/tasks.md, o teste ou comando de verificação ligado à tarefa e a evidência registrada. Se qualquer ponto faltar, o fio se rompe: um requisito sem tarefa nunca foi implementado de propósito; uma tarefa sem verificação foi implementada sem prova; um trecho de código sem requisito é uma decisão que ninguém pediu.

5.6 Ferramentas de SDD existentes

Spec-Driven Development tem ferramentas próprias. O GitHub Spec Kit organiza o fluxo em comandos para o agente (especificar, planejar, gerar tarefas, implementar) e gera arquivos de especificação no repositório. O OpenSpec propõe um fluxo parecido, centrado em propostas de mudança sobre especificações vivas. As duas servem como referência de como a comunidade está estruturando a prática. A disciplina não depende delas: usa a convenção de pastas da seção 5.3 e prompts CREATE escritos à mão, porque assim cada etapa fica explícita, funciona com qualquer agente e não exige instalar mais uma ferramenta no Codespace.

6. O formato CREATE

CREATE é um formato de prompt proposto por Dave Birss. As seis letras nomeiam as seis partes que um pedido precisa ter para que o modelo não precise adivinhar: Character, Request, Examples, Adjustments, Type of output e Extras. Na disciplina, todo prompt para o agente usa esse formato, com rótulos em português.

6.1 As seis partes, com exemplo

6.2 Por que o formato reduz ambiguidade

Cada parte fecha uma porta que o modelo abriria por conta própria. Sem personagem, o agente assume o papel mais genérico, que costuma ser o de "assistente que resolve tudo" e por isso avança etapas. Sem pedido com caminho de arquivo, ele escolhe onde gravar. Sem exemplo, ele escolhe o formato, e cada execução sai diferente. Sem ajustes, ele inventa números e escolhe tecnologia. Sem tipo de saída, ele escreve demais. Sem extras, ele não sabe quais arquivos são fonte de verdade nem quando parar. O exemplo é a parte que mais muda o resultado: um único RF bem escrito ensina ao modelo o nível de detalhe, a numeração e o estilo do critério de aceite melhor do que um parágrafo de instruções.

6.3 O mesmo pedido, antes e depois

Pedido sem estrutura:

Resultado provável: um documento com requisitos genéricos ("o sistema deve ser escalável"), números sem origem ("disponibilidade de 99,9%"), escolha de tecnologia misturada com requisito e nenhuma ligação com a persona. O mesmo pedido no formato CREATE é o prompt 3 da seção 12.3: ele diz quem o agente é, qual arquivo escrever, mostra um RF de exemplo, proíbe números sem origem, limita o tamanho e manda parar ao final.

7. Boas práticas de prompt para agentes

Um agente de código age no repositório. As práticas abaixo existem porque cada uma evita um tipo de dano observado com frequência em sala.

  1. Um prompt por etapa. Pedir persona, spec e código na mesma mensagem faz o agente produzir tudo raso e impede a revisão entre etapas. Refazer um prompt grande também custa caro, em tempo e em cota do agente.
  2. Contexto por arquivo, e não por memória. O agente deve ler AGENTS.md, docs/ e specs/ a cada etapa. A memória da conversa se perde quando a sessão fecha, quando outro integrante assume ou quando o contexto do modelo enche; o arquivo continua no repositório.
  3. Pedir o plano antes de editar. O agente lista os arquivos que pretende criar ou alterar e o motivo. O grupo confirma ou corrige antes que algo seja escrito.
  4. Critério de parada explícito. Todo prompt termina com "pare ao final da etapa". Sem isso, o agente tende a seguir para a próxima etapa por iniciativa própria.
  5. Gates verificáveis. Uma etapa termina quando um critério objetivo é atendido: o compose valida, o teste passa, a listagem mostra os quatro buckets. "Parece bom" não é gate.
  6. Revisão do diff. Antes de cada commit, git diff e git status. Procure segredos, números sem origem, arquivos fora do escopo e mudanças que ninguém pediu.
  7. Segredos fora do prompt. Nunca cole chave ou senha na conversa. Tudo o que o agente lê, inclusive a saída de comandos que ele executa, é enviado ao provedor do modelo. Por isso, nesta aula, a senha do MinIO é gerada e configurada por uma pessoa do grupo em outro terminal, e o AGENTS.md proíbe o agente de ler .env.
Registre o que foi enviado

Depois de cada prompt, cole o texto enviado em docs/prompts.md, com data, modelo e resultado da revisão. Se o prompt foi refeito, registre as duas versões. Depois, faça o commit da etapa, por exemplo docs(T-00): persona do projeto MinIO.

11. Por que MinIO e por que a imagem da coolLabs

O MinIO é um servidor de object storage que implementa a API S3. Isso significa que qualquer cliente S3 (o mc, a biblioteca boto3, o SDK minio para Python, a extensão httpfs do DuckDB) conversa com ele apenas trocando o endpoint. Rodar o mesmo MinIO localmente e no Railway permite desenvolver com o compose e publicar com o mesmo binário.

Há um fato recente que muda a forma de obter o MinIO. A edição comunitária entrou em modo de manutenção em dezembro de 2025, o repositório foi arquivado em abril de 2026 e a empresa deixou de publicar imagens Docker oficiais. O endereço de download do cliente mc (dl.min.io) responde hoje com HTTP 410. A disciplina usa a imagem mantida pela coolLabs, construída a partir das releases oficiais e usada pelo template de MinIO do próprio Railway: ghcr.io/coollabsio/minio (também publicada como coollabsio/minio no Docker Hub). A tag é fixada em RELEASE.2025-10-15T17-29-55Z, a mesma do template do Railway. Usar latest faria cada deploy depender do que a coolLabs publicou por último.

A imagem já traz o cliente mc (release RELEASE.2025-08-13T08-35-41Z) e não traz curl nem wget. Por isso o healthcheck do compose usa mc ready local. Esses dois fatos foram conferidos no preparo da aula, executando a imagem localmente.

As portas são duas: 9000 é a API compatível com S3, usada por todos os clientes; 9001 é o console web. As credenciais de administrador vêm das variáveis MINIO_ROOT_USER e MINIO_ROOT_PASSWORD, e o comando de execução é server /data --console-address ":9001".

15. Exemplo resolvido de ponta a ponta

Uma linha completa, do driver de negócio até a evidência, para a decisão de expor só a API. É esta a forma que docs/atam.md, o ADR e docs/rastreabilidade.md devem ter ao fim da aula, repetida para cada decisão relevante.

Driver de negócio

O repositório do grupo é público e o MinIO publicado tem um endereço acessível de qualquer lugar da internet. Os dados das Aulas 02 a 04 e do projeto final passam por ele, e qualquer acesso indevido compromete o trabalho do semestre.

Cenário de seis partes (CEN-06)

ParteConteúdo
FonteCliente anônimo na internet.
EstímuloTenta listar o bucket raw e procurar um console de administração no domínio do serviço.
AmbienteOperação normal, serviço publicado no Railway.
ArtefatoServiço minio e seus domínios públicos.
RespostaA API nega a requisição sem assinatura; não existe domínio público que leve ao console.
Métrica100% das requisições sem assinatura recebem 403; zero domínios públicos apontando para a porta 9001.

Decisão e tática

Publicar domínio apenas para a porta 9000 e operar o MinIO publicado pelo mc; o console fica só no ambiente local. Táticas de segurança de Len Bass: limitar exposição (menos portas na internet) e autenticar atores (toda requisição S3 é assinada). A senha gerada e fora do Git aplica limitar acesso e alterar configurações padrão.

Descobertas do ATAM

  • Ponto de sensibilidade: a lista de portas com domínio público define a superfície de ataque do serviço.
  • Ponto de trade-off: sem console remoto, a segurança melhora e a usabilidade piora; inspecionar o storage publicado exige mc.
  • Risco: todos os scripts e integrantes usam a credencial root; um vazamento dá controle total, inclusive de apagar buckets.
  • Não-risco: requisição anônima recebe 403 (evidência: curl registrado em docs/evidencias/T-04_verificar_railway.txt).
  • Tema de risco: dependência de uma única credencial, que reaparece no CEN-02 (credencial vazada).

Status: aceito

Condição de revisão: se o grupo precisar de console remoto, reavaliar com usuário
  de leitura separado (mc admin user add) antes de expor a 9001.
