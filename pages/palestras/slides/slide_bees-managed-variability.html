Retrieval from the Kick Off: options for a new demand

Every demand that reaches the platform ends in one of seven options. This session deals with the technical mechanisms behind the options that keep the demand inside the product.

Poll: which variation mechanism is most used in your systems today? Country or customer conditionals, configuration files, metadata tables, feature flags, entitlements, extension points and adapters, or separate deployments per customer or region.
Planned variability: core, variation points and variants

Software product line engineering separates what is common to every customer from what is allowed to differ, and decides in advance where and when each difference is resolved.

Common core

Shared by all customers and markets

Capabilities and rules that remain consistent everywhere and evolve as part of the common product. At Tradeline, order issuing, the order state machine and the pricing pipeline belong to the core.

Variation point

A declared place where behaviour may differ

A point in the architecture where the product admits alternatives, such as the tax applied to an order. The variation point is designed once and has a known contract.

Variant

One alternative bound to a variation point

The concrete behaviour selected for a market, a tier or a customer, such as IVA at 19% in Colombia. Variants are added without changing the code of the core.

Binding time

When the variant is chosen

At build, at deploy or at runtime. Later binding gives flexibility per tenant and moves cost to testing and operations, because more combinations exist in production.

Pohl, Böckle & van der Linden (2005); Apel et al. (2013)

Five types of variation and their binding time

Classifying a demand before choosing a mechanism avoids treating every difference in the same way. The type indicates who owns the rule and how long it is expected to last.

Multi-tenant models: pool, silo and bridge

The tenancy model decides how much of the infrastructure customers share. It determines the cost to serve, the isolation of failures and the noise one tenant can cause to the others.

Pool

Everything shared

All tenants run on the same services and databases, separated by a tenant identifier. Lowest cost to serve and simplest to evolve, with the risk of noisy neighbours and a blast radius that covers everyone.

Silo

Dedicated resources

Each tenant, or each market, gets its own stack. Strong isolation and easy compliance with residency rules, with higher operating cost and the temptation to let each silo diverge in code.

Bridge

Mixed by layer or tier

Some layers are pooled and others are siloed, for example a shared application tier with a dedicated database for a large distributor. Most real platforms end up here.

Whatever the model, the code needs a tenant context: who the tenant is, its market, tier and entitlements, propagated with every request and every event. Metadata-driven platforms resolve behaviour from that context instead of branching on it.

Golding (2024); Microsoft (2024); Weissman & Bobrowski (2009)

Feature flags and entitlements have different lifecycles

A toggle is classified by why it exists and how long it should live. Using release flags as permanent commercial differentiation is the most common confusion in this topic.

TogglePurposeExpected lifeWho changes it
ReleaseShip incomplete code safely and expose it progressivelyDays to weeks, then removedEngineering
ExperimentCompare variants for a decisionDuration of the experimentProduct and data
OperationsDegrade or switch off a feature under load or failureLong-lived, rarely changedSRE and on-call
PermissionGive access to a capability for some usersLong-livedProduct and support
EntitlementExpress what a customer bought or negotiatedAs long as the contractCommercial, through billing
Each flag needs an owner, a removal date and a test of both paths. An entitlement needs a link to the contract and a single place in the code where it is checked.

Hodgson (2017)

Platform primitives instead of conditionals

A platform team offers a library or service that resolves tenant and market context once. Application code asks the primitive for a policy and no longer knows which country it is serving.

Before · service/orders/pricing.py
def compute_tax(order):
    if order.country == "BR":
        tax = order.subtotal * 0.18
    elif order.country == "MX":
        tax = order.subtotal * 0.16
    elif order.country == "CO":
        tax = order.subtotal * 0.19
    ...
    if order.country == "BR" and \
       order.customer.customer_id == "DIST-0042":
        st = order.subtotal * override
After · policy resolved from context
def compute_tax(order, ctx: TenantContext):
    policy = tax_policies.resolve(
        market=ctx.market,
        delivery_region=order.delivery_region,
        tier=ctx.tier,
        at=order.issued_at,
    )
    return policy.apply(order)

# policies are versioned data with an owner,
# a start date and tests per policy
Golden paths make the primitive the easiest way to build. A new market then becomes a new policy reviewed by the owner of the rule, and not a new branch in every layer.

Fournier & Nowland (2024); Skelton & Pais (2019)

AI agents for large-scale changes

Coding agents speed up the search for every occurrence of a variation and the first draft of the refactoring. The speed is only useful when the output is verified against the repository and the architecture.

1Search

Ask the agent to find every place where the market decides behaviour, in all layers, including SQL and configuration.

2Impact map

Require file, line and reason for each occurrence, and the list of what was searched.

3Verify

Confirm each line by hand, look for spellings the agent did not try and remove false positives.

4Constrain

State the architecture rules in the prompt: public contracts that cannot change, where the primitive lives.

5Review

Review the diff as code from a new colleague: tests of both paths, no secrets, no unsafe input handling.

Generated code inherits the security risks of any code, and some of its own, such as invented dependencies and credentials copied from context. Human review and the usual pipeline checks remain mandatory.

DORA (2025); OWASP (2024)

Lab: three needs at Tradeline

Tradeline is a fictional global B2B ordering marketplace operating in Brazil, Mexico, Colombia, South Africa and the Dominican Republic. Its tax rule already lives as country conditionals in three layers.

Need 1 · Regulatory

Regional tax rule at order issuing

Colombia exempts orders delivered to two departments from IVA, from a legal start date. Mexico may follow with border zones. The rule depends on the delivery address.

Need 2 · Commercial

Approval flow for premium distributors

About 120 premium accounts want orders above their own threshold to wait for a purchasing manager. Some want thresholds per region, one wants two approvers.

Need 3 · Integration

ERP of a large distributor

The largest distributor in South Africa wants orders pushed in real time and stock pulled every 15 minutes from a SOAP ERP that changes twice a year. Others may ask next.

The full brief, the sample repository and the template are in the lab kit: needs-brief.md, tradeline-orders-sample.zip and architecture-option-sketch-template.md.

Differentiation by class and no-login alternative

Both classes run the same lab. The emphasis changes with the profile of the participants.

Class 1 · Developers

Refactoring and the primitive

More time for the assisted refactoring: the group implements the tax policy primitive in the sample repository and keeps the existing tests passing.

Class 2 · Architects, QA, SRE

Mechanisms and isolation

Architects lead the comparison of mechanisms and tenancy models; QA and SRE assess the testability and operability of each option.

No-login alternative

Pre-generated agent output

If Cursor or the repository is not accessible, the group verifies impact-map-pregenerated.md against the code listings in the kit.

Mixed groups work well in both classes. In Class 1, a developer drives the agent while the skeptic checks each occurrence in the code; in Class 2, the QA or SRE participant writes the testing and operating cost lines of the sketch, which are the lines groups most often leave empty.
Assistant facilitators circulate through the breakout rooms. When a group stalls on need 3, they ask which part of the integration belongs to the core contract and which part belongs only to this distributor.
Debrief: comparing the chosen options

Fifteen minutes across groups. The comparison matters more than any single answer.

Questions

Which groups chose the same mechanism for the same need, and did they justify it by the same constraint? What is the testing cost of the preferred option for need 1, measured in combinations of market, region and date? Which occurrences did the agent miss, and why was the search unable to find them? Where did a group use a feature flag for something that will last as long as a contract?

Transferable principles

Classify the variation before choosing the mechanism. Resolve tenant and market context in one place. Give every exception an owner, a cost and an exit path. Treat an impact map produced by an agent as a hypothesis to verify.

5′Need 1 across groups

Two groups present their options for the regional tax rule; the others mark agreement and disagreement.

5′The agent map

Groups compare the occurrences they confirmed, removed and added to the agent's impact map.

5′Needs 2 and 3

One flag-versus-entitlement decision and one adapter decision, with their testing costs.

Formative rubric

There is no grade. The rubric tells each group where its sketch stands and what to strengthen in the post-work.

How the rubric is used

Each group reads its own sketch against the three criteria during the debrief and marks one criterion where it is still developing. That criterion becomes the focus of the post-work.

Evidence the facilitator looks for

A classification for each need, two options with the testing and operating cost written down, and an impact map with at least one occurrence confirmed, added or removed by hand.
